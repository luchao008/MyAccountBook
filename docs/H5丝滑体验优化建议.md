# H5 端「丝滑体验」优化建议

> 实测基线 **2026-10-02** · 对象 `frontend/`（uni-app + Vue 3 + Vite 5，目标端 H5）  
> 所有体积数字由 `node scripts/audit-h5-bundle.mjs` 输出，gzip 口径 = **level 9**（与线上 `gzip_static` 一致），可复现。  
> 每条标了 **适用场景 / 优先级 / 预期收益 / 注意事项**，并区分 **【已做】** / **【建议做】** / **【建议不做】**。  
> 写这份文档的目的不是"再压 20 KB"，而是把力气放到**真正还有空间的地方** —— 结论是：首屏加载已经比较透了，  
> 剩下的空间集中在**交互手感**和**数据竞态**。

## 0. 现状实测：先看数字

### 0.1 关键路径（首屏必须下完才画得出第一帧）

| --------------------- | ------------ | -------- |

## 1. 页面加载性能

### 1.1 【已做，别动】

| 项                  | 说明                                                                                                                               |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| 启动图 `#boot-splash` | 样式内联在 `index.html`（不等 JS 拉 CSS），等 `uni-page-body` 真有文字才撤，6 s 兜底。当初实测：200 KB/s 下 Vue 挂载 2118 ms、登录页真渲染 2841 ms，中间 723 ms 空窗就是它盖住的 |
| 彩色图标动态分包           | 2026-09-16 改的。此前被 15 个文件引用（含首页），首屏白下 212 KB                                                                                      |
| TrendChart 异步组件    | `delay: 0` + 骨架占位，避免切年粒度时先闪空白                                                                                                    |
| 分类图标按端裁剪 + WebP    | H5 只留 `.webp`（94 张 1.884 MB → 0.215 MB，省 88.6%）                                                                                  |
| 页面依赖并行预取           | 每个页面的 chunk 由入口里的 `__vite__mapDeps` 登记，与页面 chunk **并行**下载，渲染层不存在 RTT 瀑布                                                          |
| 部署层                | `gzip_static` + `gzip` 双层（预压优先、动态兜底）、`index.html` `no-cache`、带 hash 的资源一年长缓存                                                     |

### 1.2 【建议做 · P2】登录成功后就预热 `/accounts`

- **适用场景**：冷启动 → 登录页 → 登录成功 → reLaunch 到主页面。这是每个新用户/清缓存用户的必经路径。
- **现状**：`HTML → 入口(103 KB) → 登录页 chunk → [用户输入] → 主页面 chunk → /accounts → (/categories ∥ /transactions/summary)`。`/accounts` 之前的那几跳都是**串行**的。
- **做法**：在 `store/user.ts` 的 `setSession()` 里、**token 落盘之后**，fire-and-forget 调一次 `accountStore.load()`（不 `await`）。
- **收益**：省 1 个 RTT。移动网 RTT 100~300 ms，且这点时间能被登录成功动画 + `reLaunch` 覆盖掉，用户几乎无感。
- **注意事项**：⚠️ 必须**在 token 写入 storage 之后**发起 —— 否则 `utils/request.ts` 的拦截器取不到 token，请求 401 → 拦截器 `reLaunch` 到登录页，**把用户刚成功的登录流程打断**。另外失败要静默（预热不是用户操作，弹 toast 会莫名其妙）。

### 1.3 【建议做 · P2】给前两个屏的 chunk 加 `modulepreload`

- **适用场景**：所有冷启动。
- **现状**：`index.html` 里 **0 条** `modulepreload`（脚本已报 WARN）。浏览器要等入口 chunk 下载 + 解析 + 执行到 `import("./pages-login-index…")` 那一行，才"发现"登录页 chunk 要去下。
- **做法**：写一个构建插件（Vite 的 `transformIndexHtml`），把「登录页 + 主页面」两个 chunk 的 `<link rel="modulepreload">` 注入 `index.html`。
- **收益**：高延迟网络省约 1 个 RTT（100~200 ms）。HTTP/2 下收益有限（连接复用、并发请求），所以是 P2 而不是 P1。
- **注意事项**：
  - ⚠️ **不能手写**。文件名带内容 hash，会跟着每次构建变 —— 手写必然漂移。必须插件自动注入。
  - **只 preload 前两个屏**，别把 19 个页面全列上，那等于"变相全量预下载"。

### 1.4 【建议不做】继续压入口那 103 KB

103 KB gz 基本是 Vue + uni-h5 runtime 的地板。把 vendor 拆出去**不减少总字节**，只增加请求数与一层的调度开销。  
真要继续降，方向是**换掉 uni-app 的 H5 runtime** —— 那是框架级决策，不是这个层级能抠出来的。

## 2. 交互动画与过渡

### 2.1 【建议做 · P2】`transition: all` 收窄成具体属性

- **适用场景**：分类网格（`components/CategoryGrid.vue`）。一屏最多 89 个格子，每格都有这个过渡。
- **现状**：`.icon-box { transition: all 0.15s }`。
- **问题**：`all` 会对**每一个可动画属性**建立过渡 —— 包括 `width` / `height` / `padding` 这些**布局属性**。布局属性一变就走 layout + paint，而不是合成层。
- **做法**：收窄成实际会变的那几个：`background-color, border-color, box-shadow`。
- **收益**：选中/切换时的 layout 次数下降。低端机（本项目的目标机型区间）更明显。
- **注意事项**：选中态是**靠 2px 描边承担**的（`$v11-gold-soft` 压白卡只有 1.07 的可见度）。改过渡属性时**别把 `border-color` 漏掉**，否则选中动画会"跳"一下。

### 2.2 【建议做 · P2】环图拖拽用 rAF 合并写入

- **适用场景**：图表页转盘（`pages/charts/index.vue`）。触摸端 + 桌面端鼠标拖拽。
- **现状**：`onRingTouchMove` / `onDocMouseMove` 每次事件都直接 `rotation.value = …`（`applyPointerAngle`）。
- **问题**：`mousemove` 的采样率在桌面端可以是 **500~1000 Hz**（高回报率鼠标）—— 一次滑动触发的 Vue 更新远超帧率。触摸端一般是每帧一次，问题不大。
- **做法**：指针角度先存普通变量，用 `requestAnimationFrame` 每帧只写一次 `rotation.value`。
- **收益**：桌面 H5 拖转盘更跟手，去掉一帧内多次更新造成的抖动。
- **注意事项**：⚠️ **不要指望框架兜底** —— 已读 `uni-h5` 源码确认：它对 **scroll 事件做了 rAF 节流**（`onPageScroll` 一帧最多回调一次），但对 **touchmove / mousemove 不做任何节流**。另外 `.ring-rotator.dragging { transition: none }` 已经做对了（否则环在追 280 ms 前的角度），别动它。

### 2.3 【建议做 · P2】把 `top` 过渡换成 `transform`

- **适用场景**：`components/CategoryPicker.vue` 的滑动指示条。
- **现状**：`transition: top 0.08s linear`。
- **问题**：`top` 是布局属性，每帧都触发 layout；`transform` 只走合成。
- **做法**：定位从 `top` 改成 `transform: translateY()`。
- **收益**：跟随滚动的指示条不再引起 layout。
- **注意事项**：这是**结构性改动**（改定位方式要同步改赋值），且该文件有一套 `measureAnchors` 锚点测量体系 —— 改之前先把那段读完，别只改 CSS。

### 2.4 【已做，别动】

- `.ring-rotator` 拖拽期间 `transition: none`（松手才吸附）
- `@include reduce-motion` —— 已尊重系统「减弱动态效果」
- 顶栏吸顶用**迟滞**（下滚 20 px 收起、上滚 12 px 恢复）而不是单阈值 —— 避免在阈值上下抖动时吸顶块反复膨胀收缩

### 2.5 【建议不做】给骨架屏加 shimmer 波光

- **现状**：`Skeleton.vue` 里 **0 处** `transition / animation`（已核实），是**静态灰块**。
- **结论**：**不加**。静态骨架在本项目的 iOS 观感下更稳 —— shimmer 会让低端机在"正在加载"这段时间**持续合成**，开销真实、收益只是"看起来在动"。
- 若哪天一定要加，必须挂 `prefers-reduced-motion`，并且要接受低端机的持续帧开销。

## 3. 渲染与响应速度

### 3.1 【建议不做】虚拟列表

- **量级实测**：流水页单组明细一页 100 条（后端 `size` 上限也是 100），真实库里最多的一个月 **259 条**（翻 3 页到底）。
- **结论**：**量级不足以支撑虚拟列表**。在 uni-app 里做虚拟滚动的成本（`scroll-view` 高度计算、各端差异、与现有「分组展开 + 加载更多 + 按日归组」的耦合）远高于收益，而且极易引入"滚动位置跳变""行高抖动"这类**看起来像性能问题的新问题**。
- **判据**：等某一页稳定出现在屏项目 **> 500 条**再回来考虑。

### 3.2 【先测再定 · P2】`categoryStore` 的 `byId` / `fullNameOf` 是 O(n) 闭包 getter

- **现状**：每次调用都 `state.list.find(...)`，全量 89 条分类。
- **猜测中的场景**：流水列表每行都可能调 1~2 次（分类名 + 图标）→ 100 行一次重渲染 ≈ 1.8 万次比较。
- **⚠️ 但这是猜测，不是实测**：89 条量级大概率还在噪声里。
- **做法**：先用 Performance 面板录一段「展开分组 + 加载更多」的 profile，看 `Array.find` 是否真的进热点；进了再改（加一个 `byIdMap` computed，或让消费点自己建 Map）。
- **注意事项**：别凭"看起来是 O(n)"就动手。本项目已经有过「改外键只测一半」的教训（只测"清空"不测"换成另一个值"，接口 200、响应体还是旧值，界面毫无察觉）。**改 getter 前先把 profile 拿出来**。
- **✅ 结论（luchao 2026-10-03 拍板）：不做。** 量级估算 89 条 × 100 行 × 1~2 次 ≈ 1.8 万次 `Array.find` ≈ **不到 1ms**，正常在帧噪声里；既然最可能的结论就是"不需要改"，再花一轮证明它不划算。**这是量级判断，不是"不敢测"。** 详见 `docs/H5丝滑体验优化执行计划.md` §5.8。

### 3.3 【观察项，不改】`expanded` / `loadingDetail` 整体替换 Set

- **现状**：展开一个分组 = `expanded.value = new Set(expanded.value)` → 整张列表 `v-for` 重新 patch。
- **量级**：组数量 ≤ 几十，单次 patch 成本可忽略。
- **判据**：组数上百时，改成 `reactive(new Set())` + 把每个分组拆成子组件，让 patch 收敛到单组。

### 3.4 【已做，别动】

| 项              | 说明                                                                                                            |
| -------------- | ------------------------------------------------------------------------------------------------------------- |
| 滚动监听           | 由 `uni-h5` **rAF 节流**（源码确认 `ticking` + `requestAnimationFrame`），且各页 handler 只在**跨阈值**时才写响应式 → 一帧最多一次，绝大多数帧零写入 |
| 主容器滚动位置        | 用**普通对象**存（刻意不走响应式），并有"正在恢复中"标志防止中间态污染记忆位置                                                                    |
| 分类页 60 Hz 自动滚动 | `clearInterval` 有显式守卫（且注释里记了"不能在清除逻辑之前抛异常"这个坑）                                                                |

## 4. 网络请求与数据加载

### 4.1 【建议做 · **P0**】页面级加载缺「最后写入者胜」保护 —— 这是**正确性**问题，不只是性能

- **适用场景**：**六处**页面级加载点，全都没有请求序号 / 取消
  （⚠️ 2026-10-02 更正：本文初版只列了 3 处，完整枚举后是 6 处 —— 只修 3 处就是"改一半"）：
  - `pages/flow/index.vue` → `loadGroups()`（改筛选、切粒度、切分类层级都会调）
  - `pages/flow/index.vue` → `loadSearchResults()`
  - `components/views/ReportView.vue` → `loadData()`（切 Tab、点 `◀ ▶` 步进时段、改粒度都会调）
  - `pages/charts/index.vue` → `loadData()`（切粒度 / 切方向 / 切层级 / 翻时段；后果是**图例与数据对不上**，
    且它会按错数据调 `resetRotation()` 把转盘转正）
  - `components/views/HomeView.vue` → `loadData()`（下拉刷新 / **切换账本** / 视图激活；
    后果最严重：**跨账本串台** —— 顶部显示「已切到 B」，下面的合计与排行是 A 账本的钱）
  - `pages/calendar/index.vue` → `loadDetail()`（连续点不同日期；后果：格子高亮 A 天、明细列的是 B 天的账）
  - **考虑过但不改**：`calendar` 的 `ensureRange()`（合并型加载 + 已加载月份去重，不存在"旧盖新"）；
    `recycle`/`export`/`import`/`account`/`record`/`category` 的加载（一次性动作或写后读，
    风险属于**重复提交**而不是竞态）；`store/*`（已有 `reqSeq` / 迟到保护）
- **可复现的触发路径**：在两个**后端成本差异大**的请求之间快速切换 ——
  - 报表页 `basic ↔ category` 切 Tab（两个口径工作量差很多）
  - 流水页 `年 ↔ 天` 切粒度
  - 连续点 `▶ ▶ ▶` 步进时段
- **后果（不是"慢"，是**&#x9519;**）**：先发的响应可能后到。
  - **报表**：`Object.assign(report, data)` 把**旧时段**的数据写回去，而界面上的 `period` 已经是新的 → 用户看到「2026-08 的标题 + 2026-06 的数字」。**数字是错的，且不报任何错。**
  - **流水**：`groups.value` 被旧响应覆盖，列表与筛选条件不一致。
  - 两个页面还有一个共同副作用：旧请求的 `finally` 会把 `loading` / `skeleton` 提前置 `false`，**把新请求的加载态关掉**。
- **为什么说"现成范式在手"**：`store/account.ts` 的 `reqSeq` 就是为**完全同一个问题**写的（注释原文：「用序号把"过期响应"整个丢掉，比赌到达顺序可靠」），`store/category.ts` 里也有"迟到响应保护"。**页面层只是漏了同样的守卫。**
- **做法（二选一，建议 A）**：
  - **A. 统一序号守卫**：抽一个 `utils/latest.ts`，导出 `useLatest()` 返回 `run(fn)`，内部自增 seq，只让最新一次的结果落地。三个调用点接上 —— 改动面小、语义明确。
  - **B. AbortController**：`utils/request.ts` 支持传 `signal`，页面持有 controller、新请求前 abort。更彻底（真省流量），但要改请求封装 + 各 API 签名。
- **注意事项**：
  - ⚠️ **不要用"取消所有在飞请求"** —— 会把并发的不同逻辑请求一起杀掉（首页就是 `/categories` 与 `summary` 并行）。
  - 取消/丢弃要按**逻辑键**分组（如 `flow:groups`、`report:load`）。
  - 这一条**即使不做性能优化也应该修**：它现在就能复现出「数字与标题对不上」。

### 4.2 【已做，别动】

- `accountStore.load()` / `categoryStore.load()`：本地缓存守卫 + 并发合并 + 请求序号丢弃过期响应。实测：典型路径（首页→流水→记一笔→返回→首页）原本发 14 个请求、其中 **5 个是重复的 `/accounts`（36%）**，现已收敛到 1 个。
- 切账本的迟到响应保护、`reset()` 清在飞请求
- 流水页首屏骨架：从"等 summary + 明细**两个串行 RTT**"改成"summary 到手即撤骨架，明细自己占位"
- 离线队列：串行补传 + `clientId` 幂等键

### 4.3 【建议做 · P2】把「并发合并 + 短时缓存」下沉到请求层

- **适用场景**：日后新增的页面（日历、回收站、导入…）—— 现在这套能力**只在两个 store 里手写了一遍**，新页面不会自动受益。
- **做法**：`utils/request.ts` 增加可选能力：按 `method + url + 序列化后的 params` 生成 key，合并同时在飞的同 key 请求；可选加 1~2 s 的短 TTL。
- **收益**：各页 `onShow` / `onMounted` 几乎同时触发时的重复请求自动消失。
- **注意事项（每条本项目都踩过）**：
  - **只对 GET / HEAD 合并**。POST / PUT / DELETE 永远不合并（有副作用）。
  - 必须留 `force` 逃生口 —— `accountStore` 的注释已经记过一次：force 会绕过并发合并，否则「删完账本后的回退校验」会复用到删除前就已发出的那次响应。
  - ⚠️ **更隐蔽的一条**：校验 `force` 时不能只看"调用点传了没有"，还要&#x770B;**"传进去后它真的改变了行为吗"** —— 2026-10-01 实测就踩到 `load(true)` 的 `force` 当时并**没有**绕过 in-flight 合并。要有针对 `force` 的测试。

### 4.4 【建议做 · P2】GET 加一次幂等重试（仅网络错误）

- **适用场景**：移动端弱网。现状 `timeout: 10000`、**无重试** —— 一个瞬时抖动就是一次失败提示。
- **做法**：只对 GET，且**错误类型是网络错误 / 超时**（不含 4xx / 5xx 业务错）时重试 1 次，指数退避 300~800 ms。
- **收益**：弱网下的失败率下降，用户少点几次重试。
- **注意事项**：
  - **不能重试 PUT / DELETE**。
  - **POST 新增流水可以重试** —— 因为它有 `clientId` 幂等键（服务端 `(user_id, client_id)` 唯一）。这是本项目少见的「POST 也能安全重试」的特例，代码里要把**这个理由**注明，别让人以为是通用的。
  - 重试必须计入 §4.1 的序号守卫，不能绕过它。

### 4.5 【建议做 · P3】评估 brotli

- **现状**：`deploy/nginx.conf` 只开 gzip，注释写明「`nginx:alpine` 官方镜像没编译 brotli 模块，写 `brotli on` 会让 nginx 启动失败」。
- **做法**：换带 brotli 模块的镜像（自编译或成熟的第三方镜像），加 `.br` 预压缩 + `brotli_static`。
- **收益**：JS / CSS 再降约 15~~20%（对 103 KB 的入口 ≈ 15~~20 KB）。
- **注意事项**：
  - 换了镜像要连**回落路径**一起验：`.br` 优先 → `.gz` 兜底 → 都没有则动态压。
  - ⚠️ **绝不要给 `/api` 加 `proxy_set_header Accept-Encoding ""`** —— 会**悄悄**让接口回到未压缩状态，**且不报任何错**。这是本项目已记录的坑。
- **✅ 结论（luchao 2026-10-03 拍板）：不做。** brotli 本身有效（入口 103.2 KB → 约 82~88 KB），但**换算成等待时间**后：内网（100 Mbps）省 20 KB ≈ **1.6 ms（无感）**／4G ≈ 53 ms／弱网 ≈ 320 ms。本项目是**自托管**（`deploy/` 无 CDN 配置、有 `docker-compose.nas.yml`），主要走内网 ⇒ 收益在"无感"档，而代价是换带 brotli 模块的镜像（改坏了是**线上事故**）+ 改预压缩 + 验回落路径。
  ⚠️ 另注意：开 brotli 会让产物**多一份 `.br`**，与刚做完的 5.1（删 730 KB）方向相反，要一起算净账。若将来挂公网/CDN，需**重新评估**（CDN 多半自带 brotli，改源站反而是白做）。详见 `docs/H5丝滑体验优化执行计划.md` §5.8。

### 4.6 【建议不做】给流水列表做本地全量缓存

金额类数据的一致性成本远高于收益（删/改分类、改账本、离线补传都会让它失效，而"金额显示错了"是不可接受的）。本项目已经有「离线只允许新增」这个克制的边界，**不要越它**。

## 5. 内存与资源管理

### 5.1 【建议做 · P3】把 747 KB 的 `echarts.min.js` 从产物里去掉

- **现状**：`dist/build/h5/uni_modules/qiun-data-charts/static/h5/echarts.min.js` = **730.0 KB raw / 243.5 KB gz**，随包发布 → 进部署目录 → 进镜像 → 进 CDN。
- **用户侧收益 = 0**：已核实它**从不被请求**（`qiun-data-charts` 的 `echartsH5` / `echartsApp` 默认 `false`，全项目无人传；H5 端实际走 `u-charts`）。所以这条是**给部署/运维省**，不是给用户省 —— 别把它当成"性能优化"来汇报。
- **收益**：部署目录 −730 KB（H5 产物 3.9 MB → 约 3.2 MB），构建拷贝、传输、镜像层都少一份。
- **做法**：构建期剔除产物（`vite.config.ts` 里已有 `pruneUnusedIconFormat()` 这类"只动产物"的插件可以照抄形状），或在 `scripts/precompress.mjs` 同层加一个剔除步骤。
- **注意事项**：
  - ⚠️ **不要删源文件**。`src/uni_modules/qiun-data-charts/static/` 是第三方包的一部分，删了以后重装/升级会被覆盖回来；而且将来真要开 echarts 就没了。**只动产物。**
  - 剔除步骤要**可一键关掉**，并注明："若将来有人传 `echartsH5: true`，这个剔除会让图表**静默不显示**"（`<image>` / 图表这类东西坏掉时都不报错，这是本项目反复踩的类型）。

### 5.2 【建议做 · P2】图表页鼠标拖拽的事件监听缺卸载兜底

- **适用场景**：图表页转盘，**H5 + 鼠标**拖拽。


- **现状**：`mousedown` 时给 `document` 挂 `mousemove` / `mouseup`，**只在 `mouseup` 里移除**（`onDocMouseUp`）。页面**没有** `onUnload` / `onHide` 兜底。
- **后果**：若拖拽过程中页面被卸载（返回手势、程序化跳转），两个监听会永远留在 `document` 上，且 `dragging` 停在 `true` → 之后进这一页会出现「还没按下就开始跟手」的幽灵拖拽。
- **做法**：`onUnload`（顺带 `onHide`）里调一次**幂等**的清理函数。
- **收益**：消除监听泄漏 + 幽灵拖拽。
- **注意事项**：影响面只在 H5 + 鼠标、触发窗口窄，所以是 P2 不是 P0；清理函数必须可重复调用（要确认 `onDocMouseUp` 被重复调用不会出错）。

### 5.3 【观察项】分类图标是 94 个独立请求

- **现状**：`static/cat-icons/` 94 张 webp 共 444 KB（均 4.7 KB），一屏列表可能同时出现 20~40 个。
- **结论**：**不建议优化**。总字节小（一屏 < 200 KB）、单张已压到 4.7 KB、URL 带构建版本号 + 一年长缓存 → 这是**一次性成本**。把首页必现的十几个 `preload` 收益 < 10 KB 且会让 `index.html` 变脏，不值。
- 顺带记一条（省得以后再查）：**`<image lazy-load>` 在 H5 是 no-op** —— `uni-h5` 只声明了这个 prop、零处消费。别指望它省请求。

### 5.4 【已做，别动】

- 登出 / 换账号时 `accountStore.reset()` + `categoryStore.reset()` 收敛在一处（`store/user.ts` 的 `clearSessionCaches()`）。401 拦截器虽然只清 storage，但下一次登录必经 `setSession()` → **不会漏**（这条特意核实过，不是推断）。
- `colorIconsReady` 那个全局 Map（470 个 SVG body）常驻约 1 MB —— 打开过一次图标选择器后就一直在。这是单页应用的正常代价；**不建议**离开时释放（会让二次进入重新下载 209 KB gz，净亏）。

## 7. 明确不建议做的（诚实清单）

| 项 | 为什么不做 |
|---|---|
| 虚拟列表 | 量级不够（单页 ≤ 259 条），成本与风险远高于收益（§3.1）|
| 骨架屏 shimmer | 持续合成换"看起来在动"，本项目的观感下静态更稳（§2.5）|
| 继续拆入口 chunk | 103 KB 是 Vue + uni-h5 runtime 的地板，拆不减少总字节（§1.4）|
| 分类图标 preload / 雪碧图 | 一次性成本、总量小，收益 < 10 KB（§5.3）|
| 流水列表本地全量缓存 | 一致性成本高，金额显示错了不可接受（§4.6）|
| 离开图标页释放彩色图标索引 | 会让二次进入重下 209 KB gz，净亏（§5.4）|

## 8. 复现方式

```bash
# 1. 出干净产物（沙箱会拦产物目录删除，需加环境变量）
cd frontend && CODEBUDDY_SAFE_DELETE_ENABLED=0 npm run build:h5

# 2. 体积与关键路径报告
node scripts/audit-h5-bundle.mjs

# 3. 严格模式（接 CI）：预算超标 / 懒加载回归 → 退出码 1
node scripts/audit-h5-bundle.mjs --budget
```

`scripts/audit-h5-bundle.mjs` 的**负向验证记录写在它自己的文件头**里 —— 包括一次"第一次没红"的真实经历：
合成产物里依赖表的下标写法与 vite 真实产物不一致 → 正则没匹配上 → 守卫被"解不出依赖名单"的分支兜住、
报告照样说通过。因此两处已改：① fixture 改成与真实产物同形；② **「解不出依赖名单」从 WARN 升级为 FAIL**。
守卫没跑起来必须吵 —— 否则它就是个永远绿的校验器。
