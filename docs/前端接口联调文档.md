## 1. 统一响应结构

**成功**

```json
{ "code": 0, "data": { ... }, "message": "success" }
```

**失败**

```json
{ "code": 40901, "data": null, "message": "用户名已存在" }
```

失败时 `data` 恒为 `null`，`message` 是**中文提示，可直接 toast 给用户看**。

### 1.1 HTTP 状态码与业务码分离

HTTP 状态码只表达"大类"，`code` 表达"具体原因"。业务码除以 100 取整即为 HTTP 状态码
（如 `40402 → 404`、`40901 → 409`）。

| 场景 | HTTP | body.code |
|---|---|---|
| 成功 | 200 | 0 |
| 参数校验失败 | 422 | 40000 |
| 业务规则不允许（如分类类型不匹配） | 400 | 40000 |
| 未登录 / Token 失效 | 401 | 40100 |
| 登录失败 | 401 | 40101 |
| 资源不存在 | 404 | 40401 / 40402 |
| 冲突（重名） | 409 | 40901 / 40902 |
| 服务端错误 | 500 | 50000 |

> 注意：像"账单不存在"这种**业务性失败也走 HTTP 状态码**（404），
> 不是所有失败都返回 200。前端要按 HTTP 状态码分流，不能只看 body。

## 2. 错误码表（完整）

| code | HTTP | 含义 | 前端建议处理 |
|---|---|---|---|
| `0` | 200 | 成功 | 正常渲染 |
| `40000` | 400 / 422 | 参数无效（含分类类型与账单类型不一致） | toast 提示 message |
| `40100` | 401 | 未登录或登录已过期 | 清 token，`reLaunch` 到登录页 |
| `40101` | 401 | 用户名或密码错误 | 停留在登录页，提示 message |
| `40300` | 403 | 无权限 | toast 提示 |
| `40400` | 404 | 资源不存在 | 提示并返回上一页 |
| `40401` | 404 | 分类不存在 | 刷新分类列表 |
| `40402` | 404 | 账单不存在 | 刷新账单列表 |
| `40900` | 409 | 冲突 | toast 提示 |
| `40901` | 409 | 用户名已存在 | 注册页高亮用户名字段 |
| `40902` | 409 | 分类名已存在 | 分类编辑页高亮名称字段 |
| `50000` | 500 | 服务端异常 | toast「服务异常，请稍后重试」 |

**真实错误响应样例**

```json
// E1 未带 token（HTTP 401）
{ "code": 40100, "data": null, "message": "未登录或登录已过期" }

// E2 token 失效（HTTP 401）
{ "code": 40100, "data": null, "message": "登录已过期，请重新登录" }

// E3 amount=0（HTTP 422）
{ "code": 40000, "data": null, "message": "\"amount\" with value \"0\" fails to match the required pattern: /^(?!0+(\\.0{1,2})?$)\\d+(\\.\\d{1,2})?$/" }

// E4 账单不存在（HTTP 404）
{ "code": 40402, "data": null, "message": "账单不存在" }

// E5 分类类型与账单类型不一致（HTTP 400）
{ "code": 40000, "data": null, "message": "分类的收支类型与账单类型不一致" }

// E6 用户名已存在（HTTP 409）
{ "code": 40901, "data": null, "message": "用户名已存在" }

// E7 分类名重复（HTTP 409）
{ "code": 40902, "data": null, "message": "分类名已存在" }

// E8 登录失败（HTTP 401）
{ "code": 40101, "data": null, "message": "用户名或密码错误" }
```

> E3 的 message 是 joi 原始报错，不适合直接给用户看。
> 建议前端对 `code === 40000 && http === 422` 自己写中文文案，或后端后续统一。

## 3. 前端请求封装（uni-app + luch-request）

放进 `src/utils/request.ts`，一次配好，全站复用。

```ts
import Request from 'luch-request';

// 不同端的 baseURL 见 §7.1，别写死 localhost
const BASE_URL = 'http://127.0.0.1:7001/api';

const http = new Request({
  baseURL: BASE_URL,
  timeout: 10000,
  header: { 'Content-Type': 'application/json' },
});

// 请求拦截：注入 token
http.interceptors.request.use((config) => {
  const token = uni.getStorageSync('token');
  if (token) {
    config.header = { ...config.header, Authorization: `Bearer ${token}` };
  }
  return config;
});

// 响应拦截：剥掉 {code,data,message} 外壳，业务代码直接拿 data
http.interceptors.response.use(
  (response) => {
    const body = response.data;
    if (body.code === 0) {
      return body.data; // ← 关键：只返回 data
    }
    // 业务失败（luch-request 仍走 success 回调，因为 HTTP 是 2xx）
    uni.showToast({ title: body.message, icon: 'none' });
    return Promise.reject(body);
  },
  (error) => {
    const status = error?.statusCode;
    const body = error?.data;

    if (status === 401 || body?.code === 40100) {
      uni.removeStorageSync('token');
      uni.removeStorageSync('userInfo');
      uni.reLaunch({ url: '/pages/login/index' });
      return Promise.reject(body);
    }

    uni.showToast({ title: body?.message || '网络异常，请稍后重试', icon: 'none' });
    return Promise.reject(body || error);
  }
);

export default http;
```

配好之后，业务里就是这样（**注意没有 `.data.data`**）：

```ts
const categories = await http.get('/categories', { params: { type: 'expense' } });
// categories 直接就是数组
```

### 3. GET `/categories` — 分类列表

按 `sort` 升序、同 sort 按 `id` 升序返回。只返回当前登录用户的分类。

**Query 参数**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| type | string | 否 | `income` / `expense`，不传返回全部 |
| parentId | string | 否 | `root` 只返回一级分类；传具体 ID 返回该父下的二级分类；**不传返回全部**（前端自行组树） |
| visibility | string | 否 | `all`（默认）/ `visible`。见下方「隐藏」一节 |

**隐藏（`isHidden`）与 `visibility`**

分类可以「隐藏」——语义是**只从「记一笔」的分类选择器里消失**，其余场景完全不受影响
（分类管理页仍可见、历史交易 / 明细 / 统计照旧）。

| 取值 | 返回 | 谁在用 |
|---|---|---|
| `all`（**默认**） | 全部，含隐藏的 | **分类管理页**：必须能看到被隐藏的分类，否则用户没有任何入口取消隐藏（功能死锁） |
| `visible` | 仅可用于记账的：自身未隐藏，且二级分类的父也未隐藏 | 「记一笔」的分类选择器 |

**一级分类隐藏时，其下二级也一并选不到** —— 这个判断在**查询侧**做，
不给二级分类冗余写 `is_hidden`：否则取消隐藏父级时还要回滚所有子分类，极易漏掉而留下脏数据。
所以你会看到「父的 `isHidden=true`、子的 `isHidden=false`」这种组合，那是**正确状态**，不是数据错乱。

用显式枚举而不是布尔参数（如 `visibleOnly=true`）：**query 值都是字符串，`"false"` 是 truthy**，很容易埋坑。

**响应**（`GET /api/categories?type=expense`）

```json
{
  "code": 0,
  "data": [
    { "id": "287", "userId": "2", "name": "居家物业", "type": "expense", "icon": "🏠", "sort": 1, "parentId": null, "isHidden": false },
    { "id": "301", "userId": "2", "name": "日常用品", "type": "expense", "icon": "🧻", "sort": 1, "parentId": "287", "isHidden": false }
  ],
  "message": "success"
}
```

**前端**

```ts
export const getCategories = (type?: 'income' | 'expense', parentId?: string) =>
  http.get('/categories', { params: { type, parentId } });
```

### 分类的两级结构（重要）

分类**最多两级**：`parentId === null` 是一级分类，指向某个一级分类的即为二级。

| 场景 | 做法 |
|---|---|
| 只想要一级分类 | `getCategories(type, 'root')` |
| 想要某个一级下的二级 | `getCategories(type, parentId)` |
| 想自己组树 | 不传 `parentId`，拿全量后按 `parentId` 归组（推荐，**一次请求即可**） |

几条硬规则（后端强校验，违反返回 `40000`）：

1. **二级分类下不能再挂子分类**（不支持三级）
2. 二级分类的 `type` 必须与父分类一致
3. 创建二级时传的 `parentId` 必须是一级分类，否则 `40000`
4. 已经**有子分类**的分类，不能再挂到别的分类下（否则会形成三级）
5. 分类名在同一用户下**全局唯一**（不分层级）——所以不能在不同一级下用同名二级

**记账时怎么用**：分类选择器**只允许选到二级**（一级仅用来切换分组），
所以提交的 `categoryId` 必然是一个二级分类的 id。
金额与统计层面无影响——统计会把它聚合到所属一级。

> 后端没有强制"交易必须挂二级"：历史数据与批量导入仍可能挂在一级上，
> 统计口径（聚合到一级）对两种情况都成立。这条约束目前由前端交互保证。

**统计口径**：分类占比与首页排行**按一级聚合**——挂在二级上的交易会归到它的一级父分类。
`GET /statistics/category` 返回的 `categoryId` / `name` 因此都是一级分类。

**删除**：删除一级分类会**连同其下二级一并删除**，返回 `deletedChildren` 告知删了几个；
相关交易变为「未分类」（`category_id` 置 NULL）。

**图标**：`icon` 字段现在直接存 emoji（如 `🏠`），老数据的标识符（如 `food`）仍然兼容。

### 14. GET `/statistics/category` — 分类占比

**Query 参数**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| month | string | 是 | `YYYY-MM` |
| type | string | 否 | `income` / `expense`；不传则收支一并统计 |

**响应**（`GET /api/statistics/category?month=2026-09&type=expense`）

```json
{
  "code": 0,
  "data": [
```

- 按 `sum` 降序，可直接喂给环形图（本项目用 SVG 自绘的 `RingChart`，见 §5/14 `components/RingChart.vue`）

### 14.5 GET `/statistics/overview` — 首页总览

一次返回**历年累计**以及**今天 / 本周 / 本月 / 本年 / 去年**五个区间的收支。
首页首屏要展示 6 组数字，拆成多次请求会拖慢首屏，所以合成一个接口。

**Query 参数**

| 参数 | 必填 | 说明 |
|---|---|---|
| accountId | 否 | 按账本统计；不传则统计全部账本 |

**响应**

```json
{
  "code": 0,
  "data": {
    "total": {
      "income": "16000.00",
      "expense": "131.40",
      "balance": "15868.60",
      "count": 7
    },
    "ranges": [
      {
        "key": "today",
        "label": "今天",
        "period": "2026-09-11",
        "start": "2026-09-11",
        "end": "2026-09-11",
        "income": "0.00",
        "expense": "119.40",
        "balance": "-119.40",
        "count": 4
      },
      {
        "key": "week",
        "label": "本周",
        "period": "09-07 - 09-13",
        "start": "2026-09-07",
        "end": "2026-09-13",
        "income": "8000.00",
        "expense": "131.40",
        "balance": "7868.60",
        "count": 6
      }
    ]
  },
  "message": "success"
}
```

`ranges` 固定 5 项，顺序为 `today` / `week` / `month` / `year` / `lastYear`。

> **本周按周一至周日计算**（国内习惯）。区间边界由后端统一计算，
> 前端直接用 `period` 文案展示即可，不要自己算——否则各端口径容易不一致。
>
> 所有金额是两位小数字符串；`balance` 可能为负（支出大于收入）。

### 15. POST `/categories/batch-delete` — 批量删除分类

一级与二级可混合传入。传一级会连同其下二级一并删除（外键 CASCADE）。

**请求**

```json
{ "ids": ["301", "302", "287"] }
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| ids | string[] | 是 | 1–200 个；重复 id 会自动去重 |

**响应**

```json
{ "code": 0, "data": { "success": true, "deleted": 9, "deletedChildren": 7 }, "message": "success" }
```

| 字段 | 说明 |
|---|---|
| `deleted` | **实际消失的分类总数**（含被级联删掉的二级） |
| `deletedChildren` | 其中因删除一级而连带删掉的数量 —— 提示文案要用它，别自己在前端算 |

**两条硬约定**：

1. **父子同时被选中不会重复计数**。删一级会 CASCADE 掉它的二级，所以"父已被选中"的二级
   从直接删除清单里剔除。`deleted` 报的是**实际消失的数量**（示例里 287 + 它的 7 个二级 + 另一个孤子 = 9）。
2. **有任何一个 id 不存在 / 不属于当前用户 → 整单失败**（`40401`），不做"静默少删"。
   少删会让前端提示的数量与用户预期不符，同时把越权尝试掩盖掉。

历史账单不会被删除，其 `category_id` 置为 `NULL`，在统计中归入「未分类」。

---

### 16. POST `/categories/batch-hide` — 批量隐藏 / 恢复显示

**请求**

```json
{ "ids": ["301", "287"], "hidden": true }
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| ids | string[] | 是 | 1–200 个 |
| hidden | boolean | 是 | `true` 隐藏、`false` 恢复显示 |

**响应**

```json
{ "code": 0, "data": { "success": true, "updated": 1, "hidden": true }, "message": "success" }
```

⚠️ **`updated` 可能小于传入的 id 数**：示例里传了 2 个（一个二级 + 它的父），
只写了 1 条 —— 父被选中时，其子分类**不重复写入**（由「父隐藏 ⇒ 子不可选」的查询侧规则覆盖）。
这不是漏写，是为了让「取消隐藏父级」时不需要回滚任何子分类。

## 5.5 账本接口（多账本）

| # | 方法 | 路径 | 说明 |
|---|---|---|---|
| 15 | GET | `/accounts` | 账本列表 |
| 16 | POST | `/accounts` | 新建账本 |
| 17 | PUT | `/accounts/:id` | 改名 / 改图标 / 设为默认 |
| 18 | GET | `/accounts/:id/delete-preview` | 删除前预检 |
| 19 | DELETE | `/accounts/:id?confirmName=xxx` | 删除（需名称确认） |
| 20 | POST | `/accounts/merge-preview` | 合并前预检 |
| 21 | POST | `/accounts/merge` | 执行合并 |

**账本列表**（`GET /accounts`）

```json
{
  "code": 0,
  "data": [
    {
      "id": "3",
      "userId": "2",
      "name": "默认账本",
      "icon": "wallet",
      "sort": 0,
      "isDefault": true,
      "createdAt": "2026-09-11T06:35:31.140Z"
    }
  ],
  "message": "success"
}
```

**删除前预检**（`GET /accounts/:id/delete-preview`）

```json
{ "code": 0, "data": { "transactionCount": 12 }, "message": "success" }
```

> 先调它拿到"会连带删除多少笔"，再放进确认弹窗。只剩一个账本时该接口会返回 `40002`。

**删除**（`DELETE /accounts/:id?confirmName=默认账本`）

```json
{ "code": 0, "data": { "success": true, "deletedTransactions": 12 }, "message": "success" }
```

⚠️ **`confirmName` 必须与账本名完全一致**，否则返回 `40001`。删除不可恢复。

**合并前预检**（`POST /accounts/merge-preview`）

```json
// 请求
{ "targetId": "3", "sourceId": "7" }
// 响应
{ "code": 0, "data": { "sourceTotal": 30, "willMove": 28, "willSkip": 2 }, "message": "success" }
```

| 字段 | 含义 |
|---|---|
| `sourceTotal` | 源账本总笔数 |
| `willMove` | 会迁入目标账本的笔数 |
| `willSkip` | 因**与目标完全重复**会被丢弃的笔数 |

**执行合并**（`POST /accounts/merge`）：请求同上，响应在预检结果基础上多返回 `targetId`/`sourceId`/`sourceName`。

⚠️ **合并后源账本会被删除，不可恢复**。先调预检拿到报告，让用户确认后再执行。

### 账本相关的错误码

| code | HTTP | 含义 |
|---|---|---|
| `40403` | 404 | 账本不存在 |
| `40903` | 409 | 账本名已存在 |
| `40001` | 400 | 删除时 confirmName 与账本名不一致 |
| `40002` | 400 | 不允许删除最后一个账本 |
| `40003` | 400 | 不能把账本合并到它自己 |

### 账本参数怎么传给老接口

`transactions` 与 `statistics` 新增了可选的 `accountId`：

```ts
// 记一笔：带上当前账本
http.post('/transactions', { type, amount, recordDate, note, accountId: '3' });

// 列表 / 统计：按当前账本筛选
http.get('/transactions', { params: { page: 1, size: 20, accountId: '3' } });
http.get('/statistics/monthly', { params: { month: '2026-09', accountId: '3' } });
```

> **不传 `accountId` 时行为与改造前完全一致**：记账自动落到默认账本，列表与统计覆盖全部账本。
> 老代码不改也能跑。

### 当前账本的切换方式

**前端本地存储** `currentAccountId`，不占后端字段：

```ts
uni.setStorageSync('currentAccountId', accountId);
```

进页面时校验该 ID 是否仍存在，不存在（被删/被合并）则自动回落到默认账本 —— 详见 `store/account.ts`。

## 6. 数据格式约定（最容易踩的坑）

| 项 | 约定 | 为什么 |
|---|---|---|
| **金额** | 请求响应都是**字符串**（`"38.50"`） | 避免浮点精度丢失；前端计算前 `Number()`，展示时用字符串原样显示 |
| **记账日期** | `YYYY-MM-DD` 字符串 | 与 MySQL `DATE` 对应，不做时区转换 |
| **createdAt** | ISO 8601 UTC，如 `2026-09-11T05:38:02.331Z` | ⚠️ 是 UTC 时间，格式化展示前要转本地时区（`dayjs(createdAt).format(...)` 默认会转） |
| **ID** | 字符串（BIGINT UNSIGNED） | JS Number 精度上限，统一用字符串比较，别用 `===` 比数字 |
| **ratio** | 数字百分比 | 77.78 = 77.78% |
| **分类类型一致性** | 支出账单只能挂支出分类 | 后端强校验，违反返回 40000 |

## 7. 联调环境注意事项

### 7.1 各端 baseURL 不一样

| 端 | baseURL | 坑 |
|---|---|---|
| H5 | `http://127.0.0.1:7001/api` | 浏览器跨域，后端需开 CORS（当前未开，建议用 devServer 代理） |
| 微信小程序（开发者工具） | `http://127.0.0.1:7001/api` | 需勾选「不校验合法域名」 |
| 微信小程序（真机） | `http://<本机局域网IP>:7001/api` | ❌ `127.0.0.1` 在真机上指向手机自己 |
| App | 同真机 | 需要局域网 IP 或正式域名 |

建议按环境取值：

```ts
const BASE_URL = import.meta.env.DEV
  ? 'http://192.168.1.100:7001/api' // 真机调试换成局域网 IP
  : 'https://your-domain.com/api';
```

### 7.2 跨域（H5）

后端当前**未配置 CORS**。两个解法：

1. 开发时用 Vite 代理（推荐）
2. 后端加 `@midwayjs/cors`

Vite 代理示例（`vite.config.ts`）：

```ts
server: {
  proxy: {
    '/api': { target: 'http://127.0.0.1:7001', changeOrigin: true },
  },
}
```

此时前端 baseURL 改为 `/api`。
