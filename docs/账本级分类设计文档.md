# 账本级分类设计文档

> **状态：已实现（2026-09-16）。**
> 本文档描述**把分类从「用户级共享」改为「账本级隔离」**的完整方案。
> 它与 `docs/多账本设计文档.md` 的 §2.3 / §10-4 **直接冲突** ——
> 那两处写的「分类不分账本」是 2026-09-11 的旧约定，本文档**取代**它。
> 阅读顺序：先看 §0 与 §1，再看数据模型与迁移（§2–§3），最后是接口与前端（§4–§5）。

---

## 0. 一句话概括

**每个账本拥有自己独立的一套分类。** 新建账本时从「默认账本（母本）」
勾选要用的分类（默认全选），勾中的复制成新账本的分类行；
之后可在账本的「分类设置」页随时增删。

---

## 1. 背景与决策记录

### 1.1 背景

现状（2026-09-11 起）：`categories` 挂 `user_id`，**用户级共享**，
每用户 89 个（支出 13+55、收入 2+19），与账本无关。
`docs/多账本设计文档.md` §2.3 明确写了"分类反映个人记账习惯，跨账本复用才是正常诉求"。

**新需求**：新建账本时可以选择该账本需要的分类 —— 即**账本级隔离**。

### 1.2 决策记录（逐项与使用方确认，共 26 条）

| # | 决策点 | 结论 |
|---|---|---|
| D1 | 隔离方式 | **物理隔离**：`categories` 加 `account_id`，新建账本时**复制**选中的分类成新行 |
| D2 | 存量迁移 | 现有 89 个分类**全部划归默认账本**；其他账本迁移后分类为空 |
| D3 | 新建账本默认勾选 | **默认全选**（89 个全勾），用户取消掉不要的 |
| D4 | 交互形态 | **独立页** `pages/account-new/index`（不用弹窗，分类多，窄屏/大字号下弹窗太挤） |
| D5 | 建完能否再改 | **能，随时可改**（账本列表提供「分类设置」入口） |
| D6 | 候选分类来源 | **来自默认账本（母本）**。默认账本永远是全套 89 个的权威来源 |
| D7 | 合并账本时的分类 | **按 name 匹配**：找得到就改指向目标账本的同名分类；找不到就复制一份过去 |
| D8 | 分类管理页语义 | **只管当前账本**（页面内容随「当前账本」切换） |
| D9 | 勾选粒度 | **一级二级都能勾，勾一级连带其下全部二级**（复用 `FlowCategoryPicker` 的交互模式） |
| D10 | 移除有交易的分类 | **禁止移除**，提示"该分类下有 N 笔交易" |
| D11 | 「隐藏」功能 | **保留，语义不变**（只从「记一笔」选择器消失，不删数据） |
| D12 | 非默认账本的存量交易 | 迁移后其分类为空 → 那 **6 笔**交易的 `category_id` **置空**（变未分类） |
| D13 | 「给已有账本加分类」的入口 | **两处分工**：分类设置页 = 从母本批量勾选导入；分类管理页 = 在当前账本新建全新分类 |
| D14 | 删除默认账本 | **保留可删**；删后新默认账本从 preset **自动补齐为全套 89 个** |
| D15 | 唯一键 | `(account_id, name)` —— **账本内唯一**，不同账本可有同名分类 |
| D16 | 默认账本的分类能否删 | **受保护，不能删**（它是母本）。只允许改名/换图标/隐藏 |
| D17 | 只勾二级时的父级 | **父级自动带上**（分类树永远完整，不产生孤儿） |
| D18 | 切到空账本记账 | **自动从默认账本静默导入**全部 89 个（用户无感） |
| D19 | 非默认账本新建的分类 | **不进母本**。想全局可用必须先去默认账本建 |
| D20 | 推进方式 | **文档先行**（本文档），review 通过后再写代码 |
| D21 | 文档位置 | **本文档独立成篇**；`多账本设计文档.md` §2.3/§10-4 加指针 |

> 注：D3/D9/D17 三者在 UI 上相互配合 —— 默认全选（D3）、勾一级连带二级（D9）、
> 只勾二级时自动带上父级（D17），共同保证「用户看到的树始终完整、操作最少」。

## 2. 数据模型变更

### 2.1 `categories` 表

**新增列**：

| 列 | 类型 | 说明 |
|---|---|---|
| `account_id` | BIGINT UNSIGNED NOT NULL | 所属账本，外键 → `accounts.id` `ON DELETE CASCADE` |

**唯一键变更**：

```
旧: uk_user_name (user_id, name)          -- 用户级唯一
新: uk_account_name (account_id, name)    -- 账本内唯一
```

> 保留 `(user_id, name)` 的旧注释里解释了"为什么不用 (user_id, parent_id, name)"
> （MySQL 唯一索引不约束 NULL）。新键 `(account_id, name)` 同样不含 `parent_id`，
> 理由相同：一级分类 `parent_id` 为 NULL，纳入唯一键反而拦不住重名。

**外键策略**：

- `account_id` → `accounts.id` **ON DELETE CASCADE**：
  删账本时其下分类一并删除（与"删账本 = 删其中数据"一致）。
  ⚠️ 但**默认账本受保护**（D16），且它是母本 —— 见 §2.3。
- `parent_id` → `categories.id` **ON DELETE CASCADE**（不变）。
- `transactions.category_id` → `categories.id` **ON DELETE SET NULL**（不变）。

### 2.2 新不变量

> **交易的 `category_id` 所指分类，必须与交易的 `account_id` 属于同一账本。**

这是本方案的核心约束。所有写入路径（创建/更新交易、合并账本）都必须校验它。

### 2.3 「默认账本 = 母本」的维护规则

| 场景 | 行为 |
|---|---|
| 新建账本（D6） | 候选 = 默认账本的分类；勾中的复制进新账本 |
| 默认账本被删（D14） | 新默认账本从 `category-preset` **重建全套 89 个**（即使它原本只有子集） |
| 默认账本的分类删（D16） | **禁止**。想精简用「隐藏」，或在其他账本里不选它 |
| 非默认账本新建分类（D19） | 只属于该账本，**不写回母本** |
| 空账本被记账（D18） | 静默从默认账本导入全部 89 个 |

## 3. 迁移方案

### 3.1 存量数据（实测，2026-09-16）

| 指标 | 值 |
|---|---|
| 用户数 | 125 |
| 账本总数 | 182（默认 125 + 非默认 **57**） |
| 有多账本的用户 | 55 |
| 非默认账本里的交易 | **6** |
| 交易总数 | 223 |

### 3.2 迁移步骤（顺序不可变）

```sql
-- 1. 加列（先允许 NULL，便于回填）
ALTER TABLE categories ADD COLUMN account_id BIGINT UNSIGNED NULL;

-- 2. 回填：每个用户的所有分类 → 其默认账本
UPDATE categories c
JOIN accounts a ON a.user_id = c.user_id AND a.is_default = 1
SET c.account_id = a.id;

-- 3. 非默认账本的交易：分类置空（D12）—— ⚠️ 不可逆，见 §3.4
UPDATE transactions t
JOIN accounts a ON a.id = t.account_id
SET t.category_id = NULL
WHERE a.is_default = 0;

-- 4. account_id 收紧为 NOT NULL
ALTER TABLE categories MODIFY COLUMN account_id BIGINT UNSIGNED NOT NULL;

-- 5. 唯一键：旧删新加
ALTER TABLE categories DROP INDEX uk_user_name;
ALTER TABLE categories ADD UNIQUE KEY uk_account_name (account_id, name);

-- 6. 索引：给 account_id 加普通索引（按账本查分类）
ALTER TABLE categories ADD INDEX idx_account_sort (account_id, sort);

-- 7. 外键：account_id → accounts.id ON DELETE CASCADE
ALTER TABLE categories ADD CONSTRAINT fk_category_account
  FOREIGN KEY (account_id) REFERENCES accounts(id) ON DELETE CASCADE;
```

**迁移后的数据形态**：

- 每个用户只有**默认账本**有 89 个分类
- **57 个非默认账本分类为空**（用户下次切进去记账时按 D18 自动导入）
- 6 笔原属非默认账本的交易变**未分类**

### 3.3 迁移执行方式

按项目约定，走 TypeORM migration：

```
src/migration/<ts>-CategoryPerAccount.ts
```

⚠️ **迁移里不要用 `rebuildCategories` 那套 seed 逻辑** ——
migration 只做结构 + 归属回填，preset 重建放 seed。

### 3.4 回滚与风险

| 项 | 可逆性 |
|---|---|
| `account_id` 列、唯一键、索引、外键 | ✅ `migration:revert` 可还原结构 |
| 分类归属（全归默认账本） | ⚠️ 回滚后无法恢复"原本属于谁"（本来就没这个信息） |
| **6 笔交易的分类（置空）** | ❌ **不可逆**。迁移前必须**快照备份** `SELECT id, category_id FROM transactions WHERE account_id IN (SELECT id FROM accounts WHERE is_default=0)` |

**迁移前必做**：把上述快照存到 `docs/` 或 `memo/` 下的文件（项目约定：证据要留痕）。

## 4. 接口变更

### 4.1 分类接口（`/api/categories`）

现有 6 个接口**语义从「用户级」改为「账本级」**，并新增 `accountId` 参数：

| 方法 | 路径 | 变更 |
|---|---|---|
| GET | `/api/categories` | 新增 `accountId`（必传，缺省用当前账本） |
| GET | `/api/categories/:id` | 校验归属时增加"同账本" |
| POST | `/api/categories` | 新增 `accountId`；唯一性校验改 `(accountId, name)` |
| PUT | `/api/categories/:id` | 同上 |
| DELETE | `/api/categories/:id` | **新增前置校验**：分类下有交易则拒绝（D10） |
| POST | `/api/categories/batch-delete` | 同上校验 |
| POST | `/api/categories/batch-hide` | 语义不变 |

**新增接口**：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/accounts/:id/category-candidates` | 返回默认账本的分类树，供"新建账本选分类"和"分类设置导入"用（D6/D13） |
| POST | `/api/accounts/:id/categories` | 从母本**批量复制**指定分类进该账本（body: `{ categoryIds: [] }`，勾一级连带二级） |

### 4.2 账本接口（`/api/accounts`）

| 方法 | 路径 | 变更 |
|---|---|---|
| POST | `/api/accounts` | 新增可选 `categoryIds`（不传 = 全选，D3） |
| DELETE | `/api/accounts/:id` | 删默认账本时，新默认账本**重建全套 89 个**（D14） |
| POST | `/api/accounts/merge` | 合并时分类**按 name 匹配/复制**（D7） |

### 4.3 交易/统计接口

所有涉及分类的查询与写入**增加同账本校验**：

- `POST/PUT /transactions`：`categoryId` 必须属于 `accountId`（否则 400）
- `GET /transactions`、`/statistics/*`：分类筛选自动限定在当前账本
- 关键词搜索（搜分类名）：`JOIN categories` 时按当前账本

### 4.4 新增错误码

| code | HTTP | 含义 |
|---|---|---|
| `40004` | 200 | 分类下有交易，不能移除（D10） |
| `40005` | 200 | 分类与交易不属于同一账本 |
| `40006` | 200 | 默认账本的分类不允许删除（D16） |

## 6. 对现有功能的影响

| 功能 | 影响 |
|---|---|
| 分类管理页批量操作 | 改为账本内操作；删除需过"无交易"校验 |
| 合并账本 | 分类按名匹配/复制（D7），不再"直接迁交易" |
| 统计/报表/首页排行 | 分类聚合限定当前账本 —— **天然一致**（交易本就按账本过滤） |
| 流水分类筛选 | 列表按当前账本 |
| 数据导出 | CSV 的分类列 = 当前账本的分类 |
| seed 脚本 | `rebuildCategories` 要改为"针对默认账本"；新增"为已有账本补分类"逻辑 |
| 软删除/回收站 | 不受影响（分类不参与软删除） |

## 7. 已知取舍

1. **存储膨胀**：每个账本一套分类行。极端情况（用户建 20 个账本 × 89 个）= 1780 行/用户，
   但实际用户只会选自己需要的子集，且分类行很小（~100 字节）。
2. **6 笔交易分类丢失**（D12）：迁移不可逆，已在 §3.4 要求快照备份。
3. **母本与副本会漂移**：默认账本改了分类名，其他账本的同名分类**不会自动同步**
   （物理隔离的必然结果）。用户需自行在各账本改。
4. **非默认账本新建的分类不进母本**（D19）：新账本选不到它 —— 这是有意的语义纯粹性，
   但需要 UI 明确提示"此分类仅属于本账本"。
5. **默认账本不能删分类**（D16）：用户无法从默认账本清掉碍眼的分类，只能用「隐藏」。
6. **合并时的同名不同级**：源账本"餐饮/早餐"、目标账本只有一级"餐饮" ——
   按 D7 会在目标补建"早餐"二级。若目标同时有"餐饮/早餐"和另一个"早餐"，匹配规则需
   在实现时明确（建议：**先匹配同级同名，再匹配任意同名**）。
