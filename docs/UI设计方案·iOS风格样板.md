# UI 设计方案 ·「iOS 原生观感」

> 版本：v1.0 · 2026-09-16 · **状态：待确认**
> 画布样板：Ardot `MyAccountBook · iOS 风格 UI 样板`（fileId `726321994372126`）
> 数值校验：`node scripts/check-ios-tokens.mjs`（**99 项断言**，负向验证已通过）
> 上游依据：`docs/移动端配色与字体方案.md`、`docs/UI设计方案·扁平化.md`（FL-1）

---

## 0. TL;DR

**一句话结论：形取 iOS，色值不照抄。**

把 Apple 的层级语言整套搬过来 —— 分组灰底 + 白卡片、大标题导航、毛玻璃顶栏底栏、
零阴影列表、克制阴影弹层、200–500ms 的转场 —— 成本低、见效快，App 立刻"像个 iOS 应用"。

但**不能直接用 iOS 系统色值**。实测 9 个系统色里有 **8 个不满足 WCAG AA 正文 4.5:1**：

| iOS 系统色 | 压白卡 | 结论 |
|---|---|---|
| `#007AFF` 蓝 | 4.02:1 | 不达标 |
| `#34C759` 绿 | 2.22:1 | 不达标 |
| `#5856D6` 靛 | 5.65:1 | **唯一达标** |
| `#FF9500` 橙 | 2.20:1 | 不达标 |
| `#FF2D55` 粉 | 3.65:1 | 不达标 |
| `#AF52DE` 紫 | 4.13:1 | 不达标 |
| `#FF3B30` 红 | 3.55:1 | 不达标 |
| `#30B0C7` 青 | 2.57:1 | 不达标 |
| `#8E8E93` 灰 | 3.26:1 | 不达标 |

连 Apple 自己的次级文字灰 `#8A8A8E` 也只有 **3.44:1** —— 它好看，但它不是给 AA 合规场景准备的。

所以本方案的做法是：**结构照搬 iOS，色值另配一套经 AA 校准的"文字/按钮版"，
与 iOS 原生值双轨并存**（原生值只作图形填充）。观感差异肉眼几乎不可辨，可读性却达标。

**本次只交付样板与规范，没有改动任何业务代码。** 逐页面改造待确认后启动。

> ⚠️ **v1.1 已修订（2026-09-16 当天）**：初版评审时你指出「线条太深」，并给了 11 张参考图。
> 逐像素采样后确认属实 —— 分隔线应由 `#C6C6C8` 改为 **`#F1F1F1`**、页面底改为 **`#F8F8F8`**、
> 卡片去掉描边、主色由 iOS 蓝改为**暖橙金 + 青绿**。
> **下方 §1–§8 保留初版（v1.0）的原文作为历史快照**；当前有效值见 **§9 v1.1 修订**。
> 按项目既定口径：历史快照不删改，只在"当前状态"处追加。

## 1. 现状体检

### 1.1 项目资产盘点（实测）

| 项目 | 现状 |
|---|---|
| 技术栈 | uni-app + Vue 3 + TypeScript + SCSS，主端 H5 / 小程序 |
| 页面 | **15 个**（含 3 个 `pages/main` 页内视图） |
| 组件 | **22 个** |
| 功能图标 | **31 个**（`frontend/src/constants/icons.ts`，唯一真源） |
| 分类图标 | 15 个 `cat-*` + 彩色体系 329 + 141（生成物） |
| 设计 token | `frontend/src/styles/tokens.scss`（已接入阶段 1–4） |
| 设计语言 | FL-1「数字优先 · 通栏扁平」 |
| 校验脚本 | `check-contrast.mjs`（155 项）、`reflow-audit.mjs`（30 屏）等 25 个 |

### 1.2 现有视觉语言的三条结构性特征

1. **通栏扁平**：页面底 = 卡片 = `#FFFFFF`，分区靠发丝线 `#E6E9EF`，不靠卡片浮起。
2. **几乎无阴影**：全项目 `box-shadow` 仅 **6 处**（其中 2 处还是 `inset` 和 `transition`），
   `backdrop-filter` **0 处**。
3. **无转场动效**：Tab 切换刻意做成"零滑动"单容器多视图。

### 1.3 与 iOS 的差距（也就是本次要补的部分）

| 维度 | FL-1 现状 | iOS 目标 |
|---|---|---|
| 分层手段 | 发丝线 | 背景明度 + 卡片 + 材质 |
| 页面底 | `#FFFFFF`（与卡片同色） | `#F2F2F7` 分组灰（与卡片拉开层次） |
| 顶栏 / 底栏 | 实色 + 1px 线 | 半透明 + 毛玻璃 |
| 主色 | 品牌橙 `#C7430F` | iOS 蓝 `#0060DF` |
| 阴影 | 6 处，接近零 | 仍是零 —— 只给 Sheet / 弹窗 / FAB |
| 动效 | 无 | 100–500ms 分档 + iOS 曲线 |

> 注意最后一行：**iOS 的阴影比 FL-1 更少而不是更多。** iOS 靠"谁浮起来了"表达层级，
> 不是靠"谁加了投影"。这一点两个方案其实高度一致，改造时不要矫枉过正。

## 2. 配色系统

### 2.1 背景三层（实测）

| Token | 值 | 用途 | 明度差 |
|---|---|---|---|
| `bg-grouped` | `#F2F2F7` | 页面底，通铺整屏 | — |
| `bg-card` | `#FFFFFF` | 卡片 / 列表行 | 压灰底 **1.12:1** |
| `bg-inset` | `#EFEFF4` | 内嵌槽（搜索框 / 分段控件底） | 压灰底 **1.03:1** |
| `separator` | `#C6C6C8` | 分组内分隔线 | 压白卡 **1.71:1** |
| `fill-system` | `#E5E5EA` | 按下态填充 | 压白卡 **1.26:1** |

**1.12:1 是刻意的** —— iOS 的分组层次本来就极轻，靠大面积色差而非强对比。
这与 FL-1「页面底与卡片同为白」是根本冲突，必须二选一。本方案选 iOS。

### 2.2 文字阶梯（双底核验）

| Token | 值 | 压白卡 | 压分组灰底 | 用途 |
|---|---|---|---|---|
| `label` | `#1C1C1E` | 17.01:1 | 15.25:1 | 标题 / 金额 / 主文案 |
| `label-2` | `#636366` | 5.99:1 | 5.37:1 | 次级说明、时间戳、表单标签 |
| `label-3` | `#8A8A8E` | 3.44:1 | 3.08:1 | **仅装饰图形**，禁作正文 |
| `placeholder` | `#B4B4BB` | 2.06:1 | 1.85:1 | **仅输入框占位符** |

**关键改进**：原 `$text-tertiary #6E7787` 只能压白卡（4.51:1），换到非白底就跌破。
新的 `label-2 #636366` **双底都达标**（5.99 / 5.37），是唯一一个可以到处用的次级色。
这是"非白背景"这个新前提逼出来的结论 —— 页面底从白变成 `#F2F2F7` 后，
原先所有"只能压白卡"的 token 适用范围都缩小了，必须补一个双底安全的中间色。

### 2.3 主色 · 蓝

| Token | 值 | 压白卡 | 压灰底 | 用途 |
|---|---|---|---|---|
| `blue-native` | `#007AFF` | 4.02:1 | 3.60:1 | **仅图形填充**：图标、选中图形、非文字强调 |
| `blue` | `#0060DF` | **5.62:1** | **5.03:1** | 蓝字 / 链接 / 实心主按钮底 / 焦点环 / Tab 选中 |
| `blue-pressed` | `#004BB3` | — | — | 按下态底色 |

**一个值打通两个场景，这是本方案最省力的决策。**

理由是**对比度是对称的**：白底上的蓝字是 5.62:1，蓝底上的白字同样是 5.62:1。
所以只要选定一个 ≥4.5 的蓝，它就同时满足"作文字"和"配白字的按钮底"两个需求 ——
不需要像原来品牌橙那样拆成 `#CF4A12`（按钮底）+ `#C7430F`（文字）两个 token。
**token 数量直接减半，改造面随之减半。**

（原品牌橙方案是被"白字压 `#FF6B35` 只有 2.84:1"逼着拆的。换蓝之后这个约束消失了。）

### 2.4 辅助色（双轨制）

iOS 原生值作**图形填充**，AA 校准值作**文字**：

| 色 | 原生（图形） | 压白卡 | 校准（文字） | 压白卡 | 压灰底 |
|---|---|---|---|---|---|
| 蓝 | `#007AFF` | 4.02 | `#0060DF` | 5.62 | 5.03 |
| 绿 | `#34C759` | 2.22 | `#157F37` | 5.09 | 4.56 |
| 靛 | `#5856D6` | 5.65 | `#4A48B8` | 7.22 | 6.47 |
| 橙 | `#FF9500` | 2.20 | `#B25000` | 5.20 | 4.66 |
| 粉 | `#FF2D55` | 3.65 | `#D31E45` | 5.20 | 4.66 |
| 紫 | `#AF52DE` | 4.13 | `#7B2FB8` | 7.14 | 6.40 |
| 青 | `#30B0C7` | 2.57 | `#0A6E80` | 5.91 | 5.29 |
| 黄 | `#FFCC00` | 1.51 | `#7E6300` | 5.72 | 5.13 |
| 灰 | `#8E8E93` | 3.26 | `#636366` | 5.99 | 5.37 |

**靛是唯一例外**：原生值 `#5856D6` 本身就 5.65:1 达标，可以直接当文字色用，
不需要校准值。这由一个断言钉住（"原生值即达标的个数应为 1"）。

**黄是唯一改过两轮的**：初版用 `#8A6D00`，压白卡 4.92 达标但压灰底只有 **4.41** 差一点，
加深到 `#7E6300` 后双底都过（5.72 / 5.13）。这正是"背景一变，前景必须重算"的又一次发作。

### 2.5 收支语义色 · 色值不动，改的是载体约束

| Token | 值 | 压白卡 | 压分组灰底 | 结论 |
|---|---|---|---|---|
| `income` 收入 | `#D92D20` | 4.83:1 | **4.33:1** | 跌破，**禁压灰底** |
| `expense` 支出 | `#0B8038` | 5.05:1 | 4.52:1 | 双底达标 |

**这是本次改造最容易被忽略、也最容易出事故的一条。**

`#D92D20` / `#0B8038` 是 2026-09-14 用户明确定下的业务约定（收入红 / 支出绿），
**不随 iOS 改造变更**。但 iOS 把页面底从白改成 `#F2F2F7` 后，
收入红从 4.83 掉到 **4.33**，直接跌破阈值。

处理方式不是改色值，而是加一条**硬性版式约束**：

> **收支金额只能落在白卡片或白色列表行内，绝不直接压 `bg-grouped` 灰底。**

好消息是这条约束在 iOS 分组列表里天然成立 —— 每一行都是货真价实的白色载体，
所以实现时是"顺势"而非额外负担。这条在后续每个页面的改造里都要复核。

### 2.6 深色模式

| Token | 值 | 压 `#2C2C2E` 卡片 | 压 `#1C1C1E` 底 |
|---|---|---|---|
| `dark-label` | `#FFFFFF` | 13.94:1 | 17.01:1 |
| `dark-label-2` | `#98989F` | 4.86:1 | 5.94:1 |
| `dark-blue` | `#0A84FF` | — | 4.66:1 |
| `dark-expense` | `#3DD68C` | 7.43:1 | 9.07:1 |
| `dark-income` | `#FF6B6B` | 5.02:1 | 6.13:1 |
| `dark-bg` / `dark-card` | `#1C1C1E` / `#2C2C2E` | 层级差 1.22:1 | — |

**两处必须提亮，不能复用亮色值**：
- 收入红 `#D92D20` 压暗卡片只有 **2.88:1** → 必须换成 `#FF6B6B`（5.02）。
  （项目原 `$dark-income: #ff6b6b` 的做法本来就是对的。）
- 蓝 `#0060DF` 压暗底只有 3.03:1 → 必须换成 iOS 的 `#0A84FF`（4.66）。

**顺带修正一处历史数值**：`tokens.scss` 里 `$dark-expense: #3dd68c` 的注释写"7.97:1"，
实测压 `#1C1C1E` 是 **9.07:1**、压项目原深色底 `#14161A` 是 **9.66:1**，
7.97 这个数来源不明。建议一并更正注释。

深色模式本轮只做 token 预留：H5 端可用 `@media (prefers-color-scheme: dark)`，
小程序端支持度参差，先不铺开。

## 3. 字体与度量

### 3.1 字体族：一个字都不用改

```
-apple-system, BlinkMacSystemFont, 'PingFang SC', 'Noto Sans CJK SC', sans-serif
```

现有 `$font-family-base` 已经把 `-apple-system` 和 `PingFang SC` 排在前面 ——
在 iOS 上自动命中 SF Pro，中文自动落到苹方。**这就是 iOS 观感最省力的来源**，
属于"已经有了所以不列进改造清单"的项。

### 3.2 字号阶梯：沿用现有 8 档，不推翻

现有阶梯已通过 30 屏 × 200% 字号的重排复验（`reflow-audit.mjs`），**保持不动**：

| Token | 字号/行高 | iOS 对应 | 用途 |
|---|---|---|---|
| `display-lg` | 36 / 44 | Large Title 34 | Hero 金额 |
| `display` | 28 / 36 | Title 1 28 | 页面标题 |
| `h1` | 20 / 28 | Title 3 20 | 卡片标题 |
| `h2` | 17 / 24 | **Headline 17** | 区块标题 |
| `body-lg` | 16 / 24 | Body 17 | 列表金额 |
| `body` | 15 / 24 | Subhead 15 | 正文基准 |
| `body-sm` | 14 / 22 | Footnote 13 | 次要正文 |
| `caption` | 12 / 18 | Caption 12 | 辅助说明（中文硬下限） |

现有的 36/28/20/17/16/15/14/12 与 iOS 的 34/28/20/17/17/15/13/12 高度重合 ——
这不是巧合，两套阶梯都是从同一批光学实验里收敛出来的。**没有推翻的必要。**

**iOS 特征只在字重与字距上补**：
- 大标题（36 / 30）加**负字距 −0.4px**，这是 iOS 大标题的标志性紧凑感。
- 小标签（12px 全大写场景）加**正字距 +0.36px**。
- 字重仍只用 400 / 500 / 600，**禁用 700**（CJK 伪粗体问题，沿用现有约定）。

### 3.3 圆角

| Token | 值 | 用途 |
|---|---|---|
| `xs` | 6px | 色块 / 小标签 |
| `sm` | 10px | **分组列表卡片**（iOS 标准值） |
| `md` | 14px | 按钮 / 输入框 |
| `lg` | 16px | 大卡片 / 图表容器 / Hero 卡 |
| `sheet` | 20px | 底部弹层顶部 |
| `pill` | 999px | 药丸 / 分段控件槽 |

比 FL-1 的 6/10/14 更软一档。iOS 的分组卡片标准圆角是 10px，
弹层和 Hero 卡用更大的 16–20px 制造"更高级"的观感。

### 3.4 间距与行高：三个数字统治全局

| 值 | 含义 |
|---|---|
| **16** | 页面左右边距 = 卡片内边距 |
| **44** | 列表标准行高 = 最小触控目标（WCAG 2.5.8） |
| **32** | 分组与分组之间的呼吸 |
| **12** | 图标与文字的贴合间距 |

保持 FL-1 的 4 的倍数原则（8px 栅格 + 4 半格）。

### 3.5 图标：零成本项

**31 个现有图标一个都不用重画。** 检查 `icons.ts` 的规格后确认：

| 规格 | 现有实现 | SF Symbols | 结论 |
|---|---|---|---|
| 画布 | 24×24 | 24×24 | 一致 |
| 描边 | 1.75px | ~2px | 几乎一致 |
| 线帽/线接 | round / round | round | 一致 |
| 着色 | `currentColor` 单色 | 单色可继承 | 一致 |
| 尺寸阶梯 | 8 档（`$icon-xs`…`$icon-4xl`） | 随字号缩放 | **我们更优**（解耦） |

这套图标本来就是按 SF Symbols 的画法做的。**唯一建议改动**：TabBar 图标从 22px 提到 24px，
与凸起项对齐，也更接近 iOS 习惯。

## 4. 材质 · 阴影 · 动效

### 4.1 阴影：五档，其中一档是"零"

| Token | 参数 | 用途 |
|---|---|---|
| **none** | — | **分组列表、卡片、列表行（默认全部零阴影）** |
| `shadow-card` | `0 1px 2px rgba(0,0,0,.04)` | 独立卡片脱离背景时 |
| `shadow-float` | `0 4px 16px rgba(0,0,0,.10)` + `0 1px 3px rgba(0,0,0,.06)` | 下拉菜单、悬浮卡、Toast |
| `shadow-sheet` | `0 -8px 32px rgba(0,0,0,.16)` | 底部弹层 |
| `shadow-fab` | `0 4px 14px rgba(0,96,223,.35)` | 记一笔悬浮按钮（品牌色投影） |

**默认是零。** 页面上 90% 的元素不该有阴影。

### 4.2 材质：iOS 的灵魂在顶栏与底栏

```scss
background: rgba(249, 249, 249, 0.72);
backdrop-filter: saturate(180%) blur(20px);

/* 降级必须写，否则部分机型是一片纯透明 */
@supports not (backdrop-filter: blur(1px)) {
  background: rgba(249, 249, 249, 0.96);
}
```

**降级方案不是可选项。** uni-app 编译到各家小程序时 `backdrop-filter` 支持度参差，
没有 `@supports` 兜底会出现"导航栏完全透明、文字叠在内容上"的灾难。

### 4.3 动效

| 场景 | 时长 | 曲线 |
|---|---|---|
| 列表行按下 | 100ms 变 / 200ms 回 | `ease-out`，底色转 `#E5E5EA`，**无位移** |
| 按钮按下 | 120ms | `ease-out`，`scale(0.97)` + 底色降为 `#004BB3` |
| Tab 视图切换 | 250ms | `ease-out`，只淡入，**禁止横滑** |
| 页面 push / pop | 300ms | `cubic-bezier(.32,.72,0,1)`，进出并行 |
| 底部弹层 Sheet | 400ms | `cubic-bezier(.32,.72,0,1)`，遮罩 200ms 同步淡入 |
| 金额变化 / 成功反馈 | 500ms | `cubic-bezier(.34,1.56,.64,1)` 弹簧 |
| `prefers-reduced-motion` | 0.01ms | 全部压平，只保留透明度变化 |

**两条从现有实现里继承的正确决定**：
1. **Tab 切换零滑动** —— 项目现在的"单容器多视图"手感正是 iOS 原生 Tab 的行为，
   iOS 的 Tab 切换本来就没有横向滑动。**这条要保留，不要"改成 iOS 风格"反而加上了滑动。**
2. **金额必须配等宽数字** —— 弹簧动效里的数字滚动如果没有 `tabular-nums`，
   宽度会在动画中抖动。

## 5. 组件规范

画布 Board E 已给出可视规格，此处只列关键尺寸。

| 组件 | 关键规格 |
|---|---|
| **分组列表** | 行高 56（双行）/ 44（单行）；左右 16；图标 32；金额等宽右对齐；分隔线 `#C6C6C8` |
| **大标题导航** | 大标题 30/38 Bold → 滚动后收窄为 17px 居中；底部 1px `#C6C6C8` |
| **分段控件** | 槽 `#EFEFF4` 圆角 9；选中项白底圆角 7 + 微投影；文字 14/22 |
| **搜索框** | 高 40；圆角 10；槽底 `#EFEFF4`；图标 18 `#636366`；占位符 16/22 |

## 8. 风险与已知缺口（诚实清单）

### 8.1 三条需要你拍板的取舍

1. **不做 iOS 26 的 Liquid Glass。**
   液态玻璃重度依赖多层高光描边 + `backdrop-filter`，小程序端支持度参差、低端 Android 掉帧。
   本方案用 iOS 17–18 式的"半透明 + 毛玻璃"近似，观感接近、成本可控。

2. **iOS 系统色全部重算了一遍。**
   如果你更看重"和 Apple 文档完全一致的色值"而不是 WCAG AA，可以全部换回原生值 ——
   代价是小字在强光下明显偏淡。**这一条需要你明确选择。**

3. **收支语义色不动，改为约束载体。**
   收入红在灰底上跌破阈值（4.33），方案是"金额只落白卡"而不是改色值。
   如果你愿意微调收入红（例如 `#C62828`），约束就可以取消 —— 同样需要你选。

### 8.2 已知缺口

- **分类图标未绘制**：画布上分类项用色块占位。实际实现时复用现有 `cat-*` 图标与彩色体系。
- **只做了 3 个页面样稿**：其余 12 个页面在改造时按同样的规则推导，未逐一预演。
- **`check-contrast.mjs` 尚未更新**：它现在断言的是 FL-1 的 155 项数值，
  切到新配色后会大面积 MISMATCH —— 这是**预期行为**（有兜底比没兜底好），
  需要在阶段 5 统一改基线。**在此之前不要跑它，免得误判成"改坏了"。**
- **`reflow-audit.mjs` 未覆盖新组件**：分段控件、开关、毛玻璃顶栏都是新增元素，
  需要补进 30 屏巡检清单。

|---|---|---|---|

| `gold` | `#A85F12` | **4.87** | 文字、实心按钮底、Tab 选中、焦点环 |

#### Hero 区块：浅金底 + 深金字（你选的方案，但有个坑我处理了）

你选了浅金方案后我去算了一遍，发现一个必须处理的问题：

**`#FDF6EF` 与页面底 `#F8F8F8` 的亮度差只有 1.01** —— 浅金 Hero 会糊进背景里看不见。
（对比度只算亮度不算色相，所以数值上"看不见"，但人眼其实能靠色相分辨——只是边界会很弱。）

处理方式有两条，都做了：

| 决定 | 原因 |
|---|---|
| 底色做**渐变** `#FDF6EF → #FBF0E4` | 暗端与页面底的亮度差升到 1.06，边界有了；同时渐变比纯色有质感 |
| 文字用 **`#8F5312`** 而不是 `#A85F12` | `#A85F12` 在渐变暗端只有 **4.33**（跌破）；`#8F5312` 是 **5.74 / 5.47**（两端都达标） |

**这是一条通用教训**：加了渐变的区块，要按**最暗的那一端**校验文字，而不是按亮端。
亮端过不代表暗端过 —— 这类"渐变上放文字"的场景，最容易在这里翻车。

### 9.5 一个意外的收获：底色变浅救回了收入红

对比度回升到 4.55，**约束仍然建议保留（余量只有 0.05，太薄）**，但至少不再是硬伤了。

## 12. 补齐"最终版"时发现的三件事

### 12.1 校验器基线**不能现在改** —— 顺序反了

`check-contrast.mjs` 的 155 项断言，守卫的是**代码的当前状态**，不是设计的意图。
如果现在把它改成 v1.1 的值，会出现最糟的状态：**脚本一直红、代码一行没改**，
于是没人再跑它，守卫作用直接归零。

正确顺序是 **设计定稿 → 改代码 → 改脚本断言 → 跑通**。
所以本次交付改为 §11 那张映射表 —— 改造时照它逐行改，改完立刻能跑通。

（`check-ios-tokens.mjs` 不存在这个问题：它守卫的是"设计规范"，与代码无关，所以可以随时更新。）

### 12.2 `reflow-audit.mjs` 的真实缺口不是"新组件"

我上一轮说它"未覆盖新组件"，不准确 —— 它是**按 URL 扫 DOM** 的，
页面已在清单里，新加的分段控件/开关/下划线会被自动扫到。

**真实缺口是：弹层等交互态扫不到。** 脚本只加载 URL，不会去点开：
记一笔的数字键盘、流水页的 5 个弹层、时间选择器的三列滚轮……
这些恰恰是 v1.1 改动最集中的地方。

补法（独立任务，成本不小）：在巡检里对指定页面加"先点击 → 再测量"的步骤。

### 12.3 `color-icons.ts`：接入是零成本，但有个**既有**性能问题

**好消息**：`CategoryIcon.vue` 已经按 icon 值自动分流三种渲染器
（彩色 key → `ColorIcon`、单色 key → `SvgIcon`、emoji → `SvgIcon` 兜底），
所以 v1.1 要的"列表行显示彩色图标"**不需要写任何新代码** ——
用户挑过彩色图标的分类，列表里本来就会显示彩色。

**坏消息（既有问题，不是 v1.1 引入的）**：`utils/colorIcon.ts` 是**静态导入**
`constants/color-icons.ts`（632 KB 源文件）并在模块顶层建索引。
`CategoryIcon` 被首页、流水页等大量使用 → **这些页面的 bundle 里都躺着全量图标数据**。

**已定方案（你选定）：改成延迟加载，首屏省下这 212 KB。**

具体做法：

1. **`utils/colorIcon.ts`** —— 去掉静态 `import { COLOR_ICON_SETS }`，
   改为 `await import('@/constants/color-icons')` 按需载入并缓存索引。
2. **`CategoryIcon.vue`** —— 索引未就绪时先渲染 `SvgIcon`（单色兜底，形状正确），
   就绪后切到 `ColorIcon`。

⚠️ **这次改动要打破一处刻意的设计，必须小心**：
`isColorIconKey()` 现在的判定依据是"**在索引里查得到**"，
源码注释明确写着「不用「含不含冒号」判断，因为那会把将来可能出现的其它带冒号的值误判成图标 key」。
但懒加载后首屏**没有索引可查**，这个判断必须换成格式判断（前缀白名单 + 冒号）。

**改完必须专门复核一条**：单色 key（`cat-food`）与 emoji 不会被误判成彩色 key，
否则会出现"整页图标变白块"——这正是当年把三种情况收敛进 `CategoryIcon` 想避免的事。

顺带收益：省掉启动时遍历 470 个图标建 Map 的开销。

### 12.4 图表序列重排（你选定"整套按参考图重排"）

**参考图实测**（1206×2622 采样）：环形图是**青绿主导** —— 青绿 `#56C4C5` 占 29609 px，
其余是蓝 `#5F8EF4` / 紫 `#6F54F4` / 橙 `#F5862D`。

**但 4 个色里 2 个连 3:1 都不到**（青绿 2.08、橙 2.52）→ **色值不能照抄，只能借色相骨架**。

**踩到的坑**：按参考图的色相顺序直接排（青绿→蓝→紫→橙），
闭环最小可区分度只有 **10 ~ 16** —— 因为这些色相**全挤在冷区**（青 185° / 蓝 213° / 紫 251°），
色盲下几乎同色。而原项目序列是**冷暖交替**排的，所以有 90.15。

**解法分两步**：

1. 闭环序列有个性质：**旋转不改变相邻关系**（末位与首位相接，转一圈相邻对完全相同）。
   所以把青绿从第 4 位**转到首位**，可区分度一分不损。
2. 但有个硬约束：**「其他」必须固定在第 7 位**（前端 `MAX_SLICES = 6` 截断），
   所以不能简单旋转。于是固定「首 = 青绿、末 = 灰」，把中间 5 个**全排列**（120 种）搜一遍 —— 最优解 **73.63**。

**最终序列**：

```
#0E7C86   青绿   4.95   ← 首色，占比最大的分类
#7c3aed   紫     5.70
#0e7c42   翠绿   5.28
#c2185b   品红   5.87
#1d63b8   蓝     5.95
#c2410c   橙红   5.18
#8a94a6   灰     3.06   ← 「其他」专用，禁放白字
```

- 闭环最小可区分度 **73.63**（阈值 70，**余量只剩 3.63**）
- 前 6 色压白 **4.95–5.95**，全部可当白字底色
- 90.15 → 73.63 是**重排的代价**，已记录在案，不是无限余量

**改动极小**：只改了 **1 个色值**（青绿 `#0e7490` → `#0E7C86`，色相 193°→185°，更贴参考图）
+ 重排顺序，其余 6 色原样不动。

⚠️ **不要再动青绿和灰这两个色** —— 它们是当前最弱的一对。
⚠️ 两个真源要同步：`constants/chart.ts` 与 `tokens.scss` 的 `$chart-series`（双写，由校验脚本比对）。

### 12.5 Logo 跟着主色改金（已定，待执行）

**现状**：`frontend/src/static/logo.svg` = 品牌橙 `#CF4A12` 圆角方块（rx 16）+ 白色 ¥，
由生成脚本产出 `logo.png`(192) / `logo-512.png`(512)，登录页与 favicon 共用同一份资源。

**决定：改成深金 `#A85F12`。**

- 白 ¥ 压 `#A85F12` = **4.87**（原有 `#CF4A12` 是 4.52，改完反而更清楚）
- 理由：这个 logo 的结构就是"品牌色方块 + ¥"，**它本身就是主色的载体**，
  没有独立于主色的品牌资产价值。橙色图标配金色 UI 会像两个产品。
  （反例是 Spotify 那类——UI 主题色可以变而 logo 不变，因为 logo 已经独立成立。本项目不属于这种情况。）

**执行时机**：与登录页改造一起做（阶段 4），一次做完三步：

1. 改 `logo.svg` 的 `fill` 与那行注释（`#CF4A12` → `#A85F12`）
2. 重跑生成脚本，产出新的 `logo.png` / `logo-512.png`
3. 登录页与 favicon 自动跟随（同一份资源，无需额外改动）

**不要只改 SVG 不重跑脚本** —— 那样页面会显示旧的橙色 PNG，而源文件已经是金色，
下次别人看会更困惑。
