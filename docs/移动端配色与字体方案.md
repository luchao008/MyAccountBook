# 移动端配色与字体方案

> 适用范围：`frontend/`（uni-app Vue3，目标端 H5，后续可复用到小程序 / App）
> 设计标准：**WCAG 2.2 Level AA**
> 文档中的对比度、灰度差、色盲可区分度**全部为脚本实测值**，非目测。测量方法见附录 A。

---

## 0. 结论先行

| 项 | 结论 |
|---|---|
| 主色 | 品牌橙 `#FF6B35` **降级为装饰色**（不得承载文字）；实心按钮/选中态用 `#CF4A12`，橙色文字用 `#C7430F` |
| 辅助色 | 信息蓝 `#1D63B8`、成功 `#0B8038`、警告 `#B45309`、危险 `#D92D20` |
| 背景色 | 页面 `#F5F6F8`（保留）、卡片 `#FFFFFF`、浅底 `#EEF1F5` |
| 文字色 | 主 `#1F2329` / 次 `#5A6472` / 辅助 `#6E7787` / 禁用 `#A8B0BD` |
| 字体族 | 系统字体栈，**不引入任何中文 Web 字体**（含数字 `tabular-nums`） |
| 最小字号 | **12px 为中文硬下限**，现有 11px 全部抬升 |
| 字重 | 只用 **400 / 500 / 600**，禁用 700（CJK 伪粗体） |
| 行高 | 正文 1.6、标题 1.4、大数字 1.2 |
| 最关键的修复 | 现状有 **9 处对比度不达标**，其中「白字压主色按钮」只有 2.84:1 |

## 1. 现状体检（实测）

### 1.1 三个结构性问题

**① 没有 token 层。** 全 `src/` 扫描出 **40+ 个裸色值**，其中"同义不同值"的灰色多达 5 个：

| 语义 | 现网同时存在的色值 |
|---|---|
| 页面底 | `#f5f6f8`、`#f7f8fa`、`#f7f7f8`、`#f8f8f8`、`#fafafa` |
| 浅分隔底 | `#f5f5f5`、`#f2f3f5`、`#f0f0f0`、`#f1f1f1`、`#eeeeee` |
| 最弱文字 | `#bbb`、`#ccc`、`#c0c0c0`、`#c8c7cc` |

**② `uni.scss` 里的变量引用次数为 0。** 文件里定义了 `$uni-color-primary` 等一整套 token，但**没有任何组件引用过**——它是一个没人用的设计系统。这是最讽刺的一条：项目**有** token 文件，只是它名存实亡。

**③ 颜色直接写在组件里。** 改一次品牌色要动 15 个 vue 文件。

### 1.2 对比度实测（WCAG 2.2 AA）

判定标准：正文 **≥4.5:1**，大字（≥24px 或 ≥18.66px 粗体）**≥3:1**。

| 场景 | 色值 | 实测 | 判定 |
|---|---|---|---|
| 正文 | `#333` on `#fff` | 12.63:1 | ✅ |
| 次要文字 | `#666` on `#fff` | 5.74:1 | ✅ |
| **辅助文字** | `#999` on `#fff` | **2.85:1** | ❌ 需 4.5 |
| **最弱文字** | `#bbb` on `#fff` | **1.92:1** | ❌ |
| **占位符** | `#ccc` on `#fff` | **1.61:1** | ❌ |
| **辅助文字（页面底）** | `#999` on `#f5f6f8` | **2.63:1** | ❌ |
| **白字压主色按钮** | `#fff` on `#ff6b35` | **2.84:1** | ❌ 连大字号的 3:1 都不到 |
| **渐变 banner 未端** | `#fff` on `#ffb347` | **1.78:1** | ❌ 严重 |
| **收入金额** | `#52c41a` on `#fff` | **2.27:1** | ❌ 需 4.5 |
| **支出金额** | `#ff4d4f` on `#fff` | **3.27:1** | ❌ 需 4.5 |
| **Tab 选中** | `#ff6b35` on `#fff` | **2.84:1** | ❌ |
| **Tab 未选中** | `#999999` on `#fff` | **2.85:1** | ❌ |
| 链接色 | `#4a90d9` on `#fff` | 3.34:1 | ❌ 需 4.5 |

**9 处不达标**。其中"白字压橙色按钮"是最要命的一处：它是主操作按钮，用户在阳光下、在低端机上最先看不清的就是它。

> 注意一个反直觉点：**颜色越"好看"越容易不达标**。橙、绿、青这类高明度色相天生对比度低——这不是审美问题，是光学问题。解决办法不是放弃品牌色，而是**给它分派正确的职责**（见 §2.2）。

### 1.3 字号现状

现网实际使用：`11 / 12 / 13 / 14 / 15 / 16 / 26 / 36`，共 8 档，其中 **11px 出现 3 处、13px 出现多处**。11px 的中文在手机上笔画糊成一团，属于"设计师在 27 寸屏上做的决定"。

## 2. 配色方案

### 2.1 三条设计原则

1. **品牌色只做"识别"，不做"承载"**——`#FF6B35` 用于图形、渐变、图标底、图表首色；凡是要在上面写字的地方，一律换深阶。
2. **每个语义只允许一个值**——灰就是灰，不再有 5 个"差不多"的灰。
3. **颜色永不单独传达信息**——收支必须同时有 `+`/`-` 号或文字标签（WCAG 1.4.1）。

### 2.2 品牌主色阶

| Token | 色值 | 白字对比度 | 使用场景 |
|---|---|---|---|
| `brand-50` | `#FFF3EE` | — | 选中行背景、极浅提示底 |
| `brand-100` | `#FFE3D6` | — | 标签底、进度条槽、次级按钮底 |
| `brand-200` | `#FFC7AE` | — | 边框、分割强调 |
| `brand-300` | `#FFA07A` | — | 图形、插画 |
| `brand-400` | `#FF8552` | 2.41 ❌ | 渐变亮端、装饰（**禁放文字**） |
| **`brand-500`** | **`#FF6B35`** | **2.84 ❌** | **品牌基色**：Logo、图标底、渐变、图表首色、装饰条（**禁放文字**） |
| **`brand-600`** | **`#CF4A12`** | **4.52 ✅** | **实心按钮底**（白字）、开关选中底、徽标底 |
| **`brand-700`** | **`#C7430F`** | **4.95 ✅** | **橙色文字**：链接、Tab 选中、焦点环、金额强调 |
| `brand-800` | `#B33A0C` | 5.95 ✅ | 按下态、浅底徽标上的深字 |
| `brand-900` | `#8F2E08` | 8.20 ✅ | 深色渐变暗端 |

**理由**：品牌识别靠的是**色相**而不是明度，所以把 `#FF6B35` 原封不动留在 Logo、图标、图表里，视觉记忆一点没丢；只在"白字压橙底"这类需要对比度的场合换成 `#CF4A12`，人眼在正常浏览下几乎察觉不到这是两个橙。

**另一条路**（如果想 100% 保留 `#FF6B35` 做按钮底）：改用深墨字 `#3D1200` 压在 `#FF6B35` 上，实测 **5.76:1** ✅。适合做「浅橙底 + 深字」的次级按钮，比白字版本更透气。

**首页渐变 banner**：
```scss
// ❌ 现状：#FF6B35 → #FF9563 → #FFB347（白字最差 1.78:1）
// ✅ 改为：
background: linear-gradient(135deg, #CF4A12 0%, #A8380A 100%);  // 白字最差端 4.52:1 ✅
```

### 2.3 辅助色（信息 / 成功 / 警告 / 危险）

| Token | 色值 | on `#fff` | 使用场景 |
|---|---|---|---|
| `info` | `#1D63B8` | 5.95 ✅ | 信息提示、链接型文案、帮助说明 |
| `success` | `#0B8038` | 5.05 ✅ | 保存成功 Toast、正向提示 |
| `warning` | `#B45309` | 5.02 ✅ | 删除前警示、额度提醒 |
| `danger` | `#D92D20` | 4.83 ✅ | 危险操作按钮、错误文案、**支出金额** |

> ⚠️ **不要在同一个列表里同时用 `warning` 和 `brand`**：`#B45309` 与 `#C2410C` 在红绿色盲模拟下距离仅 **11.7**，等于同一个颜色（实测数据）。如果某处两者必须共存，warning 改用 `#9A6700`（偏黄）并加图标区分。

**浅底徽标组合**（深字压浅底，非白底场景，已单独实测）：

| 用途 | 文字色 | 底色 | 对比度 |
|---|---|---|---|
| 收入徽标 | `#0B6B33` | `#E7F6ED` | 5.94:1 ✅ |
| 支出徽标 | `#B42318` | `#FDECEA` | 5.75:1 ✅ |
| 品牌徽标 | `#B33A0C` | `#FFF1EB` | 5.40:1 ✅ |
| 中性徽标 | `#4A5563` | `#EEF1F5` | 6.69:1 ✅ |

> 注意徽标**不能直接复用 `$income` / `$expense` 的色值**——同一个绿压到浅绿底上就掉下去了（实测）：

| 若直接复用主语义色 | 实测 | 判定 |
|---|---|---|
| `$income` `#0B8038` on `#E7F6ED` | 4.52:1 | ✅ 勉强过（余量 0.02） |
| `$expense` `#D92D20` on `#FDECEA` | **4.22:1** | ❌ 差 0.28 |
| `$brand-700` `#C7430F` on `#FFF1EB` | **4.49:1** | ❌ 差 **0.01** |

**结论**：浅底场景必须用专门的深一档文字色（`#0B6B33` / `#B42318` / `#B33A0C`）。这是"同一语义在不同背景上需要不同色值"的典型例子——`#C7430F` 在白底上 4.95:1 达标，压到浅橙底上就只剩 4.49:1。**背景变了，前景必须重算。**

### 2.4 背景与边界

| Token | 色值 | 使用场景 |
|---|---|---|
| `bg-page` | `#F5F6F8` | 页面底色（保留现状，无需改动） |
| `bg-card` | `#FFFFFF` | 卡片、列表项、弹窗 |
| `bg-subtle` | `#EEF1F5` | 输入框底、代码块、次级区块 |
| `bg-mask` | `rgba(0,0,0,0.45)` | 弹窗遮罩 |
| `divider` | `#EDEFF3` | 卡片内分隔线（**纯装饰，豁免对比度要求**） |
| `border-card` | `#E3E7EE` | 卡片描边（装饰） |
| **`border-input`** | **`#8A94A6`** | **表单控件边界**（实测 3.06:1，满足 WCAG 1.4.11 的 3:1） |

**关键区分**：分隔线是"装饰"，可以很浅；**输入框边界是"控件"**，必须 ≥3:1，否则弱视用户找不到这个输入框在哪。现状用 `#c8c7cc` 做边界（≈1.7:1）不达标——这正是很多 App 的表单在弱视用户眼中"消失"的原因。

**焦点环**：`2px solid #C7430F` + `outline-offset: 2px`（4.95:1 ✅）。键盘用户全靠它，别用 `outline: none` 一刀切。

### 2.5 文字色阶

| Token | 色值 | on 卡片 | on 页面底 | 使用场景 |
|---|---|---|---|---|
| `text-primary` | `#1F2329` | 15.78 ✅ | 14.59 ✅ | 金额、标题、列表主文案 |
| `text-secondary` | `#5A6472` | 6.00 ✅ | 5.55 ✅ | 次级说明、表单标签、备注 |
| **`text-tertiary`** | **`#6E7787`** | **4.51 ✅** | 4.17 ✅ | 时间戳、计数、辅助说明（**此前用 `#999`，仅 2.85**） |
| `text-disabled` | `#A8B0BD` | 2.19 | 2.02 | 禁用态（WCAG 豁免，但保留可辨识） |
| `text-inverse` | `#FFFFFF` | — | — | 深底上的文字 |

> `text-tertiary` 的 4.51:1 是**卡着 4.5 线过的**（差 0.01）。这是刻意的：既要满足 AA，又要保持"辅助信息"该有的轻。如果后续要改，只能往深改，不能往浅。

### 2.6 语义色：收入与支出

| 语义 | 色值 | on `#fff` | 场景 |
|---|---|---|---|
| 收入 | `#0B8038` | 5.05 ✅ | 收入金额、结余为正、正向变化 |
| 支出 | `#D92D20` | 4.83 ✅ | 支出金额、负向变化 |
| 中性/结余 | `#1F2329` | 15.78 ✅ | 结余、不区分方向的数字 |

**这里有个必须说清的约定冲突**：

- **记账场景（本项目）**：支出红、收入绿。这与随手记、支付宝账单等国内记账产品的主流习惯一致，且现状代码已经是这个方向，改了反而制造认知断层。
- **投资/股市场景**：**红涨绿跌**（中国内地惯例，与欧美相反）。

**结论：本项目沿用"支出红 / 收入绿"，但这两组语义色 token 禁止被投资类组件复用**——将来若加「理财持仓 / 基金收益」模块，必须另建一组 `market-up`（红 `#D92D20`）/ `market-down`（绿 `#0B8038`）token。把两套约定塞进同一个 token，是未来 bug 的种子。

**并且**：所有收支金额必须带符号。现状明细列表已正确渲染 `+`/`-`，但首页 `formatMoney()` **不输出正负号**（只输出负数号），五区间卡片靠"总收入/总支出"文字标签兜底——这个兜底成立，所以不改也合规；但**新增页面时不能用"只有颜色"来区分收支**。

### 2.7 图表（分类占比环形图）

环形图**最多 7 段**（Top 6 + 「其他」）。不是审美洁癖：8 段以上的环形图，每段都窄到看不清，图例比图还长。

```scss
$chart-series: (
  '#C2410C',  // 1 品牌橙红
  '#1D63B8',  // 2 蓝
  '#C2185B',  // 3 品红
  '#0E7C42',  // 4 翠绿
  '#7C3AED',  // 5 紫
  '#0E7490',  // 6 青
  '#8A94A6'   // 7 中性灰（「其他」专用）
);
```

**实测验收**：

| 检查项 | 结果 |
|---|---|
| 每色对白底对比度 | 3.06 ~ 5.95 ✅（作为填充色可见） |
| **相邻两段**在红/绿色盲下的可区分度 | **最低 75.0**（阈值 ≥70）✅ |
| 全组合最小可区分度 | 15.6（品牌橙红 ↔ 品红）⚠️ 二者不相邻，靠图例兜底 |

**配套硬要求（缺一不可）**：
1. 相邻扇区之间加 **2px 白色描边**（`stroke="#FFFFFF" stroke-width="2"`）——让相似色也被物理隔开；
2. 图例必须显示**分类名 + 金额 + 占比**——这才是满足 WCAG 1.4.1 的真正手段，颜色只是辅助；
3. 对现状 `#7ED321`（青柠）与 `#50E3C2`（薄荷）这种"双绿并存"的调色板要一并替换：两者色相太近，色盲下几乎同色。

### 2.8 使用场景速查

| 界面元素 | 用色 |
|---|---|
| 主按钮（保存/确定） | 底 `#CF4A12`，字 `#FFFFFF` |
| 主按钮按下态 | 底 `#B33A0C` |
| 次级按钮 | 底 `#FFE3D6`，字 `#B33A0C`（5.40:1 ✅） |
| 记一笔悬浮按钮（FAB） | 底 `#CF4A12`，图标 `#FFFFFF` |
| 底部 Tab 选中 | 图标+文字 `#C7430F` |
| 底部 Tab 未选中 | `#6E7787` |
| 金额输入 | `#1F2329`，36px/600，`tabular-nums` |
| 收入金额 | `#0B8038`，带 `+` |
| 支出金额 | `#D92D20`，带 `-` |

## 3. 字体方案

### 3.1 字体族

```scss
$font-family-base:
  -apple-system, BlinkMacSystemFont,        // iOS / macOS：SF Pro + 苹方
  'PingFang SC',                            // iOS 中文
  'HarmonyOS Sans SC', 'MiSans',            // 鸿蒙 / 小米（国产 ROM 主力）
  'Source Han Sans SC', 'Noto Sans CJK SC', // Android 中文兜底
  'Microsoft YaHei',                        // Windows（H5 调试）
  'Helvetica Neue', Arial, sans-serif;
```

**为什么坚决不引入中文 Web 字体**：

1. 中文全字库动辄数 MB，`font-display: swap` 会造成首屏字体跳动（FOUT），对于"打开就要记账"的工具类 App，这是拿 3 秒换一个用户永远注意不到的"字体质感"。
2. 移动端系统字体**已经是最适合该设备的字体**：iOS 上苹方的字形是为小字号屏显优化过的，Android 上各 ROM 自带字体的字重也比 Web 字体更齐全。
3. 已核实：`frontend/` 目录下**没有任何字体文件**（唯一的 `.ttf` 是 `uni-ui` 的图标字体 `uniicons.ttf`）。这个现状是对的，别动。

**数字用等宽数字（这是记账 App 的关键细节）**：

```scss
.amount {
  font-variant-numeric: tabular-nums;   // 数字等宽，纵向对齐
  font-feature-settings: 'tnum' 1;      // 小程序/旧 WebView 兜底写法
  text-align: right;                    // 列表金额右对齐
}
```

**理由**：默认的比例数字（proportional）里「1」比「8」窄，导致金额列表的个位、十位、小数点**竖向错位**（形如"锯齿"）。记账 App 的数字列表是要被"竖着扫"的，等宽数字让小数点排成一条直线，扫读速度显著提升。这条比任何配色微调都更影响实际体验。

### 3.2 字号层级 / 字重 / 行高

单位用 **px**（不用 rpx）：rpx 会随屏宽放大，在 6.7 寸大屏上会让 36px 的金额变成 41px，反而撑破布局。App 内文字应当"物理尺寸稳定"，不跟着屏幕等比放大。

| Token | 字号 | 行高 | 字重 | 使用场景 |
|---|---|---|---|---|
| `font-display-lg` | 36px | 44 (1.22) | 600 | 记一笔页金额输入 |
| `font-display` | 28px | 36 (1.29) | 600 | 首页资产总额 |
| `font-h1` | 20px | 28 (1.40) | 600 | 页面标题、卡片主标题 |
| `font-h2` | 17px | 24 (1.41) | 600 | 区块标题（如"本月各分类支出排行"） |
| `font-body-lg` | 16px | 24 (1.50) | 500 | 列表金额、主要动作文字 |
| `font-body` | 15px | 24 (1.60) | 400 | 正文、表单值、备注（**基准字号**） |
| `font-body-sm` | 14px | 22 (1.57) | 400 | 次要正文、列表副标题 |
| `font-caption` | 12px | 18 (1.50) | 400 / 500 | 辅助说明、时间戳、标签（**中文硬下限**） |

**与现状的差异**：

| 现状 | 处理 | 原因 |
|---|---|---|
| 11px（3 处） | **抬到 12px** | 11px 中文笔画粘连，且低于任何移动端可读性经验下限 |
| 13px（多处） | 并入 12 或 14 | 13 与 12/14 差异肉眼难辨，只增加维护成本 |
| 26px | 调为 28px | 与 36px 拉开过近，层级不清 |
| 行高未声明 | 全部显式声明 | 各端默认行高不一致（浏览器 1.2 / 小程序继承行为有差异），必须显式声明 |

**字重只用 400 / 500 / 600，禁用 700**：
CJK 字体在字重缺失时靠**算法加粗（伪粗体）**补齐，结果是笔画粘连发虚——同一份代码在 iOS 上正常、在某些 Android WebView 上"糊"。600（Semibold）是拿得到真字重的最重档位。
> 若目标端字体确实缺 500，会自动降级到 400，视觉层级会塌一档。**上线前需在 Android 真机复验**（尤其 500 字重的金额行）。

### 3.3 换行与字距

```scss
.text {
  letter-spacing: 0;                    // 中文默认字距，不加
  line-break: anywhere;                 // 长串（如金额）允许断行，防溢出
  word-break: break-word;
}
.text-caps {
  letter-spacing: 0.02em;               // 仅英文全大写标签（如 "TOTAL"）才加
}
```

**WCAG 1.4.4 与 1.4.10 相关**：用户把系统字号调到 200% 时，布局必须不横向滚动（320px 宽仍可用）。因此：所有固定宽度容器改用 `min-width`，金额用 `flex: 1` + `text-overflow: ellipsis` 兜底，不要给 `text` 写死 `width`。

### 3.4 触控目标

WCAG 2.2 SC 2.5.8 要求触控目标 **≥24×24 CSS px**（AA）。本项目建议 **≥44×44**（Apple HIG / Material 的舒适值）——尤其「左滑编辑/删除」的滑动区域、分类网格的九宫格。

## 附录 A：测量方法（可复现）

所有对比度按 WCAG 2.2 相对亮度公式计算：

```
L = 0.2126·R + 0.7152·G + 0.0722·B      （R/G/B 为 sRGB 线性化分量）
Contrast = (L_light + 0.05) / (L_dark + 0.05)
```

**色盲可区分度**：采用 Viénot/Brettel 线性近似模拟绿色盲（deuteranopia）与红色盲（protanopia），在模拟后的线性 RGB 空间取欧氏距离（×255）。
判定阈值：**≥40** 视为可区分；**环形图相邻段要求 ≥70**（因为相邻段是唯一需要"当场分辨"的一对）。

**灰度可辨性**：用相对亮度差 ΔL 衡量，ΔL < 0.05 视为灰度下难以区分。

> 本方案的所有数值均由脚本实测得出。**后续任何颜色改动，都应重跑这套校验，而不是目测。** 校验脚本可按上述公式复现。
