# 多账本设计文档

> 目标：在**保留"唯一默认账本"语义**的前提下，把单账本结构平滑扩展为可管理多账本。
> 覆盖：创建、删除、合并、当前账本切换、默认账本归属、数据迁移。
> 实施状态：**已完成**（后端 + 前端 + 迁移）。本轮落地时单测 75/75、回归 45/45；
> 截至 2026-09-12 全量为**单测 98/98、回归 47/47** 全绿。

---

## 0. 一句话概括

新增 `accounts` 表，交易通过 `transactions.account_id` 归属账本；
**存量数据在迁移中被自动归入各自的「默认账本」，老接口不传账本参数时也自动落到默认账本**，
因此改造对既有功能完全透明。

---

## 1. 四项关键决策（已与使用方确认）

| # | 决策点 | 结论 |
|---|---|---|
| D1 | 合并时的重复判定 | **严格全字段匹配**：金额 + 日期 + 收支类型 + 分类 + 备注 全同才算重复 |
| D2 | 删除账本时其中数据 | **一并删除**，且必须输入账本名确认 |
| D3 | 合并后源账本 | **直接删除** |
| D4 | 默认账本归属 | 注册自动创建，可改名可删，但**系统保证至少保留一个账本** |

## 2. 数据模型调整

### 2.1 新增表 `accounts`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint unsigned PK | |
| `user_id` | bigint unsigned | 外键 → `users.id`，`ON DELETE CASCADE` |
| `name` | varchar(64) | 账本名，**同一用户名下唯一**（`uk_user_account_name`） |
| `icon` | varchar(64) | 图标标识，默认 `''` |
| `sort` | int | 排序值，默认 0 |
| `is_default` | tinyint | 是否默认账本（每用户有且仅有一个，应用层保证） |
| `created_at` | datetime(6) | |

索引：`uk_user_account_name (user_id, name)` 唯一、`idx_user_default (user_id, is_default)`。

### 2.2 `transactions` 表调整

| 变更 | 内容 |
|---|---|
| 新增列 | `account_id` bigint unsigned **NOT NULL** |
| 新外键 | `FK_transactions_account` → `accounts.id`，**`ON DELETE CASCADE`** |
| 新索引 | `idx_user_account_date (user_id, account_id, record_date)` |
| 未变 | `user_id`、`category_id` 及其索引全部保留 |

> `ON DELETE CASCADE` 是"删除账本 = 连带删除其数据"这条语义的数据库层落地，
> 即使应用层漏写了清理逻辑，也不会留下孤儿交易。

### 2.3 分类为什么不做账本隔离

`categories` 仍是**用户级共享**，不挂账本。理由：分类反映的是个人记账习惯
（餐饮、交通这类），跨账本复用才是正常诉求；与随手记等主流产品的做法一致。
副作用：删除账本不会影响分类。

## 3. 合并规则（重点）

### 3.1 重复交易的判定

**指纹**由五个字段拼接而成：

```
金额 | 记账日期 | 收支类型 | 分类ID | 备注
```

只有五个字段**全部相同**才判定为同一笔（严格全字段匹配，决策 D1）。

- 判定为重复 → **丢弃源账本那条，保留目标账本那条**
- 只要有一个字段不同 → 视为**两笔不同的交易，全部保留**

### 3.2 金额/日期"冲突"如何处理

**不存在冲突取舍问题。** 这是严格口径带来的直接结果：

| 场景 | 处理 |
|---|---|
| 金额、日期相同，但备注不同 | 不是重复 → **两笔都保留** |
| 金额相同、日期不同 | 不是重复 → **两笔都保留** |
| 分类不同（其余相同） | 不是重复 → **两笔都保留** |
| 五个字段全同 | 是重复 → 保留目标，丢弃源 |

之所以不需要"以谁为准"的规则，是因为任何差异都已经被判定为不同交易。
这比"金额日期相同就以目标为准"要保守得多——**同一天两次 38.5 元的午饭，不会被误合并成一笔**。

### 3.3 源账本内部自带的重复

**不处理。** 合并只解决"两个账本之间"的重复，不擅自整理单个账本内部的数据。
即源账本里本来就有两条完全相同的记录时，合并后会原样保留两条。

> 这是有意的边界：如果顺手去重，用户可能会发现"我明明记了两笔，合并后少了一笔"。

### 3.4 合并的执行过程

```
1. 校验 targetId / sourceId 都属于当前用户，且两者不相等（否则 40003）
2. 开启事务
   a. 读出目标账本全部交易，构造指纹集合
   b. 遍历源账本交易：
      · 指纹命中 → 删除该条源记录（计入 willSkip）
      · 未命中   → 把 account_id 改为目标账本（计入 willMove）
   c. 删除源账本
3. 提交事务，返回报告
```

**全过程在单个事务内**，任何一步失败整体回滚，不会出现"数据迁了一半"的中间态。

### 3.5 合并前必须预检

`POST /api/accounts/merge-preview` 不修改任何数据，只返回：

```json
{
  "sourceTotal": 4,   // 源账本共有多少笔
  "willMove": 3,      // 会迁入目标多少笔
  "willSkip": 1       // 因完全重复会丢弃多少笔
}
```

前端把这份报告展示在确认弹窗里，用户点了"确认合并"才真正执行。
**合并是不可逆的，必须让用户在动手前看到确切影响。**

## 4. 删除规则与防误删（重点）

### 4.1 数据怎么处理

**连同账本下全部交易一起删除**（决策 D2），由 `ON DELETE CASCADE` 保证。

### 4.2 三道防线

| # | 校验 | 失败码 |
|---|---|---|
| 1 | **必须输入与账本名完全一致的 `confirmName`** | `40001` |
| 2 | **不允许删除最后一个账本** | `40002` |
| 3 | 删除前先调 `delete-preview` 拿到交易笔数，在弹窗中明示 | — |

第 1 道是核心：输入名称比"再点一次确认"有效得多——用户必须**看着账本名手打一遍**，
误删的概率被大幅压低。名称不一致时后端直接拒绝，并提示正确的账本名。

第 2 道保证"每个用户至少有一个账本"这一不变量，
否则用户会陷入"没有账本可记账"的死局。

### 4.3 默认账本的继承

删除的若是默认账本，**默认标记自动转给剩余账本中的第一个**（按 `sort`、`id` 升序）。
保证"必定存在一个默认账本"从注册那刻起始终成立。

## 5. 平滑迁移方案（重点）

迁移脚本：`src/migration/1789137009697-MultiAccount.ts`

### 5.1 五步迁移（顺序不可变）

```
1. 建 accounts 表（含唯一索引与外键）
2. transactions 增加 account_id 列 —— 先设为【可空】，避免存量数据插入失败
3. 为每个既有用户 INSERT 一条「默认账本」，is_default = 1
4. UPDATE transactions SET account_id = 该用户默认账本
5. 校验 account_id IS NULL 的行数为 0 后，
   收紧为 NOT NULL 并加外键
```

### 5.2 为什么这样设计

**第 2 步先可空、第 5 步再收紧**：如果一上来就加 NOT NULL 列，
存量 19 行交易会因为取不到值而迁移失败。先加可空列、灌好数据、校验无遗漏，
再收紧约束，整个过程对存量数据零风险。

**第 5 步带断言**：迁移里显式 `SELECT COUNT(*) WHERE account_id IS NULL`，
只要还有漏网的记录就直接抛错中止迁移，而不是带着脏数据继续往下走。

### 5.3 实测迁移结果

| 校验项 | 迁移前 | 迁移后 |
|---|---|---|
| users | 16 | 16 |
| transactions | 19 | 19 |
| accounts | — | **16**（每用户 1 个） |
| is_default = 1 的账本 | — | **16**（每用户恰好 1 个） |
| **account_id 为 NULL 的交易** | — | **0** ✅ |

### 5.4 向后兼容（不影响现有功能的具体表现）

这是"平滑"的核心，做了两件事：

1. **老接口不传 `accountId` 时自动落到默认账本**
   `TransactionService.resolveAccount()` 在拿不到 accountId 时回退到默认账本。
   实测：改造前的请求体 `{type, amount, recordDate, note}` 依然能记账，
   新增的交易自动带上默认账本的 `accountId`。

2. **列表/统计不传 `accountId` 时统计全部账本**
   `GET /transactions`、`GET /statistics/monthly` 等在不传账本参数时行为与改造前一致，
   老前端无需任何改动。

回归测试 31 个既有用例在改造后**全部通过**，即是对这一点的直接验证。

### 5.5 回滚方式

`npm run migration:revert` 可完整回滚：删外键与索引、删 `account_id` 列、删 `accounts` 表。
注意回滚会**丢失账本划分信息**（所有交易重新变成扁平结构），已合并的数据无法还原。

## 6. 当前账本的切换方式

| 项 | 方案 |
|---|---|
| 存储位置 | **前端本地存储** `currentAccountId`（`uni.setStorageSync`） |
| 为什么不上后端 | 切换是纯客户端偏好，后端不必知道用户"正在看哪个账本"；少一个字段少一次同步 |
| 代价 | 多端不同步。换设备登录会回落到默认账本。本项目以 H5 单端为主，可接受 |
| 悬空保护 | 每次进页面 `accountStore.load()` 会校验：本地记录的账本若已不存在（被删/被合并走），**自动回落到默认账本** |
| 生效范围 | 首页概览、明细列表、统计汇总与占比，全部随当前账本联动 |
| 交互入口 | 首页顶部账本胶囊 → 系统 ActionSheet 选择；「我的 - 账本管理」可做增删改合并 |

## 10. 已知取舍与限制

1. **合并不可逆**：源账本删除后无法恢复。缓解手段是强制预检 + 确认弹窗。
2. **当前账本存前端**：多端不同步，换设备回落到默认账本。若将来要多端一致，
   可在 `users` 表加 `current_account_id` 字段。
3. **源账本内部重复不去重**：见 §3.3，有意为之，避免"顺手删数据"。
4. **分类不分账本**：见 §2.3。若将来要按账本隔离分类，需要给 `categories` 也加 `account_id`。
5. **明细页"全部账本"视图未提供**：当前只按选中账本展示。
   后端的列表接口已支持不传 `accountId` 查全部，前端加一个"全部"选项即可，属 P2。
6. **删除账本无回收站**：删除即物理删除（含交易）。若要软删除，需引入 `deleted_at` 并改所有查询。
