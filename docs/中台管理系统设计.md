# 中台管理系统设计（v1.0）

> 2026-09-20 定稿。luchao 已确认三个关键决策：注册改申请制、删除=物理级联、驳回=直接删除记录。

## 1. 目标

PC 端管理后台（中台），功能：**审批用户注册申请、驳回、停用/启用用户、删除用户**。
不含：数据看板、全局流水管理、管理员管理页（后期演进，接口路径已预留）。

## 2. 架构

| 层 | 方案 |
|---|---|
| 前端 | 新增 frontend-admin/（Vben Admin v5，MIT），与 frontend/ 平级 |
| 后端 | 共用现有 Midway 进程，新增 /api/admin/* 路由组 + AdminGuard |
| 数据库 | 同一 MariaDB，新增 admins 表，users 加 status 列 |
| 部署 | NAS 共部署；dev 期 Vite 代理，生产期 CORS_ORIGINS 追加中台域名 |

## 3. 账号体系（两套完全隔离）

| | App 端 | 中台 |
|---|---|---|
| 账号表 | users | admins（新表） |
| 登录接口 | POST /api/auth/login（不动） | POST /api/admin/auth/login |
| token payload | { userId, username }（存量无 scope，按 user 处理） | { adminId, username, scope: 'admin' } |

```sql
CREATE TABLE admins (
  id            BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  username      VARCHAR(64) UNIQUE NOT NULL,
  password_hash VARCHAR(255) NOT NULL,
  nickname      VARCHAR(64) NULL,
  status        ENUM('active','disabled') NOT NULL DEFAULT 'active',
  last_login_at DATETIME NULL,
  created_at    DATETIME
);

ALTER TABLE users ADD COLUMN status ENUM('pending','active','disabled') NOT NULL DEFAULT 'pending';
UPDATE users SET status = 'active'; -- 迁移收尾：存量用户一次性放行
```

status 列默认 pending（默认收口：宁可新用户卡待审，不能漏放），存量靠 UPDATE 放行。

## 4. 守卫体系（默认保护、显式放行）

中间件注册顺序（src/configuration.ts onReady）：
`useMiddleware([JwtGuardMiddleware, AdminGuardMiddleware, ResponseMiddleware])`

**JwtGuard（改造）**：
- match 范围收窄：/api 路径，排除 /api/auth/login、/api/auth/register、**整个 /api/admin/**（admin 路由全权交给 AdminGuard，避免双重校验）
- 验签后增加 scope 检查：payload.scope === 'admin' 的 token 拒绝（管理员凭证不能调 App 用户接口）；无 scope 的存量 token 视为 user
- 增加状态校验：验签后按 userId 查 users.status，disabled → 40103；停用即时生效，砍掉已签发 token 的 7 天存活期

**AdminGuard（新增）**：
- match：/api/admin/ 前缀，排除 /api/admin/auth/login（管理员登录本身不要求 token）
- 验签（同一 JWT secret）后要求 scope === 'admin' 且 adminId 存在
- 再查 admins 表：status !== 'active' → 拒绝（管理员停用即时生效）
- 通过后挂 ctx.admin = { adminId, username }

## 5. 用户状态机

```
注册 ──> pending ──approve──> active ⇄ disable/enable ⇄ disabled
              └──reject──> 物理删除（pending 用户只有空账本+预设分类）
active/disabled ──delete──> 物理级联删除（外键 CASCADE：账本/分类/流水全删）
```

硬规则：驳回/删除/停用动作的目标是**用户**，与操作的管理员不同体系，不存在"误删自己"问题；
但 AdminGuard 保护下管理员自身停用走 admin:manage 演进阶段处理，v1 不提供接口。

## 6. 接口契约（/api/admin/*，除 auth/login 外全部 AdminGuard 保护）

| 方法 | 路径 | 说明 | 响应 data |
|---|---|---|---|
| POST | /api/admin/auth/login | 管理员登录 | { token, adminId, username, nickname } |
| GET | /api/admin/users | 列表 ?page&pageSize&keyword&status | { items, total, page, pageSize } |
| GET | /api/admin/users/:id | 详情（含账本数/流水数） | UserAdminItem |
| POST | /api/admin/users/:id/approve | pending→active | UserAdminItem |
| POST | /api/admin/users/:id/reject | pending→物理删除 | { success: true } |
| POST | /api/admin/users/:id/disable | active→disabled | UserAdminItem |
| POST | /api/admin/users/:id/enable | disabled→active | UserAdminItem |
| DELETE | /api/admin/users/:id | 物理级联删除 | { success: true } |

UserAdminItem = { id, username, status, createdAt, accountCount, transactionCount }
（列表计数聚合一次带出）

## 7. 错误码新增（沿用分段约定）

```
40102 USER_PENDING        登录时：账号审核中
40103 USER_DISABLED       登录时：账号已被停用
40014 USER_NOT_PENDING    approve/reject 仅对 pending 生效
40404 USER_NOT_FOUND      管理接口目标用户不存在
40301 ADMIN_LOGIN_FAILED  管理员登录失败（不暴露账号是否存在）
40302 ADMIN_DISABLED      管理员已被停用
```

## 8. 注册/登录行为变更（App 端联动）

- POST /api/auth/register：不再返回 token，返回 { status: 'pending' }；用户建为 pending（默认账本+89 预设分类照常创建）
- POST /api/auth/login：pending → 40102（提示"审核中"），disabled → 40103
- App 前端两处改动：注册成功文案改"申请已提交，等待管理员审核"；登录错误处理加两个新码
- seed：demo 用户显式 status: 'active'，否则 seed 完直接卡待审

## 9. 管理员初始化

`npm run admin:create -- <username>`（幂等，交互输密码或 ADMIN_PASSWORD 环境变量）。
后续加管理员 v1 同样走脚本；中台"管理员管理页"为后期演进。

## 10. 删除语义（已确认）

物理级联删除，不保留痕迹。中台删除弹窗展示"将连带删除 N 个账本、M 笔流水"（详情接口数据）。
驳回同样物理删除，同用户名可重新注册。

## 11. 实施阶段（每阶段独立提交 + 全量门禁）

1. **后端**：迁移（admins 表 + users.status）→ JwtGuard 改造 → AdminGuard → 管理接口 + 单测
2. **注册/登录变更**：后端 + App 前端联动（146 单测基线中注册相关用例逐条改）
3. **中台骨架**：Vben 起项目、登录打通、用户管理页
4. **部署**：NAS + CORS_ORIGINS + admin:create 跑一次
