## 1. 执行顺序与依赖（不是简单的优先级排序）

```
4.1 ──┬──> 1.2          （预热会新增一个 load() 发起方，守卫先到位再叠加请求源）
      ├──> 4.3 ─┐
      └──> 4.4 ─┴─> （合并成一次实现：都改 utils/request.ts）
1.3 ──> 5.1             （同改 vite.config.ts，合并成一次构建验证）
2.1 · 2.2 · 5.2         （互相独立，也无外部依赖）
3.2 测量 ──> 任何 store getter 改动之前
```

**关键依赖，逐条说明理由：**

| 依赖 | 理由（不是形式上的顺序） |
|---|---|
| **4.1 → 1.2** | 1.2 会在 `setSession()` 里 fire-and-forget 发 `/accounts`，**与页面自己的 `load()` 天然并发**。守卫没到位就加这个请求源，等于给一个已知有竞态的地方再叠一层竞态。 |
| **4.1 → 4.4** | 4.4 的重试会**重新发起请求**，必须计入 4.1 的守卫：否则"重试回来的旧结果"照样会盖掉新状态。守卫是语义基础，重试只是优化。（原条目还含 4.3 —— 它已**降级不做**，见 §4.3 那节。）|
| ~~**4.3 与 4.4 合并实现**~~ | 原计划如此（都改 `utils/request.ts`）。**4.3 降级后，本轮只动 4.4 一处**；但"共享封装每动一次都是一次全站风险"这条判断仍然成立 —— 所以 4.4 的验证做到了端到端（含 5 个真实失败场景 + 1 条基线对照）。|
| **1.3 → 5.1** | 都要改 `vite.config.ts`，合并成**一次构建**验证（一次 `build:h5` 是分钟级）。1.3 只是往 `index.html` 注入 `<link>`（不改产物文件内容），5.1 会**删产物文件** —— 先加后删，出问题时容易二分定位。 |
| **3.2 → store 改动** | "先测再定"。反过来写就是"没测就改"。 |

## 2. 各批次：目标 + 退出条件

### 批次 1 · 4.1 页面级请求竞态（P0，**正确性问题**）

> ⚠️ **执行时的更正（2026-10-02）**：建议文档 §4.1 只点了 **3 处**调用点
> （`flow.loadGroups` / `flow.loadSearchResults` / `ReportView.loadData`），
> 但按"同一概念所有出现位置全局搜一遍"的原则做完整枚举后，**实际是 6 处**。
> 只修 3 处就是典型的"改一半" —— 剩下 3 处同样是"旧结果盖新结果"，且其中两处更严重：
>
> | 补上的第 N 处 | 触发源 | 后果 |
> |---|---|---|
> | `pages/charts/index.vue` `loadData` | 切粒度 / 切方向 / 切层级 / 翻时段 | 图例与数据对不上，且 `resetRotation()` 会按错数据把转盘转正 |
> | `components/views/HomeView.vue` `loadData` | 下拉刷新 / **切换账本** / 视图激活 | **跨账本串台**：顶部显示「已切到 B」，合计与排行却是 A 账本的钱 |
> | `pages/calendar/index.vue` `loadDetail` | 连续点不同日期 | 格子高亮 A 天、明细列的是 B 天的账（金额都对，只是对的是另一天）|
>
> 枚举范围＝`pages/` + `components/` 下所有"`await` 之后写状态"的加载器。
> **明确考虑过但决定不改**的两类（避免以后重复论证）：
> - `calendar/index.vue` 的 `ensureRange()` —— 它是**合并型**加载（按天 merge 进 `dayAgg`
>   + 用 `loadedMonths` 集合去重），不存在"旧盖新"，最多白发一次请求；
> - `recycle` / `export` / `import` / `account` / `record` / `category` 的加载
>   —— 都是一次性动作或"写后读"，风险属于**重复提交**而不是竞态，是另一件事；
> - `store/account.ts`、`store/category.ts` —— 已有 `reqSeq` / 迟到响应保护，不需要套两层。

**目标**：六处页面级加载在"后发的请求先返回"时，**旧响应不落地**，且**不提前关掉新请求的加载态**。

**做法**
1. 新增 `frontend/src/utils/latest.ts`：`createLatest()` → `{ run, begin, isCurrent, invalidate }`。
   把「只让最新一次落地 + `onSettled` 只在最新时跑」这条规则**收口到一处**。
   为什么不许三个调用点各写一遍：每个调用点都要正确处理 `try / catch / finally` 里的
   `loading` / `skeleton` / `error` 三个标志，写三遍就是**三倍漏掉其中一个的机会**（本项目已有"改外键只测一半"的前科）。
2. 三处调用点改用它；页面 `onUnload` 调 `invalidate()` —— 否则离开页面后，过期的失败响应仍会弹 toast。
3. 新增 `test/latest.test.ts`（走根目录 jest，与 `amount-expr.test.ts` 同一路数）。

**退出条件**
- [ ] `npm run test` 全绿，单测数 = 233 + 新增
- [ ] **负向验证**：把 `run()` 里的过期判断注释掉 → 新用例必须**红**（不跑这一步就等于没有校验器）
- [ ] `cd frontend && npx vue-tsc --noEmit` = 0
- [ ] `node scripts/verify-flow.mjs` 不回归（需起 dev server）
- [ ] `node scripts/verify-report.mjs` 不回归

### 5.4 `npm run test`：这一项**没能给出可信结论**（如实记录）

三次运行的数字**都在抖动，且抖动方向与并发负载一致** —— 所以都不能当"基线"用，
但合起来足以定性：

| 运行 | 并发情况 | 失败套件 | 失败用例 | **通过用例** |
|---|---|---|---|---|
| 1 | 有（另一个 jest 进程 + vue-tsc）| 5 | 77 | 164 |
| 2 | 有（Playwright 探针 + dev server）| 4 | 83 | 158 |
| 3 | 基本无 | **3** | **36** | **205** |

**并发越少，通过数越高（164 → 158 → 205），失败套件集合每次都不同**
（`statistics.service` / `category.service` / `transaction-import.service` 在一轮失败、另一轮全过）。
⇒ 这是**负载相关抖动**，不是确定性回归。

**根因已确认（不是猜测）**——失败不是断言不通过，而是：

```
MidwayCodeInvokeTimeoutError: Function "configuration.onReady" of "typeorm" call more than 30000ms
```

即 **TypeORM 的数据库连接在 30 秒的钩子超时内没建立起来**。一个套件启动失败 → 它下面所有用例全红，
这正是"36 / 77 / 83 条"这个量级的来源。

**为什么可以确定不是本次改动引入的**（这条比上面的数字更硬）：
- `git status` 显示本轮**只改了 8 个前端文件 + 新增 4 个文件**，**没有任何后端文件**；

### 4.4 的落点：两条路都没走，走了第三条（2026-10-03）

原计划把落点二选一：**A. 包一层薄模块**（要动 5 个 api 文件的导入）／
**B. 在实例上包 `request()`**（猴补丁第三方库）。实际调研后发现**两条都不必**：

**关键事实一：全站调用形状收敛在 4 个方法上。**
`grep -oE 'http\.[a-zA-Z]+'` 的统计是 `get`(12) / `post`(14) / `put`(3) / `delete`(4)，
共 33 个调用点、**全部在 5 个 api 文件里**，没有任何 `http.request(...)` 直调。
⇒ "薄封装"根本不需要改 api 文件的导入 —— 直接改 `utils/request.ts` 内部的接线即可，
**零调用点改动**。

**关键事实二：`mergeConfig()` 只保留白名单字段。**
`luch-request` 的 `src/lib/core/mergeConfig.js` 里：

```js
let config = {
  baseURL, method, url, params,
  custom: { ...(globalsConfig.custom || {}), ...(config2.custom || {}) },
  header: deepMerge(...)
}
```

**任何自定义字段都会被丢掉** —— `custom` 是唯一的自由通道，也是官方给出的扩展位。
⇒ 重试计数走 `config.custom.__attempt`，**不是猴补丁**、也不依赖库内部实现。

**最终落点**：在 `utils/request.ts` 的**响应拦截器失败分支内部**接线，
判据抽到 `utils/retry.ts`（纯函数，29 条单测）。
- 相对 A：**零调用点改动**（33 个点一个没动）；
- 相对 B：不覆盖实例方法，走库的公开契约（`custom` + 拦截器），升级安全。

⚠️ **为什么必须写在拦截器内部、而不是包在外层**：`luch-request` 把请求链串成
`promise.then(fulfilled, rejected)`，失败分支是整条链的最后一环。若包在外层，
下面那段"弹 toast / 401 跳登录"会在**每一次失败**都执行 —— 重试 3 次就弹 3 次 toast、
跳 3 次登录页。写在内部并**提前 `return http.request(config)`**，
才能保证只有"最终失败"才走到提示逻辑。（`verify-retry.mjs` 里有一条结构判据钉着它。）

### 4.4 判据的实测依据（不是照着源码猜的）

三条判据都在 `scripts/verify-retry.mjs` 里被**真实失败**验证过。脚本用 Playwright
拦截请求，实测到**三种不同的失败形状**：

| 场景 | 制造方式 | 实测 `statusCode` | 实测 `errMsg` | 判据 | 实测请求次数 |
|---|---|---|---|---|---|
| 断网 / 连接被拒 | `route.abort('failed')` | `undefined` | `request:fail` | **重试** | **2 次（成功救回）** |
| HTTP 500 | `route.fulfill({status:500})` | `500` | **`request:ok`** | 不重试 | 1 次 |
| 超时 | 请求挂起，等 XHR 自身 10s 超时 | `undefined` | `request:fail timeout` | 不重试 | 1 次 |
| POST 断网 | 拦 `/auth/login` 后 abort | `undefined` | `request:fail` | 不重试 | 1 次 |

⭐ 注意 500 那行的 `errMsg` 是 **`request:ok`** —— HTTP 500 在 XHR 层面算"收到了响应"，
uni 的 `invokeSuccess` 给它打了 `request:ok`，是 `luch-request` 的 `settle()`
再按 `statusCode` 判失败的。这恰好说明判据里
**"必须有 `statusCode`"与"`errMsg` 必须以 `request:fail` 开头"这两道是真正的冗余防线**
—— 实测中拆掉任意一条，另一条仍能拦住 500（拆掉第一条后场景 C 依然绿，就是证据）。

**为什么超时不重试**（与原计划写的"仅网络错误/超时"**有出入，是刻意收窄的**）：
本项目 `timeout` 是 10s，超时意味着用户**已经干等了 10 秒**，再重试 2 次就是 30 秒才给反馈
—— 那比直接报错更糟。重试预算留给**瞬时失败**（断网、连接被拒、连接重置）：
这类失败几乎立即返回，重试的额外等待只有几百毫秒退避，却能把一次"网络异常"变成一次成功。
⇒ **先实测出"超时与断网的 errMsg 确实不同"，才据此收窄的。**

**为什么写接口一律不重试**（也与原计划不同——原计划写"POST 新增流水可以，因为有 `clientId` 幂等键"）：
`clientId` 只存在于 `createTransaction`，**不是所有写接口都有**。与其逐个甄别
"这个 POST 有没有幂等键"，不如一律不重试 —— 范围收窄优先，而且误重试写接口的代价
（重复提交）远高于少救回一次请求。

### 4.3 为什么降级为"不做"

这是**基于新信息的重新评估**，不是遗漏：

- 4.3 的原始卖点是"新页面自动受益，不用手写 `inflight`"。但 4.1 落地后，
  重复请求的主要来源已经被**更便宜的机制**覆盖：页面级竞态守卫（`utils/latest.ts`）、
  store 侧 in-flight 合并、登录后预热（`setSession` 里 fire-and-forget 拉 `/accounts`）。
- 再铺一层"全局按 key 合并 GET"，收益需要**重新证明**（目前没有实测证据说明还剩下多少重复请求），
  而代价是明确的：动的是**所有人共用的请求契约**，还要额外维护 `force` 逃生口
  —— 而本项目已经踩过"`force` 传了却没生效"的坑（见 §一 实现约定）。
- ⇒ **决定不做**。若后续实测发现仍有可观的重复请求，再按当时的证据重新评估。

### 3.2 / 4.5 收口：不做的量化依据（luchao 2026-10-03 拍板）

两项**都不做**，但理由不同，记下来是为了避免将来重新讨论一遍：

**3.2（`byId` / `fullNameOf` 的 O(n) getter）—— 收益概率太低。**

把量级算出来就明白了：89 条分类 × 每行 1~2 次查 × 100 行 ≈ **1.8 万次 `Array.find`**，
在 JS 里大约 **不到 1ms** —— 正常就在一帧（16.7ms）的噪声里。
计划里本来就只安排"测量"、不安排修复；而既然**最可能的结论是"不需要改"**，
再花一轮去证明它也谈不上划算。**这不是"不敢测"，是量级判断。**

**4.5（brotli）—— 自托管场景下收益量级不划算。**

brotli 本身是有效的（JS/CSS 相对 gzip 再降 15~20%，入口 103.2 KB → 约 82~88 KB），
问题出在**换算成用户实际等待**之后：

| 网络 | 省 20 KB ≈ 省下 |
|---|---|
| 内网（100 Mbps）| **约 1.6 ms —— 无感** |
| 4G（约 3 Mbps）| 约 53 ms |
| 弱网（500 kbps）| 约 320 ms |

本项目是**自托管**（`deploy/` 里没有 CDN 配置，但有 `docker-compose.nas.yml`），
主要走内网访问 ⇒ 收益落在"无感"那一档。而代价是**换带 brotli 模块的 nginx 镜像**
（官方 `nginx:alpine` 没编译该模块，写 `brotli on` 会直接启动失败）+ 改 `precompress.mjs`
产出 `.br` + 验回落路径（`.br` 优先 → `.gz` 兜底）+ 重跑整套部署验证。
**改坏了是线上事故。**

⚠️ 还有一个**方向相反**的账：开 brotli 会让产物**多一份 `.br`**（与 `.gz` 并存），
部署目录与镜像层都会变大 —— 这与刚做完的 5.1（删掉 730 KB）方向相反，要一起算净账。

> 若将来挂了公网域名 / CDN，这两条的结论都要**重新评估**：公网弱网下 brotli 的 320 ms
> 是可感知的；但**如果走 CDN，很多 CDN 自己就会做 brotli** —— 那种情况下改源站 nginx
> 反而是白做。**先确认链路，再决定改哪一层。**

|---|---|---|---|

**为什么一直没被发现**：`[6]` 段长期因为"当月无数据"整段红，

这正是"红得太多 = 没有红"的实例。

**成因**（算出来的，不是猜的）：

```
LABEL_GAP = outerR + 8，而 outerR = size/2      ⇒ size 130 → gap = 73 ✓ 与实测一致
名称可用  = 容器半宽 − LABEL_GAP − 百分比宽 − 3
          = 311/2 − 73 − 45 − 3 ≈ 35px         ✓ 与实测一致
```

差额在**容器宽度**：`.panel` 是 `margin: 16px` + `padding: 16px`
⇒ 环图容器 = 375 − 2×16 − 2×16 = **311**。
而 `RingChart.vue` 注释里那笔账用的是「面板宽 **343**、半宽 171.5 → 名称约 50px」——
343 是**面板外宽**，少算了内边距那 32px。
⇒ **断言目标 46px 是按 343 标定的，实际容器只有 311。**

> ⚠️ 本文件初版把成因写成"百分比文字从 33px 变宽到 45px"，**是错的**（注释里那笔账本来就用 45）。
> 已更正。这个例子说明：**"看起来像的变量"和"真正变化的变量"经常不是同一个**，
> 必须把公式写出来代进去算，而不是凭差值猜。

`.ring-label-name` 有 `text-overflow: ellipsis`，注释明确写着「名称可压缩、百分比不可压缩」
—— 所以**截断是刻意的取舍**，问题只在于"留给名称的空间掉到了目标之下"。

⚠️ **「放大环」是反向的**（已用公式验证）：`LABEL_GAP = size/2 + 8`，

### 5.2.3 ⚠️ 该改动**带出一个我没预见到的副作用**（诚实记录）

面板变宽使趋势图的 canvas 由 **311 → 335**，而趋势图那条

- 2px 是**恒定基准差**（组件用 `area[3]`、uCharts 画在 +2px），**不是每格漂移** ——

  放宽到 3px 是把**代理指标校准到意图**。
- **≤3px 仍是有意义的门**：真正的错位（chip 用了过期的 width）会 >5px；

- ⛔ 断言旁已写明：**不要为了"看起来更严"改回 2px** ——
  那会让它在任何取整波动下随机变红，而**会假红的校验器会训练人忽略红色**。
