## 0. TL;DR

**扁平化不是"把阴影删掉"，那是化妆。** 真正的取舍是三条结构性决策：

1. **大面积中性 + 小面积强调** —— 品牌橙的用量从约 15% 压到约 5%。
   现状是"彩色 banner + 彩色图标底 + 彩色按钮"三处大面积上色，扁平体系里这是噪音。
2. **用分隔线分层，而不是用卡片** —— 页面底从灰改成白，取消"每块都浮在灰底上"的碎片感。
   这一步不只是审美：实测发现浅灰底会让 `ink-3`、收入红、输入框边界**同时失效**（见 §4.3）。
3. **零阴影，唯一例外是模态** —— 模态必须表达"我在你之上"；其余所有层级由底色与分隔线承担。

配套的三条具体动作：**渐变换纯色**、**凸起 FAB 换为 Tab 栏内等高主按钮**、**emoji 全部换成几何图标**。

## 1. 设计对象与边界

**在范围内**：8 个页面的视觉语言、图标系统、配色与版式 token、组件状态定义、响应式策略、落地路径。

**不在范围内**：信息架构与导航结构的增删（保持现有 4 Tab + 4 流程页）、后端与接口、
具体业务逻辑与文案（沿用现有文案，只改呈现）。

**一条自我约束**：本方案提出的所有色值都必须满足已建立的无障碍基线。
如果某个"更好看"的配色做不到这一点，它就不进方案 —— **美观不能以牺牲可读性换取**。

## 2. 目标用户与核心使用场景

### 2.1 三类用户

| 用户 | 特征 | 对设计的要求 |
|---|---|---|
| **随手记型（主力，约 70%）** | 每天 1–3 笔，多在消费当下掏手机记。单手操作、可能在地铁或饭桌上 | 记账路径要短；主操作必须在拇指热区；金额输入不能有"先点输入框"这种前置步骤 |
| **月末复盘型（约 25%）** | 每周或每月看一次统计，关心"钱花在哪了" | 数字优先、可扫读；分类占比要能一眼分辨；不要让他滚动才能看到总额 |
| **对账型（约 5%）** | 需要找回某一笔、改分类、核对金额 | 明细页要能快速筛选与定位；金额必须等宽对齐（否则小数点错位、竖着对不上） |

> **共同点：三类用户都在"看数字"。** 这是本方案把"数字优先"放在第一条的原因 ——
> 记账 App 的第一功能不是"记账"，是"看清钱去哪了"。

### 2.2 核心场景

| 场景 | 用户目标 | 设计含义 |
|---|---|---|
| S1 消费当下快速记账 | 15 秒内记完一笔 | 金额键盘常驻；分类一行入口；默认带出今天此刻 |
| S2 打开 App 看本月花了多少 | 3 秒内得到答案 | 首屏即大数字，无需滚动；区间（今天/本周/本月/本年）一屏可见 |
| S3 复盘某月支出结构 | 知道前几大类是谁 | 环形图 + Top6 图例（名称/金额/占比三通道）；占比与金额都要给出 |
| S4 找回并修改某笔 | 定位到那一笔 | 吸顶筛选（月份 + 收支）；按日分组 + 日期粘性头；行高 56px 便于点击 |
| S5 管理账本与分类 | 新建 / 改名 / 换图标 | 设置类通栏列表 + 右侧 chevron；危险操作单独用浅红底区分 |
| S6 在大字号下使用 | 仍能读全所有数字 | 字号用 px 固定、只随系统设置缩放；金额折行而非截断（见 §9） |

### 2.3 由场景推导的四条硬约束

1. **数字可扫读**：金额一律 `tabular-nums` + 右对齐 + 定宽列。三位用户里有两位在这个场景里"竖着扫"。
2. **拇指可达**：主操作（记一笔）在底部中央；所有可点元素 ≥44px。
3. **一屏见结论**：首屏必须包含"本月支出"这个结论，不能被 banner 装饰挤到折叠线以下。
4. **大字号不崩**：不能用"好看的固定宽度"换布局稳定性 —— 这条有实测账单（§9）。

## 3. 视觉风格：扁平化的边界

### 3.1 三条结构性取舍

**① 大面积中性 + 小面积强调**

| | 现状 | 新方案 |
|---|---|---|
| 上色面积 | 彩色渐变 banner（整块）+ 区间图标底 + 排行进度条 + Tab 选中 | 主按钮 + Tab 选中 + 分类选中态 + 进度条 |
| 约莫占比 | ~15% 屏幕面积 | ~5% |
| 效果 | 颜色在抢注意力，数字反而被淹没 | 颜色只在"这里可以点""这是当前项"时出现 |

**② 用分隔线分层，而不是用卡片**

页面底 `#FFFFFF`（原 `#F5F6F8`），分区之间用 `#E6E9EF` 发丝线，`#F5F6F8` 降级为"次级分区底"（日期头、输入槽）。

- 收益一（审美）：消掉"每块都浮在灰底上"的碎片感，页面是连通的整体。
- 收益二（可读性，**这条是实测出来的**）：浅灰底会让 `ink-3` 从 4.51 掉到 4.17、收入红从 4.83 掉到 4.47、
  输入框边界从 3.06 掉到 2.83 —— 三处同时跌破阈值。改白底把它们一次性救回来（§4.3）。

**③ 零阴影，唯一例外是模态**

- 卡片、按钮、Tab、键盘、Toast 一律**无阴影**。层级由「底色深浅 + 分隔线 + 留白」表达。
- **唯一例外**：模态弹窗 + 遮罩。它必须在视觉上"浮起来"，否则用户不确定自己是不是还站在原地。
  这是有语义的例外，不是偷懒。
- 顺带：按钮的层级也**不靠阴影**，靠底色饱和度分四级（实心 → 浅底 → 描边 → 文字）。

### 3.2 能扁平 / 不能扁平的清单

| 能扁平（本方案已做） | 不能扁平（做了会出事） |
|---|---|
| 卡片阴影 → 分隔线 | **输入框边界**：必须留 ≥3:1 的可见边界（1.4.11）。"扁平"不是"去掉框" |
| 渐变 → 纯色 | **焦点环**：必须有。用 `outline` 而非 `box-shadow`（不被 `overflow:hidden` 裁掉） |
| 凸起 FAB → 等高主按钮 | **收支红绿 + 正负号**：颜色不能是唯一区分手段（1.4.1），符号必须同步 |
| emoji → 单色几何图标 | **触控目标**：不能为了"干净"把可点区域做小 |
| 深阴影 → 细边框 | **模态的浮起语义**：需要一层阴影或遮罩 |

### 3.3 与现行设计的差异表

| 元素 | 现状 | FL-1 | 理由 |
|---|---|---|---|
| 页面底 | `#F5F6F8` 灰 | `#FFFFFF` 白 | 救回三处对比度；去碎片感 |
| 分区手段 | 白卡 + 12/16px 圆角 + 12px 间距 | 通栏 + 1px 发丝线 | 更连续、信息密度更高 |
| 首页顶部 | 彩色渐变 banner + 白字 | 白底 + 36px 深墨数字 | 数字 15.78:1（原 4.52:1）；去大面积上色 |
| 分隔线 | `#EDEFF3`（压浅底 ΔL 0.015） | `#E6E9EF`（压白底 ΔL 0.187） | 现状那条线在浅底上等于看不见 |
| 分类图标 | emoji（🏠🍜🚗…） | 几何图标 + 色块底 | 见 §5 |
| 记一笔入口 | 底部中央凸起 FAB | Tab 栏内等高实心按钮 | 现状 FAB 会遮挡列表内容（阶段 9 截图实证） |
| 金额 | tabular-nums + 右对齐 | 同左（保留） | 已经做对了，不动 |
| 圆角 | 12 / 16 / 24 | 6 / 10 / 14 / 999 | 收紧，去掉"软塌塌"的观感 |
| 间距 | 12 / 14 / 16 / 20 混用 | 8px 栅格（4 为半格） | 现状无栅格，靠手感 |

## 4. 配色思路

### 4.1 用色策略：一色一义

**颜色只承担语义，不承担装饰。** 具体到本 App，颜色只有四种用途：

1. **识别动作**（品牌橙）：可以点 / 当前项
2. **区分收支**（红 / 绿）：且**必须**同时带 `+/−` 符号
3. **表达状态**（信息蓝 / 警告琥珀 / 危险红）
4. **区分类别**（图表 7 色）：只在图表里用，不扩散到 UI

**明确不做的事**：不为 15 个分类各配一色。那是视觉噪音，还会与"收支红绿""图表序列"抢语义 ——
用户会分不清"这个绿是收入还是这个分类的颜色"。分类的视觉标识交给**图标形状**（§5）。

### 4.2 表面三层与分隔线（实测）

| token | 值 | 用途 | 实测 |
|---|---|---|---|
| `bg-canvas` | `#FFFFFF` | 页面底（**新增**） | — |
| `bg-subtle` | `#F5F6F8` | 次级分区底（日期头、分段控件槽） | — |
| `bg-sunken` | `#EEF1F5` | 输入底、进度槽、图标色块底 | — |
| `line` | `#E6E9EF` | 发丝分隔线（**新增**） | 压 canvas ΔL **0.187** / 压 subtle 0.108 |
| `line-strong` | `#D6DAE3` | 需强调的分隔、描边按钮边 | 压 canvas ΔL **0.300** |
| ~~`divider`~~ | ~~`#EDEFF3`~~ | 现状，**建议废弃** | 压 canvas ΔL 0.138、压 sunken **0.015（等于看不见）** |

> 现状那条分隔线压在同为浅灰的分区底上，ΔL 只有 0.015 —— 设计师在显示器上看得出，
> 手机屏幕和大字号下就没了。换成 `#E6E9EF` 后压白底 ΔL 0.187，是"能看见的线"。

### 4.3 文字 / 语义色 × 表面矩阵（实测 · 这是前置约束而非事后核对）

标注：✅ ≥4.5（正文达标）／⚠️ 3.0–4.5（仅大字或辅助，正文不达标）／❌ <3.0

| 前景 | canvas `#FFFFFF` | subtle `#F5F6F8` | sunken `#EEF1F5` | 结论 |
|---|---|---|---|---|
| `ink-1` `#1F2329` | 15.78 ✅ | 14.59 ✅ | 13.93 ✅ | 全表面可用 |
| `ink-2` `#5A6472` | 6.00 ✅ | 5.55 ✅ | 5.30 ✅ | 全表面可用（非白底上的安全下限） |
| `ink-3` `#6E7787` | 4.51 ✅ | 4.17 ⚠️ | 3.98 ⚠️ | **仅白底** |
| `ink-4` `#A8B0BD` | 2.19 ❌ | 2.02 ❌ | 1.93 ❌ | 仅装饰 / 禁用（WCAG 豁免） |
| 支出 `#D92D20` | 4.83 ✅ | 4.47 ❌ | 4.26 ❌ | **金额必须落白底** |
| 收入 `#0B8038` | 5.05 ✅ | 4.67 ✅ | 4.46 ❌ | 避开 sunken |
| 信息 `#1D63B8` | 5.95 ✅ | 5.50 ✅ | 5.25 ✅ | 全表面可用 |
| 警告 `#B45309` | 5.02 ✅ | 4.64 ✅ | 4.43 ⚠️ | 避开 sunken |
| 输入框边界 `#8A94A6` | **3.06 ✅** | 2.83 ❌ | 2.70 ❌ | **输入框必须坐白底**（1.4.11 要求 ≥3:1） |

**这张表直接决定了 §3.1 的第 ② 条决策。** 如果把输入框放在浅灰底上，边界就只有 2.70 —— 不达标；
放在白底上 3.06 —— 刚好达标。所以"页面底改白"不是审美偏好，是被实测逼出来的。

### 4.4 主色与备选主色（实测）

| 方案 | 白字压其 | 其作文字压白底 | 评价 |
|---|---|---|---|
| **`brand-600` `#CF4A12`（推荐，沿用）** | **4.52 ✅** | **4.52 ✅** | 品牌资产；已通过全部对比度实测；换色 = 全部重测 |
| `brand-700` `#C7430F`（橙字 / 焦点环） | 4.95 ✅ | 4.95 ✅ | 需要更"沉"的文字色时用这档 |
| 备选：靛蓝 `#1F4FD8` | 6.63 ✅ | 6.63 ✅ | 更"数字产品"，但丢掉品牌识别 |
| 备选：墨绿 `#0B6B4F` | 6.50 ✅ | 6.50 ✅ | 与"支出绿"撞语义，不推荐 |
| 备选：石墨 `#2B3440` | 12.59 ✅ | 12.59 ✅ | 最克制，但完全没有品牌感 |

**结论：保留品牌橙。** 换主色带来的收益（"看起来更新"）远小于代价（品牌识别丢失 + 全量重测）。
**扁平化真正要改的是"用色面积"，不是"色相"。** 三档职责保持：
装饰留 `brand-500`、实心底 `brand-600`、橙字/焦点环 `brand-700`。

若将来决定换色，上表四个备选都已测过，可一行替换。

### 4.5 图表序列：按「闭环相邻」重排（实测）

**发现一个既有校验的漏洞：环形图是闭环，首段与末段在 12 点方向也是相邻的，
但 `scripts/check-contrast.mjs` 只比对了顺序里相邻的 `i` 与 `i+1`，从未比对 `(n-1, 0)`。**
而统计数据里「其他」永远排在最后，所以这一对是稳定可达的。

实测：该闭环对（中性灰 ↔ 橙红）= **90.15**，恰好达标 —— 所以没出事，**但那是运气，不是设计**。

进一步在「首段固定为品牌橙、末段固定为中性灰（其他专用）」的约束下搜索 5! = 120 种排列：

| | 最小相邻可区分度（阈值 ≥70） |
|---|---|
| 现行顺序 橙红→蓝→品红→翠绿→紫→青→中性灰 | **74.98**（青 ↔ 中性灰） |
| **推荐顺序 橙红→蓝→品红→青→紫→翠绿→中性灰** | **90.15** ✅ |

**改动只是把「青」与「翠绿」换位，最小可区分度提升 15.17。** 七色值本身不变，
因此首页区间图标所用的前 6 色仍全部满足"可承载白字 ≥5.18:1"的不变量。

> 另记录一个**不处理**的已知项：全局两两最差是橙红 ↔ 品红 = 15.62。
> 它们在环形里永远不相邻（中间隔着蓝），所以按"相邻 ≥70"的口径无需处理。
> 但若将来支持"点图例高亮某段"或图例色点密集排列，这一对会暴露 ——
> 因此图例必须保留「名称 + 金额 + 占比」三通道，**颜色不承担唯一区分职责**（WCAG 1.4.1）。

### 4.6 唯一的阴影例外

```css
/* 只此一处允许阴影。模态之外任何元素都不应出现 box-shadow */
.modal { box-shadow: 0 8px 32px rgba(0, 0, 0, 0.18); }
```

品牌色投影（原有的 `$shadow-brand-soft` / `$shadow-brand-glow`）在扁平体系里**建议移除** ——
它们是拟物时代的残留，且会让"彩色小块"显得脏。

## 5. 图标系统（替换全部 emoji）

### 5.1 为什么必须换 —— 四条可验证的理由

1. **跨端画风不一致**：同一个 `🏘️` 在 iOS / Android / Windows / 各家小程序上是四套不同的插画。
   设计稿只在一种设备上成立，等于没设计。
2. **色彩不可控**：emoji 自带颜色、**不受 `color` 影响**，于是无法表达状态 ——
   选中态、禁用态、深色模式下都没法变；图标与文字色不联动，视觉上永远"贴不上去"。
3. **多元素 emoji 在小尺寸糊成一团**：`🏘️`（房屋+树）、`🏖️`（伞+沙滩）、`🧖`（人+蒸汽）
   在 20px 下退化成一堆色点。而分类图标恰恰是高频、小尺寸、需要一眼辨认的场景。
4. **字号与基线不可控 —— 本项目已有实测事故**：
   阶段 9 复验时，首页 banner 的 `📊` 在系统字号 200% 下**随字号一起放大**，
   溢出圆环后被 `overflow:hidden` 悄悄裁掉（见 `移动端配色与字体方案.md` §7.4）。
   **emoji 是"字"，没法只让它当"图"。**

### 5.2 规格

| 项 | 值 |
|---|---|
| 画布 | 24 × 24，内容限制在 2px 内边距内（有效区 20×20） |
| 描边 | 1.75px，`stroke-linecap: round` / `stroke-linejoin: round` |
| 填充 | **不用 fill**（纯线性）；唯一例外是 `h-.01` 靠 round cap 画的小圆点 |
| 颜色 | 一律 `currentColor`，由外层决定 → **状态可切换** |
| 与字号的关系 | **完全解耦**。图标走独立的 8 档尺寸阶梯（`$icon-xs` … `$icon-4xl`），不随 `font-size` 变化 |
| 命名 | 功能图标用「做什么」`icon-plus`；分类图标用「是什么」`cat-food`。两套不混用 |

> 「与字号解耦」这一条正是理由 4 的根治办法：图标不再是"字"，而是一张有自己尺寸阶梯的图。

**73 个二级分类不逐个精绘**，走三级回退（`resolveCategoryIcon`）：

```

② 传入的是 emoji（老数据）          → 查 EMOJI_TO_ICON（88 条字面映射）
③ 都不是                            → 按分类名查 CHILD_ICON / ROOT_CATEGORY_ICON（继承一级图标）

```

**为什么可以只画一级**：二级永远出现在它的一级分组标题下方（记账选择器、分类管理页都是），
**上下文已经提供了分组信息**，图标只需承担"个体差异"。
15 张精绘图 + 一张映射表即可覆盖全部 89 个分类，且**永不出现空图标**。

### 5.4 外框与配色

图标靠**色块底**获得体量感，替代 emoji 的"花哨"：

| 尺寸 | 外框 | 圆角 | 字形 | 用在哪 |
|---|---|---|---|---|
| `sm` | 28×28 | 8 | 16 | 列表行内的次级分类 |
| `md` | 40×40 | 12 | 22 | 明细 / 排行 / 分类网格（主力） |
| `lg` | 48×48 | 14 | 26 | 记账页的一级分类、头像 |

| 状态 | 底 | 字形 | 实测 |
|---|---|---|---|
| 默认 | `bg-sunken #EEF1F5` | `ink-1 #1F2329` | 13.93:1 ✅ |
| 选中 | `brand-600 #CF4A12` | `#FFFFFF` | 4.52:1 ✅ |
| 禁用 | `bg-sunken` | `ink-4 #A8B0BD` | 装饰/禁用，豁免 |

> ⚠️ 若默认态用 `ink-2 #5A6472`，压 `#EEF1F5` 只有 **2.93:1**，**低于 1.4.11 的 3:1**。
> 所以默认态字形取 `ink-1`。视觉上"深墨线条"也比如今的浅灰更干净。

### 5.5 交付方式

- **H5（当前目标端）**：`<svg><use href="#icon-name"/></svg>` 引用 sprite，或直接内联。
- **小程序端（若将来需要）**：小程序不支持内联 `<svg>` 标签，需降级为 **base64 data-uri 的
  `background-image`**。建议在 `SvgIcon.vue` 里按 `process.env.UNI_PLATFORM` 分支，而不是分叉两套图标。
- **数据迁移**：`categories.icon` 字段从存 emoji 改为存图标名；
  `resolveCategoryIcon` 对两种都兼容，所以可以**先上前端渲染，再慢慢迁移数据**，不需要一次性停机改库。

### 5.6 补充：分类图标另有一套「彩色」体系（2026-09-13）

§5 上面的论证针对的是**界面图标**（箭头、按钮、导航）和**系统 emoji**。
后来新增的「图标选择器」要给分类挑图标，产品侧明确要求**参考图的彩色扁平风格**，
于是增加了第二套图标渲染。两者分工如下：

| | 界面图标 | 分类图标（用户挑的） |
|---|---|---|
| 组件 | `SvgIcon.vue` | `ColorIcon.vue` |
| 数据 | `constants/icons.ts`（手绘真源） | `constants/color-icons.ts`（**生成物**） |
| 颜色 | `currentColor`，跟随选中/禁用/主题色 | **写死在 SVG 里**，不受 `color` 影响 |
| 来源 | 24 网格 / 1.75px 描边 | Iconify 离线集：flat-color-icons 329 + noto 141 |

**这不推翻 §5**：§5 反对的是"让**界面控件**用颜色不可控的图"（emoji 的四个问题）。
界面图标现在仍是清一色单色 `currentColor`；彩色只用在**用户自己挑的装饰性分类图标**上，
它不需要表达状态，也就没有"选不中态看不出"的问题。

调用点一律用 `CategoryIcon.vue`，由它按 `icon` 值**自动选渲染器** ——
不让每个页面各判一次类型：漏判一种只会显示白块，而且每页单独看都"正常"，极难自查发现。

代价：彩色图标数据 **gzip 212 KB**，挂在图标选择器页的懒加载里，不进首屏。

## 6. 版式：栅格、字号、圆角

### 6.1 间距：8px 栅格

`4 / 8 / 12 / 16 / 20 / 24 / 32`（4 为半格）。现状是 12/14/16/20 混用、无栅格，全靠手感。
**判断标准**：一个间距值如果不是 4 的倍数，就必须有理由。

### 6.2 字号：复用已验证的 8 档，不推翻

| token | 字号 / 行高 | FL-1 中的用途 |
|---|---|---|
| `display-lg` | 36 / 44 | 首页"本月支出"、记一笔金额 |
| `display` | 28 / 36 | 统计页"结余" |
| `h1` | 20 / 28 | 页面主标题、环形图中心金额 |
| `h2` | 17 / 24 | 区块标题、导航栏标题 |
| `body-lg` | 16 / 24 | 列表金额、按钮文字 |
| `body` | 15 / 24 | 正文基准 |
| `body-sm` | 14 / 22 | 次要正文、排行金额 |
| `caption` | 12 / 18 | 辅助说明（中文硬下限） |

**两条不许破的规矩**（来自前置规范的实测教训）：
- 字重只用 **400 / 500 / 600**。禁用 700 —— CJK 字体缺该字重时做算法加粗，笔画粘连发虚、跨端不一致。
- **每一条声明文字字号的规则，必须同时显式声明 `line-height`**（WCAG 1.4.12），且已有校验器强制。

### 6.3 圆角：收紧

| token | 值 | 用途 |
|---|---|---|
| `radius-sm` | 6 | 分段控件、小控件 |
| `radius-md` | 10 | 图标色块、输入框、按钮 |
| `radius-lg` | 14 | 卡片、模态、手机框 |
| `radius-pill` | 999 | 药丸标签（**只给药丸**） |

现状 12 / 16 / 24 偏"软"，配上阴影更像 2019 年的拟物残余。收紧后更利落，也更贴合"通栏"的结构感。
**圆形（50%）只给头像与环形图**，不给普通图标块 —— 方形色块在小尺寸下可辨识度更高。

## 7. 页面布局与信息层级

### 7.0 全局骨架

```
┌─────────────────────────────┐
│ 状态栏（28px，系统）          │
├─────────────────────────────┤
│ 导航栏（44px）或页面自有顶栏    │   仅流程页有标题；Tab 页用自有顶栏
├─────────────────────────────┤
│                             │
│ 内容区（flex:1，可滚）        │   通栏 + 发丝线分区
│                             │
├─────────────────────────────┤
│ TabBar（56px + 安全区）       │   4 格：记账 / 报表 / 记一笔 / 我的
└─────────────────────────────┘
```

**底栏的两种语义（2026-09-13 起）**：无 `url` 的格子切换**本容器视图**，有 `url` 的格子**跳转页面**。
「报表」属于后者 —— 它是独立页 `pages/statistics`，有导航栏与返回按钮、**没有底栏**。

**关于「记一笔」的位置**：它在 4 格里**不在正中**（实测槽位中点 12.5% / 37.5% / 62.5% / 87.5%，
凸起项落在 62.5%，距正中偏移 46px ≈ 底栏宽 12.3%）。这是「3 个视图 + 1 个动作」的必然结果 ——
凸起项要居中，左右槽位必须同宽，即需要 2+1+2 的 5 格。

**每个页面的信息层级最多 3 层**：结论层（最大字号）→ 明细层（正文）→ 辅助层（12px 灰）。
超过 3 层就说明这一屏该拆。

### 7.3 报表（原「统计」，2026-09-13 起为独立页）

> **承载方式变了**：这一屏从「容器内视图」改成**独立页** `pages/statistics`，
> 由底栏「报表」跳转进入（带导航栏与返回按钮，**没有底栏**）。
> 内容与规格不变 —— 变的是「它需不需要自己的返回路径」，不是内容本身。
> 判据见 §7.0：**需要原路返回的内容不该塞进单页容器**。

**目标**：知道钱花在哪。

| 层级 | 内容 | 规格 |
|---|---|---|
| ① 结论 | 结余 `¥18,212.75` | `display` 28px、`ink-1` |
| ② 明细 | 收入 / 支出（并列小字） | `body-sm`、绿/红 + 正负号 |
| ③ 图形 | 环形图 180px / thickness 24 + 中心合计 | 环内白色间隙分隔 |
| ④ 图例 | 色块 + 名称 + 金额 + 占比 | `body-sm` / `caption` |

**改造点（这一处修的是一个实测 bug）**：
原设计把"收入 / 支出 / 结余"三个金额做成 **20px 的并排三栏**。
阶段 5 把 `.value` 从 18px 归一到 20px 后，每栏需求从 89px 涨到 **105px**，而三等分栏宽只有 **96px** ——
三个数字**互相压在一起**，且因为 `body` 有全局 `overflow-x: hidden`，
既不出现滚动条也不报错，只有肉眼能看出来。

FL-1 的解法是**数字优先**：把**结余放大到 28px 独占一行**（它是"结论"），
收入 / 支出降为 14px 并排小字（它们是"明细"）。
这既解决了压字，也让信息层级更清楚 —— 原来的三栏并列等于告诉用户"这三个同等重要"，而事实不是。

**环形图分隔的正确做法**：`stroke-dasharray` 让每段弧长缩短 2px、偏移半个缺口，
露出下面的**白色底环**。文档原给的 `stroke="#FFFFFF" stroke-width="2"` **实测无效** ——
白描边与彩色弧同心同宽，被完全盖住。

**目标**：管理设置，改动少、但每次都要能找到。

| 层级 | 内容 | 规格 |
|---|---|---|
| ① 身份 | 头像色块 48 / 用户名 / ID | 头像用 `brand-600` 底 + 白字首字母 |

## 8. 关键组件与状态

### 8.1 状态命名规范（统一，避免各写各的）

`default / hover(桌面) / pressed / focus-visible / selected / disabled / loading / empty / error`

- **`pressed`** 用"底色加深一阶"（`brand-600` → `brand-800`），不用缩放、不用阴影。
- **`focus-visible`** 一律 `outline: 2px solid brand-700; outline-offset: 2px`。
  **必须用 `outline` 而不是 `box-shadow`** —— 本项目卡片/弹窗/列表项几乎全是 `overflow:hidden`，
  阴影版焦点环会被裁成半圈。
- **`disabled`** 不参与对比度要求（WCAG 豁免），但**必须**有可见的区别（用 `ink-4` + `bg-sunken`）。
- **`loading`** 必须是**骨架**,不是转圈：转圈会让页面高度跳动，骨架保持行高稳定。

### 8.2 组件清单

| 组件 | 变体 | 关键规格 |
|---|---|---|
| **按钮** | 主（实心）/ 次（浅底）/ 三级（描边）/ 危险（浅红底） | 高 44px；圆角 10；层级靠底色饱和度，不靠阴影 |
| **输入框** | 默认 / 聚焦 / 禁用 | 高 44px；边界 `#8A94A6`；**必须坐白底**；聚焦加 2px 焦点环 |
| **列表行** | 默认 / 按下 / 选中 / 加载 | 高 56（紧凑 48）；右侧金额 `min-width` 定宽 + 右对齐 |
| **分段控件** | 2–4 段 | 槽 `sunken`，选中项白底 + 深墨 + 600 字重（**形状也变，不只变颜色**） |
| **月份切换器** | — | 箭头命中区 44×44；月份文字可收缩（`min-width: 0`） |
| **图标色块** | sm / md / lg × 默认 / 选中 / 禁用 | 见 §5.4 |
| **金额键盘** | 数字键 / 辅助键 / 主键 | 数字白底、辅助 `sunken`、主键品牌色；完成键在最右下 |
| **底部主操作** | Tab 栏内等高按钮 | 40×32 圆角 10；**不凸起、无阴影** |
| **反馈** | Toast / 空状态 / 行内错误 | Toast 用色块 + 图标，不靠阴影浮起；空状态用图标不用 emoji 插画 |
| **模态** | 底部抽屉 / 居中弹窗 | 遮罩 `rgba(0,0,0,.45)`；**唯一允许阴影处** |
| **环形图** | 有数据 / 空 | thickness 24；段间 2px 白色缺口；中心文案 `h1` |

### 8.3 一个具体的状态演进（示例：分类网格项）

| 状态 | 外框 | 字形 | 名称 |
|---|---|---|---|
| 默认 | `sunken` | `ink-1` | `ink-2` |
| 按下 | `brand-100` | `brand-700` | `ink-1` |
| 选中 | `brand-600` | `#FFF` | `brand-700` + 600 字重 |
| 禁用 | `sunken` | `ink-4` | `ink-4` |

**四个状态里"形状/底色/字重"三样都在变**，不依赖单一颜色 —— 这是 WCAG 1.4.1 的要求，也是扁平设计能"只靠色块"还不失可读性的原因。

## 9. 响应式适配

### 9.1 策略：骨架不换，只调留白与列数

**字号不随视口缩放（px 固定），只随系统字号设置缩放。**
这条是实测教训换来的：项目已在 320px × 200% 字号下把 **8 个页面跑到 24 屏 0 不合规**（2026-09-13 结构变化后；此前为 7 页 21 屏），
不能为了"大屏更好看"把这套推翻。

### 9.2 断点

| 断点 | 典型设备 | 布局 | 关键调整 |
|---|---|---|---|
| **< 360** | 320 窄屏 | 单列 | 页面内边距 16 → 12；金额列 `min-width` 收窄；**允许换行而不是截断** |
| **360 – 599** | 手机常态（375 / 390 / 414） | 单列 | **基准**：内边距 16，行高 56 |
| **600 – 899** | 折叠屏展开 / 小平板竖 | 单列 + 居中 | 内容区上限 **560px** 居中；两侧留白同色，不加装饰 |
| **≥ 900** | 平板横 / 桌面浏览器 | 左导航 + 内容 | 侧栏 240px，内容区上限 **720px**；TabBar 转为侧栏 |

### 9.3 为什么大屏也不加列

记账是"**扫读数字**"的任务。行被拉长到 900px 后，用户的视线要横跨整屏才能把"分类"和"金额"对上。
上限 560px 保住**分类与金额在同一视野内** —— 这比"把屏幕填满"重要。

### 9.4 横屏

高度 < 500px 时：列表行高 56 → 48；记一笔页改为**左右两栏**（左侧表单、右侧键盘），
而不是上下堆叠（否则键盘会把金额挤出屏幕）。

### 9.5 大字号（200%）与安全区

- 所有固定宽度容器改用 `min-width`；flex 项补 `min-width: 0`。
- 金额用 `overflow-wrap: anywhere` **折行**，不用 `text-overflow: ellipsis` —— 截断是真的丢内容。
- 中文标签加 `white-space: nowrap`，否则「总收入」会被竖排成「总/收/入」。
- 底部固定元素加 `padding-bottom: env(safe-area-inset-bottom)`。
- **已知接受**：环形图中心注解在 320px × 200% 下无法容纳（内孔 Ø132px vs 文本需 198px，几何无解）。
  同一金额在结余行已可读，属重复标注，故不按内容丢失处理（详见 §11）。

### 10.4 落地路径与风险

建议**分三步**，每一步都可独立验收、独立回滚：

| 步骤 | 内容 | 风险 | 为什么排这个顺序 |
|---|---|---|---|
| **① 图标系统** | 替换 TabBar、列表行、分类网格的 emoji | **低**（纯增量，不动布局） | 见效最快、可逆；`resolveCategoryIcon` 兼容新旧数据，不需要停机迁移 |
| **② 配色 token** | 新增 `canvas` / `line`；图表色序重排；废弃 `divider` | **低–中** | 重跑 `npm run check:contrast` 即可验收（当前 155 项断言） |
| **③ 结构改造** | 去卡片、去渐变、去 FAB、圆角与间距收紧 | **中–高**（动布局） | 会动布局，必须**重跑 320px / 200% 复验** |

**第 ③ 步的前置提醒**：本项目为 320px × 200% 建过一套三桶判据的复验方法
（顶破文档 / 被祖先裁掉 / 压邻居，见前置规范 §7.4）。
结构改造后必须重跑 —— 阶段 5 的教训就是"字号归一"这个看起来无害的动作，
把统计页三栏金额从"刚好放下"推到了"压在一起"。

### 10.4.2 分类管理页（2026-09-13 落地）

这一页是 FL-1 里「设置类页面」的第一个完整样本，落地时确认了几条规则：

| 项 | 做法 | 依据 |
|---|---|---|
| 分层 | 页面底白 + 发丝线分区；**分组之间用 8px `bg-subtle` 灰带**分隔（而不是给每组套卡片） | §3.1 ②「用分隔线分层，而不是用卡片」 |
| 顶栏 | 自绘（`navigationStyle: custom`）：返回 / 「支出分类管理」/ 搜索 | 参考图的标题带收支类型 ⇒ 类型是**页面级参数**，页内不放切换器 |
| 选中框 | 24×24 圆角 6，选中填 `brand-600` + 白勾 | §6.3 圆角阶梯 |
| 「隐藏」态 | 换 `text-tertiary` 配色 + 「已隐藏」中性徽标，**不用 opacity** | §4.3：文字加透明度会静默吃掉对比度 |
| 底栏三操作 | 40px 圆角图标块 22px 图标 + 12px 标签；**按选中项状态自动禁用** | §8.1：禁用态必须有可见区别，且不能是"点了没反应" |
| 大字号 | 底栏 `flex-wrap`、分类名折行（不用 ellipsis 截断） | §9.5：200% 字号下不许丢内容 |

**一处有意偏离参考图**：参考图每行右侧有拖拽手柄（≡）与行内编辑图标。**只保留了编辑** ——
拖动排序尚未实现，放一个拖不动的手柄等于骗用户（与 §3.2「不能扁平」的清单同一条原则：
不为视觉完整牺牲控件真实性）。编辑入口是必要的：批量操作只能删 / 隐藏，改名与换图标没有别的入口。

**另一处**：底栏两段之间**没有放参考图那条竖分隔线**。×2 字号下两段必须换行，
换行后 `border-left` 会变成第二行左侧一道孤立的竖线，看着像渲染坏了。
顶栏那条横线已经完成"与列表分隔"的职责，装饰性元素不值得为它牺牲布局正确性。

## 11. 未决与已知取舍

1. **环形图中心注解在大字号下与环带重叠** —— 几何上无解：
   内孔直径 = `size 180 − 2 × thickness 24` = **132px**，而金额在 ×2 字号（40px）下需要 **198px**。
   同一金额在结余行已完整可读，属重复标注，故不按内容丢失处理。
   彻底解决属设计决策（大字号时把总额移出圆环 / 环内只留占比），**留给下一轮**。
2. **图表序列的全局两两最差 15.62（橙红 ↔ 品红）** —— 在环形里永远不相邻，按现口径无需处理；
   但若将来支持"点图例高亮"，需要重新评估（§4.5）。
3. **深色模式未做** —— 前置规范 §5 已有映射表（预留）。FL-1 的"大面积中性"策略对深色模式友好
   （中性换一档即可），但**不能假设**：深色下 `ink-3` 与分区的对比关系必须重测。
4. **键盘 Tab 导航未打通** —— `:focus-visible` 规则就位，但 uni-app H5 把 `<view>` 渲染成
   不可聚焦的自定义元素，实际能用 Tab 走到的只有原生可聚焦元素。
   补齐需要给交互元素补 `tabindex`，属独立任务。
5. **底部主按钮 vs 凸起 FAB** —— 本方案选前者（不遮挡内容、拇指可达）。
   若产品侧更看重"记一笔"的视觉突出度，可退回 FAB，但需要接受它遮挡列表内容的事实。
6. **品牌色未更换** —— 见 §4.4 的取舍说明；四个备选主色的实测值已给出，随时可换。
