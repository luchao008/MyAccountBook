## 一、传输层：gzip + 预压缩 + 缓存分层（提交 `d015d2c`）

**起因**：luchao 问「前端项目提升丝滑度有什么建议」。排查后发现一个反直觉的事实 ——
**代码层**其实已做过不少刻意优化（骨架屏、color-icons 动态分包、scroll-view 显式高度、
backdrop-filter 降级、prefers-reduced-motion），但**传输层完全是裸的**：

| 层 | 优化前 |
|---|---|
| nginx | 没有 `gzip`、没有任何缓存头 |
| 后端 | 没有响应压缩（依赖里没有 compress 中间件） |
| 图片 | 94 张 PNG，无懒加载（且 `lazy-load` 在 H5 本就无效，见 §四） |
| 产物 | `frontend/dist` 陈旧（源码 10-01 改过、产物停在 09-30） |

**实测收益**：

| 项 | 前 | 后 |
|---|---|---|
| App 前端 JS+CSS | 2254.8 KB | **735.9 KB（-67%）** |
| 中台 admin JS+CSS | 3021.0 KB | **897.7 KB（-70%）** |

**落地**：

- 新增 `scripts/precompress.mjs`：构建期生成 `.gz`。白名单**只压文本**（js/mjs/css/html/json/svg/
  txt/xml/map/webmanifest），**跳过 PNG/WebP/WOFF2/ICO**（本身已压缩，再 gzip 纯浪费）；
  增量（`.gz` 比源新就跳过）；**保留原文件**（`.gz` 是额外产物，nginx 只在客户端声明 gzip 时才用）。
- 两份 nginx conf：`gzip_static` 与 `gzip` **同时开**（前者吐预压 `.gz`、运行时零 CPU；后者兜住没预压的）。
  只开前者 → 漏压的文件完全不压；只开后者 → 每次冷请求都现场压同一批静态文件。
- `deploy/build-and-export.sh` 插入 **`3/7 预压缩`**：必须在两个前端构建完**之后**、打镜像**之前**
  （早于构建会压到旧产物；晚于打镜像则根本进不去镜像 —— 因为 Dockerfile 整目录 COPY，无需改 Dockerfile）。
- 后端加 `koa-compress`：`src/middleware/compress.middleware.ts`，`match()` 只认 `/api`、阈值 1KB、**只 gzip**
  （不开 br：部署是明文 HTTP，浏览器只在 HTTPS 下才广告 `br`；也不单独开 deflate，因为 nginx 的 gzip 模块
  同样只服务 gzip —— 端到端保持一致）。注册在 `useMiddleware([...])` **数组第 0 项（最外层）**：
  koa-compress 在 `await next()` 之后才读 `ctx.body`，必须站在 `ResponseMiddleware` 外面才压得到最终 body。

**缓存分层（判据：文件名带不带内容 hash）**：

| 路径 | 策略 | 理由 |
|---|---|---|
| `/assets/`、admin `/js//css//jse/` | 1 年 `immutable` | 文件名带内容 hash |
| `/static/cat-icons/` | 1 年 `immutable` | 固定名，靠 URL 上的 `?v=` |
| `/static/` 其余（logo / app-icon / tabbar） | **7 天** | 固定名、**没有版本号**；给一年会变成"我明明换了图怎么还是旧的" |
| `index.html`、admin `_app.config.js` | `no-cache` | 里面写着当次构建的 hash 文件名，缓存住 = 把用户锁在旧版本 |

⚠️ **判据与坑**：

- `add_header Cache-Control` **不要加 `always`**（会把 404 也带上一年的缓存）；不要与 `expires` 同时写（会发两个头）。
- **绝不要给 nginx `/api` 加 `proxy_set_header Accept-Encoding ""`** —— 会抹掉客户端编码偏好，
  后端不再压；而 nginx 的 `gzip_proxied any` 又只压"未压缩的"代理响应 → 接口体积悄悄回到未压缩，**不报错**。
  已在 `location /api/` 就地写了警告注释。
- nginx:alpine 官方镜像**编译了 `gzip_static`**（实测 `nginx -V` 确认），但**没有 brotli 模块** —— 写 `brotli on` 会启动失败。

**验收判据（缺一不可）**：

1. 临时 `nginx:alpine` 容器挂载产物 + `curl` 看头；关键判据是
   **nginx 返回的字节数 == 磁盘上 `.gz` 的字节数** —— 只有相等才证明走的是 `gzip_static` 预压缩
   （动态压的字节数通常不同）。实测 JS `302,467 → 105,671`，与磁盘 `.gz` 完全相等。
2. 另**单独造一个没有 `.gz` 的文件**，验动态兜底路径确实生效（实测：无 `.gz` → `Content-Encoding: gzip`；
   不带 `Accept-Encoding` → 原样 7223 字节）。

## 二、分类图标 WebP 化：双份产物 + 按平台切扩展名（提交 `0d02732`、`e23ae52`）

**实测**：94 张 **1.884 MB → 0.215 MB（省 88.6%）**，sharp `{ quality: 90, effort: 6 }`（devDependency，不进镜像）。
合成白底后逐像素平均误差 **1/255**，肉眼不可辨。我用 **PIL 独立复算**过 q90 档，体积与 sharp 产物**吻合**
（这个"独立第二实现"很值 —— 它同时验证了 sharp 的参数含义与我的测量方法）。

**为什么是双份产物**：WebP 在 H5 上省 88.6%，但小程序 `<image>` 加载**包内本地文件**走的是各端原生实现
（不是浏览器内核），**无法离线确认**它对 webp 的支持 —— 一旦不支持就是**安静地显示空白**。
故 `static/cat-icons/` 下同时存在 `.png`（小程序/App）与 `.webp`（H5）。

**⚠️ 三个高危点（迁移时最容易坏的地方）**：

1. **映射表 `CAT_ICON_FILES` 的值改成不带扩展名的基名**（`"wucan"` 而非 `"wucan.png"`），扩展名由
   `utils/catIcon.ts` 用 `#ifdef H5` / `#ifndef H5` 按平台拼。**改映射格式与改消费方必须同批合入** ——
   单独生效任何一个都会拼出 `.png.webp`，**两端同时坏**（实测 H5 得 `/static/cat-icons/wucan.png.webp?v=…`）。
2. **两段条件编译必须互补且互斥**，才能保证每个平台都必被赋值。**别改成平台白名单**
   （如 `#ifdef MP-WEIXIN`）—— 那样 App / 支付宝端会落进初始空串 → 图标整片空白且不报错。
3. **写法必须是「`let src` + 条件编译赋值」**，不能把两段 `return` 各包一层 `#ifdef`：
   `vue-tsc` 检查的是**未经 uni 预处理**的源码，两个 `return` 它都看得见 → 报不可达代码。

**`?v=` 版本号**：算 `static/cat-icons/` 的**目录内容 hash**（文件名 + 内容，8 位 hex，现覆盖 PNG+WebP 共 188 个文件）。
用**目录内容 hash** 而非构建时间戳的理由：图标没变 → 版本号不变 → 回访用户直接命中缓存；
用时间戳则每次部署都让所有人重下图标。⚠️ 算 hash 要**跳过隐藏文件**（macOS `.DS_Store` 会随 Finder 变化，
参与进去破坏跨机器可复现性）、排序**不能用 `localeCompare`**（受 locale 影响）。

**构建期裁剪**（`e23ae52`）：`vite.config.ts` 新增 `pruneUnusedIconFormat()`，删掉本端用不到的那一套
（H5 删 94 个 PNG、小程序删 94 个 WebP）。三个非显然的实现决定：

- 挂 **`closeBundle` 而非 `writeBundle`** —— `static` 的拷贝发生在 `uni:copy` 的 `writeBundle`
  （且会 await 文件监听器），写进 `writeBundle` 就是**和自己的拷贝赛跑**。
- **只动产物、绝不动源目录**（同一个 `src/static/` 供所有端构建）。
- **安全阀**：只删"同名另一套确实存在"的文件；只有一侧的**保留 + 告警**（已做负向验证：埋一个孤儿 `.png`，它被保留而非误删）。

**新的离线校验器** `scripts/verify-cat-icon-assets.mjs`（30 条判据、只读磁盘、秒级）：两套按基名一一对应 /
映射格式 / 文件头尺寸 alpha / **有没有哪个 webp 反而更大（反向检查）** / **用 uni 真实预处理器实测两端产出的 URL**。
它是 Playwright 版 `verify-cat-icons.mjs` 的**离线前哨**。

## 三、复核仓库审计结论：证伪三处

> 背景：并行 agent 跑了两份性能审计，给出了一批带数字的建议。逐条实测后，**其中三条不成立或量级严重偏差**。

### ❌ 「报表页运行时注入 730 KB ECharts」（声称合计 997 KB raw / 315 KB gz）

**不成立**。注入路径 `ecinit` 只绑定在 `<block v-if="echarts">` 内部，而 `echarts` 仅由
`echartsH5` / `echartsApp` 两个 **prop 置真，两者默认 `false`，全项目无人传**
（三个 grep 全空：prop 传递、`opts` 里的 echarts 配置键、业务代码引用 `config-echarts`）。

**真实成本**（构建产物实测）：

| 项 | 体积 | 是否下载 |
|---|---|---|
| 报表页壳 | 15,106 B raw / **4,734 B gz** | 是（async 拆分后；**原为 267 KB raw / 72 KB gz**） |
| TrendChart 异步 chunk（uCharts） | 259,028 B raw / **69,072 B gz** | 仅渲染图表时 |
| echarts.min.js | 747,492 B | **从不请求** |

⛔ **结论**：那 747 KB 只是产物里的死重量；"换 `echarts/core` 按需构建""用自研 SVG 替掉 TrendChart 省 1 MB"
都是在追幻影。**有价值的那半步（`defineAsyncComponent` 拆包）已经做了**，报表页首帧 chunk 从 267 KB 降到 15 KB。

### ❌ 「admin 的 antd 注册表白背 423 KB」

**机制真实、量级约一半**。做法：对照构建实验（备份 `adapter/component/index.ts` → 裁到 5 个组件 → 构建 → 还原 → 重建）。

| | 注册 21 个（现状） | 只注册 5 个 | 差 |
|---|---|---|---|
| `bootstrap` chunk | 1336 KiB | 1100 KiB | −236 KiB |
| JS 合计 | 2635 KiB | 2400 KiB | −235 KiB |
| JS gzip 合计 | 826 KB | 756 KB | **−70 KB gz** |

⚠️ 我裁的是"极限值"（`ApiTreeSelect` 会失去 `TreeSelect`，不可用）。**可用做法**是"保留框架真正按名请求的 +
把重的改成 `async import`"（上游注释本身就建议这么做），所以真正能落地的收益 **≤ 235 KiB**。

### ❌ 「`<image lazy-load>` 可以懒加载图标选择器的 94 张」

**H5 上是 no-op**。`uni-h5.es.js` 里 `lazyLoad` **只出现 1 次（prop 声明本身）**，读取 `.lazyLoad` **0 次**。
所以审计建议的"`<image lazy-load>` **或**只渲染可视区"里，**H5 只有后半句可行**。

⛔ **这条同时修正了我自己 `c390387` 提交里的说法**：我在那里写"图片图标补 `lazy-load`"当作 H5 优化，
实际它在 H5 不起作用（小程序端有效，因为那是原生组件）。

### ✅ 顺带证实的真实大头（admin）

- 首屏必须的 `bootstrap` chunk **1336 KiB / 415 KB gz**（每次访问都付）。
- 用户列表页 `list` chunk **560 KiB / 177 KB gz**，其中 `vxe-table` 出现 **201 次** —— 但它是**懒加载**，不伤首屏。
- 启动图 `app-icon.png` **192×192 / 73,561 B** 用在 `index.html:82` 的 **64×64** 启动画面
  （分辨率对 3 倍屏其实是对的，问题是文件太大）。
- `<!--preload-links-->` 占位符**在产物里原样保留**、无任何构建步骤填充 → 零 modulepreload。

## 五、⛔ 本日我犯的两个错误（都已修复并验证）

### 1. `pkill -f "uni"` 误杀 Docker Desktop

收尾清理 dev server 时我用了过宽的 `pkill -f "uni"`。Docker VM 进程的命令行里含
`linuxkit.`**`uni`**`fied_cgroup_hierarchy=1` → **整个 Docker Desktop 被终止**，
连带停掉 luchao 从 9-30 起跑着的 `account-book-mariadb` 容器（Exit 255；且该容器重启策略是 `no`，**不会自愈**）。

**恢复与核对**：重启 Docker Desktop（Server 24.0.5）→ `docker start` 拉起容器 → 数据在命名卷
`account_book_data` 上，**无损**（6 张表 / 15,598 条流水 / 4,251 个分类 / MariaDB `ready for connections`）。

⛔ **教训：收尾清理绝不用过宽的 `pkill -f` 模式** —— 按 PID，或用足够具体的模式
（`pkill -f "vite.*dev:h5"` 这种）。"看起来够特别"的关键词可能藏在别人的命令行参数里。

### 2. 对照构建实验把 admin `dist` 弄成混合态

turbo 命中缓存时**只还原基线产物、没清掉裁剪版的文件** → `dist` 里两个
`bootstrap` chunk 并存（JS 合计虚高到 4935 KiB）。已 `rm -rf dist` + 重建复原为干净的单 chunk（1336 KiB）。
