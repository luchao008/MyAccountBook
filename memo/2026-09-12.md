## 实现要点

- 右侧 `scroll-view` 加 `@scroll` 监听 + `scroll-into-view` 定位；
  每个分组设锚点 id（`group-anchor-<rootId>`），左侧 `side-anchor-<rootId>`。
- **锚点测量**：`uni.createSelectorQuery().in(getCurrentInstance())`，
  取各分组与滚动容器的 `boundingClientRect`，相减得到相对内容顶部的偏移
  ——该值不随滚动变化，**只需在弹窗打开后测一次**。
- **滚动反推**：`scrollTop >= anchorTops[i] - 8`（8px 容差防边界跳动），
  取满足条件的最大 i 作为当前组。
- **双向定位都要"先清空再赋值"**：`scroll-into-view` 值不变不会重新触发滚动，
  必须 `mainIntoView=''; nextTick(() => mainIntoView='group-anchor-x')`。
- 左栏跟随高亮项滚动（同样用 scroll-into-view）。
- 搜索模式切到独立结果列表（不做联动），退出搜索后重新测量。

## 踩坑

## 补充：滚动条——左侧隐藏、右侧自绘贴边

用户反馈：右侧滚动条被 `.main` 的 `padding: 12px` 挤进了内容区，不在最右侧。
**根因**：原生滚动条永远贴"滚动容器"的边缘，而 padding 在容器内侧，
所以只要容器有右 padding，滚动条就不可能贴到组件最右侧。

**解法：放弃原生滚动条，自绘**：

- `onMainScroll` 里本来就有 `scrollTop`，顺手记下 `scrollHeight`；
  `measureAnchors` 时顺便量出可视高度——三者齐了就能算滑块位置：
  `barHeight = viewport/scrollHeight * viewport`（最小 40px），
  `barTop = scrollTop / scrollable * (viewport - barHeight)`。
- 滑块是 `.content` 下的绝对定位元素（`right: 2px`），不受 `.main` 的 padding 影响。
- `pointer-events: none` —— 纯位置指示器，不拦截滚动手势。
- 原生滚动条沿用 App.vue 的全局隐藏规则（正好避免出现两根）。
- 加了 `transition: top 0.08s linear`，滑块移动更顺滑。

教训：**和框架内部 DOM 结构斗争不如换思路**。第一版试图用 CSS 选择器
精确命中 uni-scroll-view 的内层容器来"恢复"原生滚动条，位置不可控；
改为自绘后位置完全由自己的布局决定，反而更简单。

用户要求「把项目启动起来」。现状：MariaDB 容器在跑，7001 / 5173 均无监听。

### 启动方式（务必记住）

两个长驻进程都用**工具的 `run_in_background`**，不用 `nohup ... &`（会被杀）：

| 服务 | 命令 | 端口 | 说明 |
|---|---|---|---|

### 改了一处配置：`frontend/vite.config.ts`

**问题**：Vite 默认 `host: 'localhost'`，在本机 Node 下**只监听 `[::1]`（IPv6 回环）**，
`curl http://127.0.0.1:5173` 直接 `http=000`。浏览器会自动回落所以肉眼看不出，
但**只探 IPv4 的工具/预览面板会连不上**（实测经 `127.0.0.1:5173/api` 打代理就是 000）。

**改法**：`server.host = '127.0.0.1'`（显式绑 IPv4），并加 `strictPort: true`
避免端口被占用时静默换到 5174、让代理配置与实际端口对不上。

> 经验：**dev server 起来了 ≠ 你能连上**。判断服务是否可用要分别探 `127.0.0.1` 与 `localhost`，
> 只探一个很容易被 IPv4/IPv6 绑定的差异骗过去。

## 移除原生 tabBar，改用自定义导航组件

需求：原生 tabBar 无法按页定制（账本选择页只要两项），改为自定义组件；
且账本选择页跳首页后要能返回。

### 核心改动

1. **`pages.json` 删除整个 `tabBar` 配置**（含上一步刚加的 iconPath）。
2. **新增 `components/TabBar.vue`**：
   - `items` prop 可覆盖默认四项（账本选择页传两项）→ **一套组件适配两种导航**
   - 高亮同步：`getCurrentPages()` 不是响应式的，所以用 ref 在 `onMounted`/`onShow` 时读取当前路由
   - 选中态用颜色 + 字重双通道（不是只变颜色）
3. **切换策略（避免白屏/闪烁的关键）**：
   ```
   目标页已在页面栈中 → navigateBack 回退（复用实例，不重建）
   目标页不在栈中     → navigateTo（首次进入）
   ```
   反复切换不会让栈无限增长，也不会每次重建页面。
4. **账本选择页 → 首页改用 `navigateTo`**（原 `switchTab`）：保留页面栈，
   首页左上角才会出现返回按钮；点返回即回到选择页。
5. **清理失效调用**：`record` 页两处兜底 `switchTab` → `reLaunch`（原生 tabBar 移除后
   `switchTab` 会失败）。全仓已无 `switchTab` 调用残留。
6. **`RecordFab` 落位上移**：`bottom: 0` → `calc(52px + safe-area)`，坐在导航栏上沿不重叠。

### 一个如实说明的固有限制

uni-app 的**多页面**方案下，导航栏是每个页面各自持有的实例，
页面转场（300ms）会让它跟着一起平移——这是该方案的固有表现，
**无法在"每页引入组件"的前提下彻底消除**。

已做的缓解：贴底固定、背景不透明、高度与原生 tabBar 一致（52px）、
切换优先走 `navigateBack`（不重建页面，减少闪烁感）。
若要完全消除滑动感，需要改成单页 + 组件切换架构（改动大，超出"不改业务逻辑"的约束）。

## 修复：删除 tabBar 导致白屏崩溃

用户报错：
```
TypeError: Cannot read properties of undefined (reading 'height')
    at useShowTabBar (uni-h5.es.js:23708)
```

### 根因（读 uni-h5 源码确认，不是猜）

```js
function useTabBar() {
  if (!tabBar) tabBar = __uniConfig.tabBar && reactive(initTabBarI18n(__uniConfig.tabBar));
  return tabBar;                       // 无配置 → undefined
}
function useShowTabBar() {
  updateCssVar({ "--tab-bar-height": tabBar2.height });   // 无条件读 .height → 💥
}
```

**uni-app H5 假设 tabBar 配置必然存在**。整块删除后 `__uniConfig.tabBar` 为 undefined，
`&&` 短路使 `tabBar2` 变成 undefined，随后无条件读 `.height` 直接抛错 →
Layout 组件崩 → 整个页面白屏（连带 `Component is missing template` 的次生警告）。

### 解法：保留配置，只清空 list

```json
"tabBar": { "list": [] }
```

**验证（构建产物实证，非推理）** —— `dist/build/h5/index-*.js` 中：

```js
__uniConfig={ ..., tabBar:{ position:"bottom", color:"#999", ..., height:"50px", list:[], selectedIndex:0, shown:!0 }, ... }
```

- `height:"50px"` 由编译器注入 → `tabBar2.height` 有值，不再抛错 ✅
- `list:[]` → 编译期所有路由 `meta.isTabBar` 为 false → 原生 tabBar 组件不渲染 ✅
- `--window-bottom` 为 0 → 页面不会多出底部留白 ✅

> 立刻撤掉。说明只能落在文档里。

## 单页 + 组件切换架构改造（零滑动感的解法）

用户要求彻底消除导航栏随页面转场平移的问题。

### 为什么必须改架构

uni-app **多页面**方案下，导航栏是每个页面各持一个实例，
页面转场（300ms）时它必然跟着平移——这是该方案的固有表现，无解。
唯一的根治办法是让导航栏**只存在一个实例**，即单页多视图。

### 新结构

```
pages/account-select/index.vue   启动页（选账本，navigateTo 进容器，返回按钮有效）
pages/main/index.vue             容器：4 个视图 + RecordFab + TabBar（各一份实例）
components/views/HomeView.vue         ← 原 pages/home
components/views/DetailView.vue       ← 原 pages/detail
components/views/StatisticsView.vue   ← 原 pages/statistics
components/views/MineView.vue         ← 原 pages/mine
```

原 4 个页面目录**已删除**（pages 下只剩 6 个：account / account-select / category / login / main / record）。

### 关键设计

1. **导航栏只实例化一次** → 转场消失，这是"零滑动感"的全部来源。
2. **v-if + visited 懒挂载**：没访问过的视图不渲染，避免一次性打 4 个接口；
   访问过的保持挂载（`v-show` = display:none），**再次切换不重新请求、状态保留**。
3. **TabBar 双模式**：
   - 受控模式（传 `current`）：容器用，点击只 `emit('change')`，由容器切视图
   - 导航模式（不传 `current`）：账本选择页用，按 `url` 跳转（栈内 back / 否则 navigateTo）
4. **生命周期适配**（视图没有自己的页面生命周期）：
   - `onLoad`/`onShow` → 视图暴露 `activate()`，容器在切换时与容器 `onShow` 时调用
   - 首次显示交给视图自己的 `onMounted`，容器 `onShow` 用 `firstShow` 标志跳过，避免重复请求
5. **页面级事件转发**：`onReachBottom` / `onPullDownRefresh` 在组件里拿不到，
   由容器统一接收后转发给当前激活视图的 `onReachBottom?.()` / `onPullDownRefresh?.()`。
   **明细页的分页加载依赖这条**，是本次改造最容易漏掉的一环。
6. **导航栏标题自己切**：单页容器里标题不会自动变，`switchTo` 时调 `uni.setNavigationBarTitle`。
7. 跳转路径统一改为 `/pages/main/index`（login 登录后、record 页两处兜底、账本选择页），
   并支持 `/pages/main/index?tab=mine` 直接落到指定视图。

### 滚动位置记忆（后续补上）

各视图的滚动位置**独立记忆**，切回时恢复到原位：

- 位置表用**普通对象**而非 ref —— `onPageScroll` 触发极其频繁，
  走响应式等于每次滚动都推一次依赖更新，而这里根本不需要响应式。
- **恢复期间必须暂停记录**（`restoring` 标志）。原因：切换视图时页面总高会从
  「旧视图高度」突变成「新视图高度」，浏览器会立刻把 scrollTop 调整到新范围内，
  这个中间态同样触发 `onPageScroll`；若不禁用，它会被写进**新视图**的位置表，
  把用户的真实记忆污染掉。这是本功能唯一容易踩的坑。
- 恢复动作放在 `nextTick` 之后再 `setTimeout(0)`：v-show 切换后页面高度由新视图决定，
  在高度更新前滚动会被旧高度截断。
- `pageScrollTo` 的 `complete` 在部分端不回调，所以另设 120ms 兜底解除 `restoring`，
  避免它永久卡住导致位置再也不记录。

### 其余取舍

- 页面栈更深了：账本选择页 → 容器 → 记一笔/设置页。返回行为符合预期。
