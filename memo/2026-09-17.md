## 九、报表页顶栏：返回键触摸区贴到视口左边缘（luchao 报告）

**症状**：luchao 说「报表页面的顶栏有点布局问题」，追认为「返回键贴左边缘」。

### 先量，再判 —— 而且这次差点被量法本身骗了

第一次测量用的是 `svg.getBoundingClientRect().left`（**包围盒**左边缘）：
报表 12、大标题 16 → 得出"错开 4px"，差点照着去改。

改用 `getBBox()` 量**可见墨迹**后才对：`icon-chevron-left` 在 24 视口里只占中段，
缩到 20px 后墨迹还要再内缩 **5.94px**（≈ `size × 0.297`）。

| | 量法 A（包围盒） | 量法 B（墨迹） | 参考图实测 |
|---|---|---|---|
| 报表页返回箭头左边缘 | 12 | **17.94** | **17.0 pt** |
| 报表页大标题文字左边缘 | 16 | 16 | **17.0 pt** |

→ **结论反了**：箭头与大标题本来就同轴（差 1.94px），和 luchao 给的参考图
（IMG_4201，iPhone 16 Pro @3x）也差不到 1px。照量法 A 去"修"，会把对齐的推歪。
**量错比不量更危险 —— 因为它会给你一个可以执行的错误结论。**

### 真正的问题：报表页是唯一的异常值

把 5 个自绘顶栏页的 `.nav-inner` 拉平比较：

| 页面 | `.nav-inner` 左右内边距 | 返回键触摸区左边缘 |
|---|---|---|
| 流水 / 日历 / 回收站 / 数据导出 | **8px**（`padding: 0 $space-2`） | 8 |
| **报表** | **0** | **0** ← 异常值 |

### 修法：两条约束互斥，靠"内部补偿"同时满足

几何关系：`墨迹位置 = 触摸区起点 + 图标在按钮内的偏移 + 内缩(5.94)`

- 想「墨迹对齐大标题 16px」→ 触摸区起点需为 **-1.94**，不可能；
- 想「触摸区退到 8px」→ 只加行 padding 会把墨迹推到 25.94，同时偏离大标题与参考图。

解法是在按钮内部把等量位移补回来：

```
8（行 padding）+ 4（按钮 padding-left）+ 0（flex-start，不再居中）= 12
                                    原值 = 0 + (44-20)/2 = 12   ← 完全相等
.nav-inner { padding: 0 $space-2 }
.nav-back  { justify-content: flex-start; padding-left: $space-1 }
```

**实测结果**：触摸区 0 → **8**；墨迹 **17.94 → 17.94（纹丝不动）**。
终版截图与改前**字节级完全一致** —— 视觉零变化，只有那块看不见的触摸区动了。

「某页漏了一条已成文的约定」是**静态可查**的，不该等肉眼发现。守卫断言：
所有含 `.nav-inner` 的 `.vue` 都必须声明 `padding: 0 $space-2`。

## 十、报表页标题收进顶栏（luchao：「报表两个字要放到顶栏」）

### 改了什么

报表页原先是全站唯一的 iOS Large Title：返回行 44 + 左对齐大标题 48（`$font-display` 28/36）。
现在标题住进那 44px 返回行 —— 与流水 / 日历 / 回收站 / 数据导出同一形态。

| | 改前 | 改后 |
|---|---|---|
| 吸顶区高度（`.sticky-head`） | **137**（44 返回行 + 48 大标题 + 45 Tab） | **89**（44 + 45） |
| 标题位置 | 左对齐，左边缘 16 | **居中**，墨迹 170.5–204.5（宽 34），中心 **187.5** |
| 标题字号 / 颜色 | `$font-display` 28/36 · `$v11-text-primary` | `$font-h2` **17/24** + 600 · 同色 |
| 返回键 | 触摸区 8、墨迹 17.94 | **完全不变**（8 / 17.94） |

**居中这件事有个坑，值的算法不一样**：
`flex: 1 + text-align: center`（流水页 / 分类页的写法）是在**剩余空间**里居中，不是**在屏幕里**居中。
左有 44px 返回键、右侧为空 → 文字中心会右偏 `(44+8)/2 = 26px`。
宽标题看不出来，「报表」两个字一眼能看出。所以改用**绝对定位**（`left/right: 0` + `text-align: center`），
这也是 iOS 的做法。实测墨迹中心 187.5 = 视口中心 187.5，偏差 **0**。

### 顺手挖出一个「完全看不出来」的失能

绝对定位的标题横跨整行、且晚于返回键绘制 → **它盖住了返回键的 44×44 触摸区**。
漏掉 `pointer-events: none` 的话：页面照常渲染、标题照常显示、`getBoundingClientRect` 一切正常，
**只有点下去没反应**。同类漏法：忘了给 `.nav-inner` 加 `position: relative`（标题会相对更外层定位）。

**所以这条的验收方式必须是"能不能点到"，而不是"在哪"**：
用 `document.elementFromPoint()` 在返回键触摸区的**左上 / 中心 / 右下**三点做命中测试 ——
实测三点全部落在 `.nav-back` 内（`nav-back✓`）。几何探针永远查不出这一层。

### 11.2 两个关键决策的取舍

**① 后端解析，且自写零依赖 xlsx 读取器**（`src/transaction/xlsx-reader.ts`，约 400 行）。

- 为什么不前端解析：分类匹配必须用**账本级分类树**（后端权威）；且前端不打包 xlsx 库

项目**没有批量删除**，误导入只能逐条删 → 预览是唯一的防线。

## 十二、修 bug：删除账本「名字输对了却说没拿到名称」

luchao 报告：账本删除时输入了正确的账本名，后端仍提示没拿到名称。

### 12.1 根因（一行）

`frontend/src/api/account.ts` 的 `deleteAccount`：

```ts
return http.delete(`/accounts/${id}`, {
  params: { confirmName },   // ← 这个 params 根本没被当成查询串
});
```

**luch-request 的签名是 `delete(url, data, options)`** —— 第二个参数是**请求体**，
不是 axios 那种 config。于是 `{ params: { confirmName } }` 作为 **JSON body** 发出去，
URL 上干干净净没有查询串；后端 `DeleteAccountQueryDTO.confirmName` 是 `@Query()`，

浏览器实测复刻（`uni.request` 同参数）：

```
DELETE /api/accounts/3427                        → 422 {"code":40000,"message":"\"confirmName\" 是必须的"}
DELETE /api/accounts/3427?confirmName=删除复现…  → 200 {"code":0,...}
```

### 12.2 为什么一直没被发现

- 它**表现成后端校验失败**（422 + 「是必须的」），看着像后端 DTO 的问题，
  而 `regression-test.sh` 里的账本删除用例是**手写 curl 查询串**的 —— 接口本身没问题，
  所以回归全绿。
- 前端这条链路上没有任何断言：删除是写操作，UI 级验证脚本一直没覆盖它。
- **自仓库初始化起就存在**（`git show 61019ac` 确认），不是本次改动引入。

### 12.3 修法与验证

修法：查询串自己拼进 URL（与 `category.ts` / `transaction.ts` 一致，那两个本来就是对的）：

```ts
http.delete(`/accounts/${id}?confirmName=${encodeURIComponent(confirmName)}`)
```

新增 `scripts/verify-account-delete.mjs`（**16 项**，走完整 UI：点「删除」→ 可输入弹窗 →
填名字 → 确定）。刻意设计：

- **先测失败路径**（名字输错 → 40001、账本仍在），确保后面的成功路径不是"本来就绿"；
- 断言 **URL 上带 `confirmName=` 查询串** —— 直接守住"不能再退回 body 写法"；
- 只操作**自建临时账本**（建两个、删一个、清理另一个），绝不碰 demo 已有账本。

## 十四、流水导入：去掉「一次只能导 2000 条」的天花板（luchao 问 → 方案 B）

luchao 问：「为什么流水导入一次只能支持 2000 条」。

### 14.1 根因（我自己埋的）

`MAX_ROWS_RETURNED = 2000` 本意是「**预览响应**最多回传多少行明细，免得几万行 JSON 一次吐出去」，
注释也是这么写的。但前端 `onCommit()` 提交的正是 `preview.value.rows` —— **同一份被截断过的数据**：

```
preview: rows.slice(0, 2000)   →  前端拿着这 2000 行   →   commit 只写这 2000 行
```

于是 5000 行的账单：汇总卡显示「将导入 5000 条」、按钮写「确认导入 5000 条」，**实际只写进去 2000 条**。
更糟的是预览页底部那句文案还写着「导入条数不受影响」——**那句是错的**，写的时候没把
「展示截断」和「提交数据来源」串起来看。

顺带暴露三个数彼此不一致：文件体积 2MB（≈3.3 万行）/ 预览回传 2000 / 提交 DTO 上限 20000。

### 14.2 方案 B（luchao 拍板）：提交也传文件，服务端重新解析

| | 旧 | 新 |
|---|---|---|
| preview 入参 | 文件 | 文件（不变） |
| preview 出参 | **全部行**（截断到 2000） | 汇总 + **只回传异常行** |
| commit 入参 | **前端回传的 rows** | **同一个文件** |
| 行数上限 | 2000（隐性） | **文件 2MB ≈ 3 万行** |

代价只是解析两次（664 行约 30ms）。收益：

1. 行数上限只剩一条，且是显式的（文件体积）；
2. 预览与提交**天然同口径** —— 同一份 `analyze()`，不可能分叉；
3. 提交请求体从「几万行 JSON（~6MB，逼近 jsonLimit 8mb）」变成「文件 base64（~55KB）」；
4. 上一轮「只列异常行」之后，那些正常行前端**根本不渲染**，却仍要完整回传 —— 现在这个别扭也没了。

实现要点：

- 抽出 `private async analyze()`（解析 → 校验 → 分类匹配 → 去重 → 汇总），
  **preview 与 commit 共用**。commit 不再有自己那套逐行逻辑。
- `ImportCommitDTO extends ImportPreviewDTO`（同形状），前端 `commitImport` 与 `previewImport` 同签名。
- `preview()` 的 `rows` 只回传 `ABNORMAL_STATUS` 三种；新增 `abnormal` 字段给总数
  （`rowsTruncated` 现在指的是「异常明细被截断」，**与导入条数无关**）。
- 结果态补 `unmatched` 计数：分类降级是**导入成功**，不该混进 `failed`。
- 前端 `pickedFile` 记住选中的文件，提交时原样再传一次（后端刻意不存会话状态 —— 没有上传中间件、
  也没有临时目录，为一次导入引入「上传会话 + 过期清理」不值当）。
- **切「跳过疑似重复」改为重新请求预览**：前端手里只有异常行，算不出 `importable`。
  代价一次解析，换来口径唯一。

### 14.3 测试与文档

- **单测 31 → 32**：新增 **★「超过旧上限（2000 行）也能全部导入」**（2100 行真跑一遍），
  这条就是钉住天花板的 —— 谁再引入按行数截断它立刻红。
- 新增 `analyzeOf()` 测试助手：直接调私有 `analyze()` 拿**全部行**。
  理由：`preview().rows` 是「为省流量裁剪过的视图」，拿它断言「正常行解析对不对」，
  等于让被测对象决定测试能看到什么。
- 回归 **84 → 88**：提交用例改成传文件；条数断言改为**相对量**（基线 + N）——
  之前写死 0 / 4，而默认账本在脚本前面已被塞过几笔，一跑就碎（这次真碎了）。

## 十五、流水导入页可快速切换账本（luchao 要求）

### 15.1 做法

**选择态**：「导入到」那一行改成**可点**（右侧加 `icon-chevron-right` 箭头 + `:active` 按下态），
点击弹 action sheet —— **与首页 banner 左上角切账本是同一套交互**（同样的
`itemList`、同样的「（默认）」后缀），免得同一个动作在两个页面长得不一样。

**预览态**：汇总卡右上角的账本名也可点（配 `icon-chevron-down`）。

### 15.2 关键判据：换账本必须**重新预览**

预览结果里**每一项都是按账本算出来的** ——
分类匹配用该账本的分类树、疑似重复查该账本已有流水、将导入条数由前两者决定。
换了账本却留着旧报告，用户会照着一份**错的报告**点「确认导入」。

所以：

| 所处阶段 | 换账本后 |
|---|---|
| 选择态 | 只更新文案（还没有报告，没有可失效的东西） |
| 预览态 | **重新请求预览** |
| 结果态 | 退回预览态 + 重新请求预览 |

与「切跳过疑似重复开关」是同一个判据：**任何影响服务端结论的操作，都要重新问一次。**

### 15.3 验证（新增 `scripts/verify-import-account.mjs`，21 项）

脚本建**两个**临时账本，刻意让它们对同一份文件的报告不同：

- A：从母本复制**全部**分类 → 分类降级 **1** 条
- B：`copyAll: false, categoryIds: []` → 一个分类都没有 → 4 条**全部**降级

于是「换账本有没有重算」有了一个**肉眼可判、且不依赖时序**的判据：
分类降级数在 4 ↔ 1 之间跳。实测：

```
[2] 点账本行 → action sheet → 选中 B        → 文案立即变 B
[3] 在 B 预览                                 → 分类降级 = 4
[4] 预览态换回 A                              → 分类降级 = 1（同一份文件，总行数仍 4）
[5] 确认导入                                  → 提交打到 A；A 有 4 条；B 有 0 条
```

**负向验证**：把「换账本后重新预览」那段摘掉 → **FAIL=5**
（汇总卡账本名不更新、报告没重算、提交打到了 B、B 被写入、A 为空），
恢复后 md5 一致、`PASS=21`。

> ⚠️ 这次负向验证**第一次没生效**：改了磁盘，但 dev server 服务的是旧模块。
> 查 `curl http://127.0.0.1:5173/src/pages/import/index.vue` 才发现 ——
> **改完必须回读 dev server 实际吐出的内容**，别假定 HMR 一定跟上。

### 15.4 一处实现细节

`.summary-account-tap` 用 **负外边距**（`margin-top/bottom: -10px`）把点击区撑到
`$touch-target-min`(44px)，**但不把卡片撑高** —— 视觉零变化。
理由：账本名只有 12px 高，直接点很难点中；而给它加 padding 会把汇总卡顶高 20px。

另：新增的 `.card-value-strong`（当前账本名）只改**颜色 + 字重**、不加字号 ——
字号阶梯每加一条都要动 `check:contrast` §13④ 的计数断言，不值当。
实测 import 页 `font-size` 仍为 **21** 处，计数断言未动（240/238）。

## 十六、P2 池第 1 项：分类拖动排序（luchao 要求，逐条确认后实施）

### 16.1 十一个决定（每个都单独确认过）

| # | 决定 | 关键理由 |
|---|---|---|
| D1 | 按住把手**立刻**拖，不做长按等待 | 进排序态的意图就是排序，误触成本≈一次无变化的松手 |
| D2 | 排序态**全部折叠** | 让「屏幕上只有正在排的那一层」成为不变式 |
| D3 | 拖到边缘**自动滚动** | 一级 13 行 = 728px > 可用 668px，需要跨屏 |
| D4 | 只改本地，点「完成」**统一提交** | 所以顶栏必须有「取消」 |
| D5 | 串行提交，**遇错即停、已成功的保留** | 提示要说清哪层没存 |
| D6 | 拖动中列表**不重排**，用**落点提示线** | 与 D3 叠加时不会出现两层位移互相干扰 |
| D7 | 一级/二级把手**共存**，一次只展开一个组 | 一次排序能改两个层级 |
| D8 | **点一级行**展开/折叠，展开新的收起旧的 | 与普通态交互一致，不用学第二套 |
| D9 | 拖一级时**自动收起**它的二级 | 让「被拖的永远是一个单行」成立 |
| D10 | 顶栏**「取消」** + 底栏**「完成」** | 顺带修掉两个「完成」的重复 |
| D11 | 底栏普通态改**三格图标栅格** | 三种模式底栏高度一致，切换不跳 |

### 16.2 后端：`POST /api/categories/reorder`

**作用域是 `(accountId, type, parentId)` 三元组**，不是整个账本 ——
支出/收入的一级各自从 0 编号；一级与二级是两层独立顺序。

四道校验，任一不过**整单拒绝**（不做部分写入）：

| 校验 | 错误码 |
|---|---|
| 列表内有重复 id | `40011` |
| id 不属于当前账本 | `40401` |
| id 落在作用域外（跨级/跨类型） | `40012` |
| id 集合 ≠ 该层级全集 | `40013` |

> **为什么「不是全集」必须拒绝**，而不是「按传入的重排、剩下的保持原样」：
> 归一化会重写 `0..n-1`，未列出的分类原本的 sort 必然与新值撞车或错位，
> 结果是一个**没人能预测的顺序**。宁可报错让客户端补齐。

写入在**单个事务**内完成（排序是多行的一致性约束，半套顺序比整体失败更难恢复）。

### 16.3 前端：几何模型（四条不变式）

写在 `pages/category/index.vue` 的注释里，改之前先读：

1. **被拖的永远是一个单行**（D9 保证）→ 落点算法只有一套。
2. `drag.fixedTop` 是按下瞬间那行的**视口 top，永不改变**；
   浮层位置 = `fixedTop + dy`，`dy = clientY - startClientY`。
   即**浮层只跟手指**：自动滚动时手指不动、浮层不动，列表在它下面滚。
3. `drag.rects` 是各行**当前的**视口位置，随自动滚动整体平移。
4. **行位置不做每帧重测**。滚动 s 像素 = 所有行的视口位置整体上移 s，
   自动滚动每一步直接平移 `rects` 即可 —— 精确，且避开了
   `createSelectorQuery` 每帧异步测量与渲染抢时序（那正是抖动的来源）。

### 16.4 三个容易踩的实现细节

- **浮层必须放在 `scroll-view` 外面**。scroll-view 在 H5 上是 overflow 容器，
  放在里面的行一 translate 出边界就被裁掉（拖到顶/底部时整行消失）。
  流内的源行用 `visibility: hidden` 保留占位（不用 `display: none`，
  否则下面的行会上移一下，看着像跳）。
- **松手后要短暂忽略行的 click**（`suppressClickUntil`）。把手在行内部，
  H5 上按住拖完会照常合成一次 click 冒泡到行 → 触发展开/折叠，
  表现为「拖完顺手把组开关了一下」。300ms 足够。
- **`touch-action: none` 必须写在把手上**。否则移动端会先按滚动处理，
  第一次 touchmove 就被当成滚动手势收走。
