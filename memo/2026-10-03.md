## 二、改了什么（都改在 `scripts/verify-report.mjs`）

### 2.1 时序：固定 `waitForTimeout` → `waitText()`

```js
const waitText = async (needle, ms = 20000) => {
  try { await page.waitForFunction((n) => document.body.innerText.includes(n), needle, { timeout: ms }); return true; }
  catch { return false; }   // ⚠️ 超时不抛
};
```

两个设计点：
- **等文字而不是等固定毫秒**：Vite dev 首次访问报表页要现场编译，2500ms 在冷启动/高负载下远不够，
  于是断言取到的是**上一个页面**的文本 → 把"页面没加载完"误报成"页面缺内容"。
- **超时不抛**：抛异常会中断整个脚本（后面的检查一条都跑不到）。让它继续，
  由**断言本身**去红 —— 红在"内容缺失"上比"脚本崩了"有信息量。

结果：`[1]` 4/4、`[2]` 5/5 全绿（修前 3 红 + 5 红）。

### 2.2 日历依赖：硬编码期间 → 从页面自己的请求里捕获

```js
page.on('request', (req) => {
  const url = req.url();
  if (!url.includes('/api/statistics/report')) return;
  const p = url.match(/[?&]period=([^&]+)/);   if (p) lastReportPeriod = decodeURIComponent(p[1]);
  const a = url.match(/[?&]accountId=([^&]+)/); if (a) lastReportAccountId = decodeURIComponent(a[1]);
});
```

断言改成针对**页面实际显示的那个期间**；若该期间没数据，则：
① 先断言"空状态确实正确"；② 再切「年」粒度（与基础统计 Tab 同一份数据）跑全量检查。
两条支路都会打印走了哪条（`ⓘ` 行），**绝不静默跳过**。

顺带**收紧了一个逃逸阀**：原来的
`check('分类 Tab 使用二级口径…', l2.length === 0 || hitL2.length > 0)` ——
`l2.length === 0` 会让"接口返回空"时**白过**（又一个不会红的校验器）。
无数据分支现在被显式处理了，所以收紧成 `l2.length > 0 && hitL2.length > 0`。

## 三、修的过程中挖出的三个坑（比原判断更多）

### 3.1 ⚠️ `accountId` 必须带上，否则比对的是**另一个账本**

页面发的是 `/statistics/report?period=…&accountId=3`，而原探针自己 `fetch` 时**不带 accountId**
→ 后端按"默认账本"算。9 月那轮恰好默认账本也有数据，所以"看起来是对的"。

带上之后立刻看出差别：同一期间 `period=2026`，不带 accountId 返回 **81** 个二级分类，
带 `accountId=3` 返回 **10** 个。
**教训：判据与被判定的对象必须用同一组参数。** 这条适用于所有"页面 vs 接口"的比对型探针。

### 3.2 ⚠️ `支出分类统计` 不能当"数据已就绪"的判据 —— **我据此错了两次**

它是模板里的固定文字，**不等数据就会出现**：

- **第一次**：据此认为"当月（2026-10）有数据"，还写下了这个结论 ——
  其实 dump 到的是**上一个 Tab 的旧 DOM 没被覆盖**。
  后来**直接查接口才推翻**：`period=2026-10&accountId=3` → `summary.count: 0`、`L2: 0`，**确实没数据**。
  （同一次查询对照：`2026-09` → `count: 15`、`L2: 10` = 电脑 33.27 / 私家车费用 29.11 / 早午晚餐 13.42。）
- **第二次**：据此断言空状态，而取文本时 2026-10 的响应还没渲染 → 拿到旧数据 → 假红。

**正确做法：等待判据要用"真实数据里的字符串"**（本轮用第一个二级分类名 `l2[0]`），
不能用页面骨架文字。**"能 dump 到内容"不等于"内容属于当前状态"。**

### 3.3 ⚠️ 修完剩下的 1 条红：**环图分类名被截断**（被长期掩盖的真实缺陷）

断言 `名称可用宽度 ≥ 46px（≈4 个汉字）` 实测 **35px**。几何实测（`scrollWidth` vs `clientWidth`）：

| 分类名 | 显示宽 | 实际需要 | 被截断 |
|---|---|---|---|
| 私家车费用 | 35px | 60px | ✅ |
| 早午晚餐 | 35px | 48px | ✅ |
| 日常用品 | 42px | 48px | ✅ |
| 意外丢失 | 42px | 48px | ✅ |
| 工资收入 | 27px | 48px | ✅ |

**为什么一直没被发现**：`[6]` 段长期因"当月无数据"整段红，躲在后面的这条真缺陷没人看见。
—— **红得太多 = 没有红。**

**成因（算出来的）**：

```
LABEL_GAP = outerR + 8，而 outerR = size/2        ⇒ size 130 → gap = 73 ✓ 与实测一致
名称可用  = 容器半宽 − LABEL_GAP − 百分比宽 − 3
          = 311/2 − 73 − 45 − 3 = 34.5 ≈ 35px   ✓ 与实测一致
```

关键在**容器宽度**：`.panel` 是 `margin: 16px` + `padding: 16px`
⇒ 容器 = 375 − 2×16 − 2×16 = **311**（实测 `wrapW = 311` ✓）。
而 `RingChart.vue` 注释里那笔账用的是「面板宽 **343**、半宽 171.5 → 名称约 50px」——
343 是**面板外宽**，不是环图容器的实际宽度（少算了 16px×2 的内边距）。
⇒ **断言目标 46px 是按 343 标定的，实际容器只有 311，差 32px。**

> ⚠️ **我先前写错并已更正**：本文初版说"百分比文字从约 33px 变宽到 45px 挤压了名称列" ——
> **错的**。注释里那笔账本来就用 45px，百分比宽度没变。真正的差额在**容器宽度**。

⚠️ 因此**「放大环」是反向的**：`LABEL_GAP = size/2 + 8`，size 130→150 时 gap 73→83，
名称可用反而掉到 **24.5px**。环越大，标注被推得越靠外、留给文字的空间越少。

`RingChart.vue` 的 `.ring-label-name` 本身有 `text-overflow: ellipsis`，注释写明
「名称可压缩、百分比不可压缩（占比是这一屏的核心信息）」—— 所以**截断是刻意取舍**，
问题只在于"留给名称的空间掉到了它自己声明的目标之下"。

**这是一处设计取舍 → luchao 拍板「收紧面板留白」**：

`.panel` 由 `margin16 + padding16` 收紧为 **`margin 8 + padding 12`**
⇒ 环图容器 311 → **335** ⇒ **名称可用实测 47px ✅**（目标 46px），`[6]` 段 9 红 → **0 红**。

⚠️ 我在给选项时**错了两次，都已更正**：
1. 我给的四个选项里"**放大环**"是**反向的** —— `LABEL_GAP = size/2 + 8`，环越大名称越窄；
2. 随后给的"margin 16→8 → 50.5px"**算错了**（漏了 padding）。
   正确约束是 `margin + padding ≤ 20.5`，所以取 8+12。
**教训：这类几何量必须把公式写出来代进去算，不能凭差值目测。**

### 3.4 ⚠️ 该改动带出一个我没预见到的副作用（趋势图 chip 对齐）

面板变宽使趋势图 canvas **311 → 335**，于是 `chip 落在该月份的 X 轴位置上（误差 ≤2px）` **由绿转红**。

实测定性：
- 标签实测 `01月@44 … 11月@276` ⇒ `each = 23.2`；组件算的 `(335−15−42)/12 = 23.17` —— **两者一致，没有每格漂移**。
- 偏差**恒定约 2px**：组件以 `o.area[3]`(=42) 为基准，uCharts 实际把标签画在 **44**。
- 所以这条断言本来就**贴着阈值**：311 时 ≈1.5px（过）、335 时 ≈2.0px（不过）。
- chip 宽约 30px，2px 偏移仍完整覆盖文字，**肉眼不可辨** —— 断言比它的意图更严。

**→ luchao 拍板：阈值 ≤2px → ≤3px，并把实测依据写进断言旁边**（不是"为了把红改绿"）：
2px 是**恒定基准差**（组件用 `area[3]`、uCharts 画在 +2px）不是每格漂移，断言本来就贴着红线；
真实意图是"chip 盖住文字"，chip 宽 30px、2px 偏移仍完整覆盖；≤3px 仍能抓住真错位（>5px）。
断言旁已写明**不要改回 2px**（会随机假红，而假红会训练人忽略红色）。

最终实测：`chip 误差=2.14px`、`名称可用=47px`。**`verify-report` 现在 47 通过 / 0 失败、退出码 0。**

> **教训一：改布局类属性要连带跑几何类断言**，别只看被改的那一处。
> **教训二：给方案时也要把数算对** —— 我这次错了两次（"放大环"方向反了、"margin 16→8"漏算 padding），
> 根因都是**凭差值目测而没有把公式代进去**。

## 五、4.4 请求层「传输层失败自动重试」+ 4.3 降级

### 5.1 落点：原计划的 A / B 两条路都没走

原计划二选一：**A. 包一层薄模块** `utils/http.ts`（要动 5 个 api 文件的导入）／
**B. 在实例上包 `request()`**（猴补丁第三方库）。实际调研后**两条都不必**：

**事实一：全站调用形状收敛在 4 个方法上。**
`http.get`(12) / `http.post`(14) / `http.put`(3) / `http.delete`(4) = 33 个点，
**全在 5 个 api 文件里**，没有任何 `http.request(...)` 直调。
⇒ 直接改 `utils/request.ts` 内部的接线即可，**零调用点改动**（33 个点一个没动）。

**事实二：`mergeConfig()` 只保留白名单字段。**
`luch-request` 的 `src/lib/core/mergeConfig.js` 里 config 是**逐字段挑出来**的：
`baseURL / method / url / params / custom / header` + 少数几个枚举字段
⇒ **任何自定义字段都会被丢掉**，`custom` 是唯一自由通道，也是官方扩展位。
所以重试计数走 `config.custom.__attempt`，**不是猴补丁**。

⚠️ 这个事实值得单独记：`config.getTask` 也在白名单里（说明自定义**函数**能传），
但**任意自定义键**不能 —— 我一开始想用 `config.__attempt`，读了 `mergeConfig` 才发现会被丢。

**最终落点**：响应拦截器**失败分支内部**接线 + 判据抽到 `utils/retry.ts`（纯函数，29 条单测）。

⚠️ **为什么必须写在拦截器内部**：`luch-request` 把请求链串成
`promise.then(fulfilled, rejected)`，失败分支是链子最后一环。若包在外层，
下面那段"弹 toast / 401 跳登录"会在**每一次失败**都跑 —— 重试 3 次就弹 3 次 toast、
跳 3 次登录页。写在内部并**提前 `return http.request(config)`** 才能保证只有最终失败才提示。
（`verify-retry.mjs` 里有一条**结构判据**钉着这件事。）

### 5.2 实测到的三种失败形状（最关键的一手数据）

用 Playwright 拦截请求制造真实失败，实测（不是照源码猜）：

| 场景 | 制造方式 | 实测 `statusCode` | 实测 `errMsg` |
|---|---|---|---|
| 断网 / 连接被拒 | `route.abort('failed')` | `undefined` | `request:fail` |
| HTTP 500 | `route.fulfill({status:500})` | `500` | **`request:ok`** ← 反直觉 |
| 超时 | 请求挂起，等 XHR 自身 10s 超时 | `undefined` | `request:fail timeout` |

⭐ **500 的 `errMsg` 是 `request:ok`**：HTTP 500 在 XHR 层面算"收到了响应"，
uni 的 `invokeSuccess` 给它打 `request:ok`，是 `luch-request` 的 `settle()` 再按 `statusCode` 判失败的。
⇒ **判据里"必须有 statusCode"与"errMsg 必须以 `request:fail` 开头"是两道冗余防线**。

一个副产品发现：**负向验证必须拆得足够深才见红**。
我先只拆掉「errMsg 前缀」那条 → 场景 C（500 仍不重试）**依然是绿的** ——
因为 `statusCode` 那条把它拦住了。要证明脚本是活的，得把**全部判据**去掉。

### 5.3 对原计划的**两处刻意收窄**（都写进了代码注释）

1. **超时不重试**（原计划写"仅网络错误/超时"）：
   本项目 `timeout` = 10s，超时意味着用户**已经干等 10 秒**，再重试 2 次 = 30 秒才反馈，
   比直接报错更糟。重试预算留给**瞬时失败**（断网/连接被拒/连接重置）——
   这类失败几乎立即返回，重试只多几百毫秒退避。
   ⇒ **先实测出"超时与断网的 errMsg 确实不同"，才据此收窄的**（有实测表为据）。
2. **写接口一律不重试**（原计划写"POST 新增流水可以，因为有 `clientId` 幂等键"）：
   `clientId` 只存在于 `createTransaction`，**不是所有写接口都有**。逐个甄别不值得 ——
   误重试写接口（重复提交）的代价远高于少救回一次请求。

### 5.5 踩的坑：`page.goto` 到「与当前完全相同」的 URL 不会导航

`verify-retry.mjs` 第一次跑时，场景 A~D 全是"实际 0 次请求"，而基线正常。
根因：脚本用 `gotoTab('/pages/flow/index')`，但页面**已经在这个 hash 上**了 ——
`goto` 到完全相同的 URL（含 hash）时浏览器**不做任何导航**，
页面不重新走 `onLoad/onShow` ⇒ 一次请求都不发。
（而基线是从 `#/` 切过去，属于真导航，所以是好的 —— 这个对比正好暴露了原因。）

修法：URL 相同则改 `page.reload()`。
**教训：导航类断言要先确认"导航真的发生了"**，否则数出来的 0 会被误读成"功能没生效"。

## 六、3.2 / 4.5 收口：luchao 拍板都不做

**3.2（`byId` / `fullNameOf` 的 O(n) getter）—— 收益概率太低。**
量级算出来就明白了：89 条 × 100 行 × 1~2 次 ≈ **1.8 万次 `Array.find`** ≈ **不到 1ms**，
正常就在一帧（16.7ms）的噪声里。计划本来就只安排"测量"不安排修复；
既然最可能的结论是"不需要改"，再花一轮去证明它不划算。**这是量级判断，不是"不敢测"。**

**4.5（brotli）—— 自托管场景下量级不划算。**
brotli 本身有效（入口 103.2 KB → 约 82~88 KB），但**换算成用户实际等待**后：

| 网络 | 省 20 KB ≈ |
|---|---|
| 内网（100 Mbps）| **1.6 ms —— 无感** |
| 4G（约 3 Mbps）| 约 53 ms |
| 弱网（500 kbps）| 约 320 ms |

本项目是**自托管**（`deploy/` 无 CDN 配置、有 `docker-compose.nas.yml`），主要走内网
⇒ 收益落在"无感"档。代价却是换 nginx 镜像（官方 alpine 没编 brotli 模块，
写 `brotli on` 会**启动失败**）+ 改 `precompress.mjs` + 验回落路径 + 重跑部署验证，
**改坏了是线上事故**。
⚠️ 还有个**方向相反**的账：开 brotli 会让产物多一份 `.br`（与 `.gz` 并存），
与刚做完的 5.1（删 730 KB）方向相反，要一起算净账。

**两份文档已同步**：执行计划的 §0.1 / §0.2 / 状态表 / §5.8，以及建议文档的

## 十、批次⑤：D1 分组展开 / 收起（`grid-template-rows`）

**做法**：`pages/flow` 的 `.group-body` 从 `v-if` 卸载改为 `grid-template-rows: 0fr → 1fr`，
并包一层 `.group-body-inner`（`min-height: 0`）。

**为什么不用 height / max-height**：
- `height: auto` 不可过渡（浏览器不知道目标值）；
- `max-height` 猜一个大值会让**时长随内容量漂移**（内容少时表现为"点了没反应、然后突然收起"）；
- grid 的 `0fr → 1fr` **不需要预设高度**，且时长恒定 ✅

**改了三处**（都在 `pages/flow`）：
1. 模板：`.group-body` 改 `:class="{ open: expanded.has(g.key) }"`，并包一层内层；
2. 模板：`EmptyState` 条件补 `expanded.has(g.key) &&`
   —— 折叠时 `details[key]` 未加载，`!undefined` 为真会渲染「该时段无流水」；
3. 样式：`.group-body` 改 grid；`.group-body-inner` 加 `min-height: 0`。

**验收**：`verify-motion.mjs` 扩到 **14 通过 / 0 失败**（新增第五节 3 条判据）；
`verify-flow` **31/0**；`check-contrast` **158/0**；`vue-tsc` **0**。

**关键实测**：收起采样 `1395 → 1031 → 713 → 570 → 321 → 217 → 62 → 0` —— 干净的 ease-out 曲线。

**⚠️ 负向验证实证了 grid 折叠的经典坑**：去掉 `.group-body-inner` 的 `min-height: 0` 后，
收起时高度**纹丝不动（1395px 全程不变）** —— 不是"留一截"，是**功能直接坏掉**（点收起毫无反应）。
（原因：grid 子项的 `min-height` 默认是 `auto`，它会拒绝被压到 0。）
⇒ 探针里那条「收起后高度归零」是这个坑**唯一的守卫**，值得长期留着。

## 批次⑥ C3 · 骨架 ⇄ 内容交叉淡入

**做法**：三个整屏骨架处（`pages/flow` · `HomeView` · `ReportView`）统一成
`.cross-host`（`position: relative`，只为提供定位上下文）> `<Transition name="cross">` > 互斥分支；
规则**一处定义在 `App.vue`**（`.cross-enter-active` 200ms `ease-out` / `.cross-leave-active`
150ms `ease-in` + `position: absolute` 脱流）。

**三条实现要点（都是实测逼出来的，不是设计出来的）**：

1. **绝不能只做"内容淡入"** —— 骨架瞬时撤掉 + 内容从 `opacity: 0` 渐显，前几十毫秒内容
   几乎不可见，**等于亲手制造空白帧**，比瞬切更差。消除闪白只能靠**交叉**。
2. **绝不能加 `mode="out-in"`** —— 那是串行，中间必然有"两边都不在"的一帧（就是闪白）。
   负向验证实测：加了它**交叠帧 = 0**。
3. **离开的那一块必须脱流**（`position: absolute`）—— Vue `<Transition>` 默认就是"两边同时在
   DOM 里"（这正是交叉的实现方式），不脱流则容器高度 = 两者之和。
   负向验证实测：去掉脱流后容器高度 **1473 → 2057（+584px）**。

**⚠️ 本轮最重要的发现：加动画会把一个既有的、首帧渲染错分支的缺陷从"看不见"变成"明显可见"。**

`skeleton` 初值是 `false` ⇒ **首帧**落到 v-if 链最后一个分支 ⇒ 先渲染一次
「该条件下暂无流水」（ReportView 是「…暂无记录」、HomeView 是 **¥0.00**），再被骨架顶掉。
**以前只闪 1 帧（~16ms）、基本看不见；有了 150ms 淡出后，它会在屏幕上停留 0.15 秒。**

发现路径本身就是判据的胜利：探针打印了交叠帧的 `.cross-host` 结构 ——
`empty[leave] + 骨架[leave] + 内容[enter]` **三块同时在场**（`abs 取值 2` 而不是 1）。
若只写"交叠帧数 > 0"就会放过它。

**修法**：三个视图的 `skeleton` 初值改 `true`（首屏 = 首次挂载 = 必然在加载）。
安全性依据：三处加载入口（`onLoad` / `onMounted`）都是**无条件**调用的，
初值 `true` 一定会在数据回来后被 `skeleton = false` 收掉。


明细在 RTT 之后才替换内容 ⇒ 容器一帧内撑开。

⚠️ **第一版探针的结论是错的**：用「天」粒度测，每组只有 1~2 笔，突变只有 53px、不显著，

**教训：测"突变量级"之前先确认样本够大，否则量到的是噪声。**

### 为什么 CSS 侧救不了（反直觉，值得记）

transition 比较的是**指定值**，不是它解析出来的像素：
- `height: auto → auto` —— 浏览器不知道中间值；
- `grid-template-rows: 1fr → 1fr` —— **指定值根本没变**（`1fr` 一直是 `1fr`），
  变的只是解析出的像素 ⇒ **D1 那套 `0fr → 1fr` 在这里不触发**。

### 修法（`flow` 的 `animateGroupBodyGrow`）

数据变更**前**量下当前高度 → `await nextTick()` 让新内容渲染 → 显式把容器高度从旧值喂到新值。
⚠️ 两条硬约束：
1. **必须作用在容器 `.group-body`，不能是 `.group-body-inner`** ——
   inner 是 grid item，默认 `align-self: stretch`，给它设 `height` 会被轨道覆盖而无效；
   容器上已有 `overflow: hidden`（D1 留的），正好用来裁剪过渡中未长满的内容。
2. **收尾必须 `setTimeout` 兜底**，不能只靠 `transitionend` —— 元素可能在过渡结束前
   被收起/卸载，那时事件不来，而**残留的 inline `height`** 就是 `min-height: 0` 那个坑的
   同款故障（高度被钉死、再也压不下去）。
3. 量高度前必须 `await nextTick()`，否则量到的是上一帧的内容（展开前的 0）。

**实测修复后**：`0 → 56 → 56 → 404 → 562 → 710 → 847 → 973 → 1086 → 1186 → 1270 → 1336 → 1379 → 1395`
（13 帧 ≈ 217ms，与 0.2s 吻合。首帧 348px 是 `ease-out` 正常起步 ——
`cubic-bezier(0,0,.58,1)` 在 t=0.077 已走约 31%，理论值 471 ≈ 实测 404 ✅）

**验收**：`verify-motion` **22/0**（新增 1 条守卫）· `check-contrast` **158/0** ·
`verify-flow` **31/0** · `verify-report` **47/0** · `vue-tsc` **0**。
负向验证：停用 `animateGroupBodyGrow` → 「取到 **0** 个中间高度」红 ✅

⚠️ **守卫判据刻意不用阈值**（如"单帧增长 < 400px"），而是看「**有没有中间高度**」——
突变序列 `0 / 56 / 1395` 取不到任何中间值，真实缓动则会经过一串中间值。
**这样阈值怎么定都不会误报，也不会换个数据集就假红。**

## C4 交互 v2 · 改「提前预加载」（luchao 要求，不等触底）

**阈值**：`PREFETCH_VIEWPORT_MULTIPLE = 1.5` ⇒ 实际阈值 = **1.5 × 可视区域高度**（375×812 ⇒ **1218px**）。
- 用"视口高度的倍数"而非固定 px：固定 px 在小屏提前量过大（浪费流量）、大屏过小（等于没预加载）。
- 取 1.5（需求给 1~2）：1.0 = 到底才拉 ⇒ **没有真正提前**；2.0 对"一次翻一页"偏多。
- **数值现算**（每次读 `window.innerHeight`），不缓存 —— 地址栏收起 / 横竖屏会改视口高度。
- 触发器是 `onPageScroll`，但**位置现算**（`window.scrollY`）—— `e.scrollTop` 各端不一致。

**结构**：`maybePrefetch()` 三道闸（① `autoLoadingKey` 空 ⇒ 一次只预取一组 ② `loadingMore` ⇒ 同组不重入
③ 400ms 冷却 + 24px 级联守卫）。`onReachBottom` **降级为兜底**（预取失败重试 / 用户直接跳到底），
且此时失败**弹 toast**（他到底了，提示才有意义），而预取失败**静默**（不打断滚动）。
页码用 `st.page + 1` 单调递增；末页由 `hasMoreDetail` 判，返空时 total 收到实际条数、按钮消失。

**验收**：`verify-flow` **36 → 38 全绿**。关键实测：**距底部 1076px 时就已发出 `page=2`**
（`scrollY=182 / maxScrollTop=1258`）⇒ 到达底部时数据已就绪。
`verify-motion` 22/0 · `check-contrast` 158/0 · `verify-report` 47/0 · `reflow-audit` 90 屏 4 红（与基线一致）· `vue-tsc` 0。

### ⭐ 又一次被负向验证救下假绿（同一类错误的第二次）

判据「**未触底**就已预取 page=2」在阈值改成 0 时**依然绿**。
根因：我把滚动目标写成「距底部 **0.8 屏**」—— 而 **0.8 屏 < 1 屏**，那个位置落在
**maxScrollTop 之外**，浏览器只能滚到底 ⇒ 触发的是 `onReachBottom` 兜底，判据测的其实是触底。

修法：滚到「距底部 **0.9 屏**」（在 maxScrollTop 之内、且 > 0 所以确实未触底；阈值 1.5 屏仍覆盖它）；
"未触底"的判据用「**还能继续往下滚**」（`scrollY < maxScrollTop`）——
**不要用"预取完成后的距底部距离"**，预取会追加内容抬高 maxScrollTop，那个数字会被"内容变长"掩盖。

⚠️ **规律：判据里"距底部 X"这种直觉算式，先验可达性（`X < 1 屏` ⇒ 那个位置滚不到）。**
⚠️ 这已是本会话第二次"负向验证揭穿假绿"（上一次是冷却判据）⇒
**判据写完必须做负向验证，这不是可选项。**

## 15:10 流水页日头：只有「月粒度」不带月份，其余全带

**需求**（luchao）：流水页分组时，**除了以月分组，其他维度的日头都要加月份**。

**原状**：判据内联在模板里 —— `dayHeader(day.date, groupBy === 'category')`，
即**只有分类维度**带月份。时间维度的年/季/周三种粒度下，日头是「15日 周一」，
完全看不出是哪个月。

**改法**：判据收成一个具名 computed，别再内联：

```ts
const dayHeadWithMonth = computed(() => groupBy.value === 'category' || unit.value !== 'month');
```

**为什么年/季/周都必须带**（不是"顺手统一"，是各自有具体理由）：

| 粒度 | 组头 | 明细跨月？ |
|---|---|---|
| 年 | 「2026年」 | 跨 12 个月 |
| 季 | 「3季度」+ 2026 | 跨 3 个月 |
| **周** | 「第40周」+ 2026 | ⚠️ **ISO 周会跨月**（如 9月30 ~ 10月6）—— 这是最容易被漏掉的那个 |
| 月 | 「9月」 | 不跨 → **唯一该不带月份的情况** |
| 天 | 「9月14日」+ 2026 | 不跨，但与组头重复（见下） |
| 分类 | 「餐饮」 | 跨多个月 |

⚠️ **「天」粒度是个自觉的取舍**：组头已是「9月14日」，日头再加月份确实冗余。
但"某个粒度单独开口子"正是下次改错时最难排查的那类分支，所以**规则统一、不例外**。
这一条已在代码注释里写明理由，不是无声的重复。

**守卫：新规则的唯一判据在 `verify-edit-category.mjs`** —— 原来只有 ①（月粒度不带）
和 ②（分类维度带），**年/季/周三条完全没覆盖**，把判据退回旧写法也不会有人发现。
新增 ①b 循环跑 年/季/周，每档都断言日头匹配 `/^\d{1,2}月\d{1,2}日\s*周[一二三四五六日]$/`，
跑完复位到「月」。

| 改后 | **PASS=30 / FAIL=0**（月「3日 周六」· 年/季/周/分类「10月3日 周六」） |
| **负向验证**（判据退回 `groupBy === 'category'`） | **PASS=27 / FAIL=3** —— 年/季/周三条全红，反例 ① 仍绿 |

**⚠️ reflow 的覆盖缺口（本次差点漏掉）**：`reflow-audit.mjs` 那批 `flow-*` 屏巡检的
**全是默认月粒度**，而日头变长这件事**只在非月粒度下发生** ——
"点不开就扫不到"的又一例。补两屏：
