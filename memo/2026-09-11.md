## 七、踩坑记录（7 个，全部已解决）

### 7.1 CLI + mock + Node24 三方不兼容

现象：`mw dev` 报 "Please add @midwayjs/mock to your devDependencies"

根因：CLI 2.1.1 用 require.resolve 检测 @midwayjs/mock/package.json，
而 mock 4.x 的 package.json 有 exports 且未暴露 ./package.json，
Node 22+ 严格遵循 exports 直接抛 ERR_PACKAGE_PATH_NOT_EXPORTED。

解决：patch-package 给 mock 的 exports 补 "./package.json": "./package.json"。

### 7.2 mock 缺 @midwayjs/logger

根因：mock 的 dist/creator.js 里 require(@midwayjs/logger)，
但 logger 只在 mock 的 devDependencies，不会自动带出。

解决：手动装 @midwayjs/logger@4.0.1。

### 7.3 Docker 代理不生效

根因：Docker Desktop 的代理配置不能只改 ~/.docker/config.json（只管 CLI），
必须在 ~/Library/Group Containers/group.com.docker/settings.json 里配，
且 proxyHttpMode 必须从 system 改为 manual。

解决：改 settings.json，设 overrideProxyHttp/Https + proxyHttpMode=manual。

### 7.4 TypeORM @Check 不生成 DDL

根因：TypeORM 0.3 的 @Check 在 MySQL/MariaDB 方言下不参与 schema 生成。

解决：手写迁移 AddAmountCheck 补 CHECK 约束。

### 7.5 路由全 404（框架未注册）— 三个根因叠加

**根因 A：入口文件加载失败被静默吞掉**
- findProjectEntryFile 用 loadModule(..., { safeLoad: true })
- 临时调试代码有 TS 编译错误 → safeLoad 吞掉错误 → configuration 未识别
- 教训：Midway 入口文件加载失败不会报错，排查时应优先确认入口是否真被加载

**根因 B：文件扫描器必须显式声明（v4 重大变更）**
- Midway v4 的 @Configuration 必须配置 detector
- 否则 controller / middleware / filter 一个都不会被加载
- 正确写法：

```ts
@Configuration({
  imports: [...],
  importConfigs: [...],
  detector: new CommonJSFileDetector({ conflictCheck: true }),
})
```

**根因 C：全局中间件 / 过滤器必须显式注册（v4 不再读 config）**
- config.middleware 在 v4 完全无效（baseFramework 无相关代码）
- filter 也不会自动扫描
- 必须在 onReady 中注册

### 7.6 TypeORM entities 路径规则

@midwayjs/typeorm 内部用 @midwayjs/glob 扫描实体：

- glob 的 cwd = baseDir = <项目根>/src
- 匹配逻辑：文件绝对路径 replace(baseDir, '') 后比对 pattern
- formatGlobString 会给不以 * 开头的 pattern 自动补前导 /

正确写法（相对 src、不带前导斜杠）：

```ts
const entityPattern = relative(join(process.cwd(), 'src'), join(__dirname, '../entity')) + '/*.entity{.ts,.js}';
// 结果：'entity/*.entity{.ts,.js}'
```

错误写法（均匹配不到）：
- join(__dirname, ...) 绝对路径
- '/entity/*.entity{.ts,.js}' 前导斜杠导致重复补 /

### 7.7 BusinessError 状态码映射错误

原实现 Math.floor(code/100)*100 是错的（40901 → 40900，超出范围→500）。
正确：Math.floor(code / 100)（40901 → 409）。

### 15.2 关键设计：VO 必须展示"包装后"的结构

所有 `/api` 响应都会被 ResponseMiddleware 包成 `{code, data, message}`。
若 Swagger 只标 data 类型，前端会写成 `res.data.token`（实际应 `res.data.data.token`）。
因此每个 VO 都显式声明三个字段。

**不用继承**：Midway Swagger 对继承属性的解析不稳定，宁可重复。

### 15.3 顺手修掉两个启动阻塞（都不是 Swagger 引入的，是既有雷）

**坑 8：seed 自执行把服务带走**
- `src/seed/index.ts` 底部无条件调用 `seed()`，而 Midway 扫描器会加载 src 下所有 .ts
- 于是每次启动服务都跑一遍 seed；seed 又复用了带 migrations 的 data-source.ts，
  migration 类没注册进 IoC → `DefinitionNotFoundError` → `process.exit(1)`
- 修：加 `if (require.main === module)` 守卫；seed 内部自建不含 migrations 的 DataSource
- 教训：**src 下的脚本一律不要无条件自执行**

**坑 9：Swagger 被自家 JWT 守卫 401**
- `JwtGuardMiddleware.match()` 原为 `!publicPaths.includes(ctx.path)`，非业务路由也被要求带 token
- 修：非 `/api` 路径直接放行

**坑 10（小）：Swagger JSON 路径**
- 是 `/swagger-ui/index.json`，不是 `/swagger-ui.json`；UI 页是 `/swagger-ui/index.html`

**坑 11（小）：本地 curl 调试要绕代理**
- 本机有 127.0.0.1:7897 代理，curl 访问本地服务会返回 502，需 `curl --noproxy '*'`

### 16.3 关键决策：连真实 DB 而非 mock

service 层重度依赖 TypeORM（实体关系、QueryBuilder、唯一键、外键 CASCADE），
mock 成本高且测不到真实约束。所以直连 MariaDB 容器，
每用例随机用户名建独立用户，`afterAll` 按 userId 清理。

### 16.4 踩坑（4 个）

**坑 12：缺 @types/jest** —— `mw test` 会先跑 TS 类型检查，`Cannot find name 'describe'`。装上即可。

**坑 13：watchman 崩溃** —— 本机没跑 watchman 服务但依赖里有 fb-watchman，
Jest 启动即崩。解决：`jest.config.js` 里 `watchman: false`。

**坑 14：测试"卡住"不退出** —— 自建 TypeORM 数据源没关，连接句柄不释放。
`afterAll` 必须同时 `close(app)` 和 `closeTestDataSource()`。
（第一次跑就是这么挂住的，表现为命令超时被 SIGTERM。）

**坑 15：测试数据互相污染（假失败）** —— 统计用例"未分类金额"期望 100.00 实际 103.00，
根因是同文件前一个用例往同一月份插了两条未分类账单。
修：该用例改用独立月份 2026-10。
教训：**每个断言场景用独立月份或独立用户**。

### 16.5 顺手修的真 bug：清空分类无效（重要）

`PUT /api/transactions/:id` 传 `categoryId: ""` 时接口返回 200，但 **categoryId 仍是旧值**。

根因：`update()` 只改了 `entity.categoryId`，而 `findById()` 已把 `category` 关系对象加载在实体上，
TypeORM 保存时认为"关系未变"，**把外键回填成旧值**。

修（`src/transaction/transaction.service.ts`）：
```ts
if (dto.categoryId !== undefined) {
  const nextCategoryId = dto.categoryId || null;
  patch.categoryId = nextCategoryId;
  if (!nextCategoryId) {
    entity.category = null;  // 关键：同时断开关系
  }
}
```
**教训：改外键字段时，若实体上已加载对应关系对象，两者必须一起改。**

已在回归脚本补对应用例（`clear category -> null`）。

## 二十一、23:10 更新：多账本改造完成

用户要求实现多账本支持。四个关键规则**已用 AskUserQuestion 确认**（用户全选推荐）：

分类**不挂账本**（保持用户级共享）。

### 21.2 迁移（关键：五步，顺序不可变）

`1789137009697-MultiAccount.ts`：
1. 建 accounts 表
2. transactions 加 `account_id` —— **先可空**
3. 为每个既有用户建「默认账本」
4. 回填存量交易到各自默认账本
5. **校验 `account_id IS NULL` 的行数为 0**，再收紧为 NOT NULL + 加外键

> 先可空后收紧，是为了让存量数据有"灌值窗口"；第 5 步的断言避免带脏数据继续。

指纹 = `金额|日期|类型|分类ID|备注`，全同才算重复 → 丢源留目标。
任一字段不同 → 两笔都保留（所以不存在"金额/日期冲突取舍"问题）。
源账本**内部**自带的重复不动（不擅自整理单个账本）。

### 23.2 分类体系（从 9 张图整理）

- **支出**：13 个一级 + 54 个二级
  居家物业(7) / 行车交通(3) / 交流通讯(4) / 休闲娱乐(5) / 金融保险(6) / 其他杂项(3) /

- **收入**：7 个一级（图片没给收入体系，沿用原有并补「报销」）
- 图标：`icon` 字段**直接存 emoji**（几十个分类逐个维护标识→emoji 映射太笨重）

### 23.3 数据模型

`categories` 加 `parent_id` 自引用外键（`ON DELETE CASCADE`）+ `idx_user_parent` 索引。

**唯一键仍是 `(user_id, name)` 全局唯一**，不把 parent_id 纳入：
MySQL 唯一索引不约束 NULL，纳入 parent_id 后一级分类（NULL）的重名反而拦不住。

### 23.4 踩坑：唯一键导致「红包」撞名

新体系里支出的二级分类有「红包」（人情往来下），而收入一级原本也有「红包」，
唯一键冲突 → 收入侧那个被 upsert 覆盖成了支出二级（收入分类少了 1 个）。

**修法**：收入侧改名「礼金」，并在 preset 里写注释说明原因。
（这类冲突只能靠命名规避，或者把唯一键改成 `(user_id, parent_id, name)` + 应用层补一级重名校验。）

### 23.5 数据重建放在 seed 而非迁移

迁移只做结构变更（加 parent_id）。重建逻辑放 `npm run seed`：

1. 按预设 **upsert** 全部一级/二级（同名复用，不打断已有交易归属）
2. 找出不在新名单里的旧分类
3. 其下交易**按收支类型**改挂到回退分类（支出→「其他支出」，收入→「其他」）
4. 删除旧分类（子分类由外键 CASCADE）

为什么不在迁移里做：回退分类属于新体系、迁移执行时还不存在；且分类是 per-user，
在 SQL 里铺开 67 个分类非常笨重。

**实测**：demo 用户 73 → **74 个分类**（13+7 一级、54 二级），清理 9 个旧分类、改挂 1 笔交易。
第二次运行清理 0 个（幂等）。

**踩坑**：`repo.delete(In([...]))` 类型不通过（delete 不接受 FindOperator），要直接传 id 数组。

### 23.6 统计改为按一级聚合

```sql
SELECT COALESCE(p.id, c.id) AS categoryId, COALESCE(p.name, c.name) AS name, ...
LEFT JOIN categories c ON c.id = t.category_id
LEFT JOIN categories p ON p.id = c.parent_id
```

有父取父、无父取自身——用 COALESCE 一步搞定。二级交易自动归到一级。

（改用 raw SQL 后要注意：**TypeORM 的 raw query 不支持 `:name` 命名参数**，必须用 `?`。）
